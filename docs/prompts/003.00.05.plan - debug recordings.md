# Plan: debug recordings (003.00.04 prompt)

- **Branch:** `003.00.05-debug-recordings`, already created from `003.00.03-behaviour-and-scale` so the PRs stack. It
  holds the new prompt and the trimmed 993 prompt.
- **Plan file:** `docs/prompts/003.00.05.plan - debug recordings.md`, written at stage 0 from this draft.
- **Commits:** one per stage. **Orchestrator:** Opus. Sonnet takes the mechanical stages (2 and 4).

## Context

The vision fixtures are still photos, which can't show flicker, lag or quick movement. 003.00.03's camera sessions and
993's jump review both need real footage. This plan adds a recorder to debug mode. It captures a short video of the
camera, plus what the game saw and decided for each frame it processed, and downloads both as one zip.

### What the investigation found

- **Each processed frame passes through one place.** `reportAndDraw` in `startTrackingLoop`
  (`src/components/camera/CharacterCanvas.tsx:~400`) has, for each frame:
  - the model's raw output (`detected: VisionFrame`: masks, key points, scale, strays);
  - the tracked people (`frames`), their floor positions (`where`) and the spectator report (`watching`);
  - the frame's `timestamp` (`performance.now()` when it was given to the model) and `inferenceEnd`.
- **The camera stream** is in `CharacterCanvas` (`mediaStream`), and the HUD is a sibling layer
  (`HudLayerWrapper`, `GameLayerWrappers.tsx:178`). `debug` state lives in `Game.tsx:339`.
- **No zip library is installed.** The browser has `MediaRecorder` (WebM in Chrome, MP4 in Safari) and
  `CompressionStream("deflate-raw")`.
- **Sizes:** a mask is one byte per pixel, about 0.5 MB at the 960-wide model input, but it is mostly runs and
  deflates very well (estimated 20–50×). At about 10 fps that is roughly 10–25 MB a minute per person, plus 15–20 MB a
  minute of video.

## Options

### R1: the video, and matching frames to it

**What's involved:**

- `MediaRecorder` records the camera's `MediaStream` at full resolution.
- The recorder notes `performance.now()` when recording starts (its `start` event). Each processed frame records
  `videoMs = timestamp − startedAt`, so a test seeks the video to `videoMs` to find the frame the game used.

**Pros:** native, small, and the full picture, not the model's scaled-down copy.

**Cons:** timing is approximate, within about a frame, as `MediaRecorder`'s start and the browser's frame times aren't
exactly the same clock. Stage 3's test measures the error.

**Alternatives:**

- **Save each model input as a JPEG in the zip.** Exact, but large, and only at the model's rate.
- **Both.** Rule out unless stage 3 shows the error is too large.

**Recommendation:** select, and measure the error.

### R2: building the zip

**What's involved:** `fflate` (about 8 KB, no dependencies, widely used) builds the zip in the browser, deflating the
masks and JSON and storing the video as-is.

**Alternative:** a hand-written zip writer over the native `CompressionStream("deflate-raw")`. No dependency, but
about 70 lines of format code (headers, CRC32, central directory) to maintain.

**Recommendation:** `fflate`. It's less code, and the tests can unzip with it in Node too.

### R3: the metadata format

**What's involved:**

- `video.webm` (or `.mp4`, whichever the browser records).
- `recording.json`:
  - **header:** app version, the time it was recorded, the camera's label, size and mirror setting, the calibration's
    corners, the model and its settings (the vision, tracking and spectator config), the video's MIME type, and room
    for labels (for 993's calibration game);
  - **frames:** for each processed frame, its index, `timestamp`, `videoMs`, inference time, mask width and height,
    and:
    - `detected`: each person the model found (id, key points, scale, and mask and stray file names);
    - `players`: the tracked state (id, player number, role (player, spectator or held), key points, floor position,
      off-floor distance, feet).
- `masks/<frame>-<person>.bin` and `masks/<frame>-<person>-strays.bin`: raw mask bytes, one byte per pixel.

**Pros:** readable JSON, and binary masks that unzip into typed arrays without parsing.

**Cons:** many small files. Zip handles that fine at these sizes.

**Recommendation:** select. A `RecordingFormat.ts` type describes the JSON, so the tests and 993's bench share it.

### R4: a length cap

**What's involved:** recording stops itself at `recordingMaxSeconds` (default 60, overridable by URL query). The
button shows the elapsed time.

**Pros:** keeps memory bounded on a long-forgotten recording.

**Cons:** none of note.

**Recommendation:** select.

### R5: where the recorder lives, and the controls

**What's involved:**

- `src/debug/Recorder.ts`: a class that holds one recording at a time.
  - `start(stream, header)` discards any held recording.
  - `addFrame(...)`.
  - `stop()` keeps the recording in memory.
  - `download()` builds the zip, saves it, and discards it.
  - It notifies subscribers when its state changes.
- **A context** (`RecordingProvider` in `Game.tsx`) shares one recorder.
  - `CharacterCanvas` registers its stream with the recorder, and calls `addFrame` from `reportAndDraw` only while
    recording.
  - The HUD reads the recorder's state.
- **HUD, while debug is on:**
  - "● Record" becomes "■ Stop 0:12" while recording.
  - "Download" shows only when a recording is held.
  - Both are hidden when the game has no camera.

**Pros:** one owner, and nothing runs when it isn't recording.

**Cons:** a new context. The alternative, passing props through the layers, touches more files.

**Recommendation:** select.

### R6: consent

**What's involved:**

- The button is only in debug mode, and is pressed by the person being recorded.
- A red "Recording" indicator shows while it runs.
- Recordings stay in memory until downloaded, and are never uploaded.
- `docs/camera-mode.md` says so, and asks testers to agree before they're recorded.

**Pros:** no dialog in the way of a quick capture.

**Cons:** consent relies on the operator.

**Recommendation:** select.

### R7: using recordings in tests

**What's involved:**

- `tests/browser/recordings.ts`: unzip a recording, read `recording.json`, and extract the video frame at a
  `videoMs` (seek a `<video>` and draw it to a canvas).
- One Playwright test proves it end to end. The fake camera paints a frame counter, the test records about 3 s and
  downloads it, and then checks that:
  - the zip has the video, the JSON and a mask per detected person per frame;
  - the extracted frame's counter matches the frame time, to within one frame.
- The replay bench (running recordings through models and settings) stays in 993.

**Recommendation:** select.

## Outcomes

### Stage 2 (wiring)

- **Provider:** `RecorderProvider` wraps the game in `LocalGame.tsx`, as the other providers do, rather than in
  `Game.tsx`, which was at its line limit. The scene renderer has no recorder, so its HUD shows no Record button.
- **Source:** `CharacterCanvas` offers the recorder a video factory (`mediaVideoRecorder(stream)`) and a description of
  the camera, rather than the stream itself, so tests need no fake `MediaStream`.
- **Timing:** people readouts and recording now run after drawing, in one `frameReporter`, so the recording's cost
  shows in the readout's draw time rather than its monitor time.
- Done by the orchestrator, not Sonnet, as the context was already loaded.

### Stage 3 (alignment)

- **How it's measured:** the fake camera paints a binary time code across the top of each frame. The test reads the
  time code of each frame the model was given (by wrapping `createImageBitmap`), and of the video frame nearest each
  recorded frame's `videoMs`, and compares them.
- **The start event is late.** Timed from `MediaRecorder`'s `start` event, the video ran one to three frames (32–168 ms)
  behind the model's input, by a different amount each run. Timed from the `start()` call instead, almost every frame
  matched to within one frame (0–40 ms), and the worst was about 80 ms, over three runs of about 70 frames each. The
  recorder now times from the call, and `VideoRecorder.start` no longer calls back.
- **The test asserts** that at least 90% of frames match to within one and a half frames, and all to within three.
- **Seeking:** `MediaRecorder`'s WebM has no seek index, so `playVideoFrames` (`tests/browser/recordings.ts`) plays the
  video and reads each frame with `requestVideoFrameCallback` rather than seeking.
- **Still not deterministic:** matching to within a frame means a replay sees the same picture most of the time, not
  always, as agreed. Recording the model's exact inputs remains the upgrade if replays need to be exact.
