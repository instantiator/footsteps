# Rules for Jump and duck

Most of a runner already works with today's rules and effects:

- Obstacles cross the scene with an indefinite `item-move` effect.
- A hit is `body-enter` on a low obstacle, or `head-enter` on a high one, so ducking needs no new interaction.
- The score rises with an `every` rule, and the run ends with a `when` rule on the lives left, then `resetChallenge` or `completeChallenge`.

What's missing:

| Addition                                                            | Why                                                                                                                                                       |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A `random(min, max)` function in expressions                        | Obstacles arrive at varied times, and vary between high and low. Validation should allow for it, as results can't be predicted.                           |
| Expressions for effect timings (`durationMs`, `cycleMs`, `delayMs`) | Obstacles speed up as the score rises. `every` and `after` already accept expressions.                                                                    |
| `{ "spawn": "<template selector>", "into": "<selector>" }` action   | Adds a copy of a `<template>`'s content, so any number of obstacles can be on screen. Copies are removed when the scene resets, or by a `despawn` action. |
| `{ "despawn": "<selector>" }` action                                | Removes spawned copies, eg. on an obstacle's `animationEnd` once it has left the scene.                                                                   |

Spawning is the biggest of these. Check first whether a fixed set of obstacles, each restarted with a random delay, is enough for a simple runner; if it is, leave out `spawn` and `despawn`, and record them in `docs/outstanding-issues.md`.

# Badges

Show badges on each game's landing page tile and on its landing page:

- **Scene modes** it uses, eg. "2D", "2.5D".
- **Camera:** "Camera", "Camera optional" or "No camera", from its avatar modes.
- **Size:** its number of stages and challenges.
- **Progress:** "% complete", from its completed challenges, when there's a saved game to continue.
- **Sound:** whether it has music or sound effects.

Work them out from the game data and saved progress, so authors don't write them by hand.
