## Rules for Jump and duck

Most of a runner already works with today's rules and effects:

- Obstacles cross the scene with an indefinite `item-move` effect.
- A hit is `body-enter` on a low obstacle, or `head-enter` on a high one, so ducking needs no new interaction.
- The score rises with an `every` rule, and the run ends with a `when` rule on the lives left, then `resetChallenge` or `completeChallenge`.

What's missing:

| Addition                                                            | Why                                                                                                                                                       |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A `random(min, max)` function in expressions                        | Obstacles arrive at varied times, and vary between high and low. Validation should allow for it, as results can't be predicted.                           |
| Expressions for effect timings (`durationMs`, `cycleMs`, `delayMs`) | Obstacles speed up as the score rises. `every` and `after` already accept expressions.                                                                    |
| `{ "spawn": "<template selector>", "into": "<selector>" }` action   | Adds a copy of a `<template>`'s content, so any number of obstacles can be on screen. Copies are removed when the scene resets, or by a `despawn` action. |
| `{ "despawn": "<selector>" }` action                                | Removes spawned copies, eg. on an obstacle's `animationEnd` once it has left the scene.                                                                   |

Spawning is the biggest of these. Check first whether a fixed set of obstacles, each restarted with a random delay, is enough for a simple runner; if it is, leave out `spawn` and `despawn`, and record them in `docs/outstanding-issues.md`.

# Badges

# Bugs

## Bugfix 1

Sometimes when the mouse _starts_ in the right place, the game's reset doesn't seem to detect that it's _already_ there, and waits for it to enter the right element (the workaround is to exit and re-enter). Ideally, if a player or mouse pointer starts in the right place, that should be detected when the scene or reset scene starts.

This should work for both mouse pointer or player feet (or any other trigger's starting state at the start of a scene). Tests should show that this works for each type of trigger and prevent regressions.

## Bugfix 2

When there's a scroll / dialog showing, the player's video appears between the scroll background and the text. The whole scroll should somehow appear in front of the player. Screenshot is from walkaround, which starts showing the overview of Demo scenes (2.5D) with a scroll.

![scroll and camera depth bug](./illustrations/002.03.10%20-%20scroll%20and%20camera%20depth%20bug.png)

Items like scrolls and dialogs are _currently_ only for mouse interaction - so when a dialog shows, it should be in front of any other parts of the scene.

### Continuation

However, there's a future where we may want to see player interaction done with camera. For that to work, we'd need to be able to switch into another mode, where we track the player's hand relative to their head, and use that to calculate a virtual mouse pointer position, and render that on screen with a nice graphic (perhaps with a default, but overrideable per game) for the pointer.

We'll return to it, so please note it in a new prompt for future review as `994.00.00.prompt - virtual pointer mode.md` (with sufficient context to explain the purpose of it).
