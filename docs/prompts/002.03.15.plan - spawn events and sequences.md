## Context

The two prompts meet in the rules engine.

- **002.03.14:** Jump and duck uses a fixed pool of four obstacles, each restarted on `effectEnd`. It can't put more on screen than the pool holds, or pick each obstacle's kind at random. A still mouse pointer only meets an obstacle on its first pass (Chrome's `mouseover`), and `mouse-feet` only hit-tests on pointer events.
- **002.03.20:** rules can't follow a sound or reward ending, actions can't be named, grouped or run one after another, and games line things up by matching `delayMs` to effect lengths by hand.

A spawn is naturally a named action that ends as its copy arrives, with the copy as `event`. Both prompts also need a way for a rule to name "the element that fired me". One plan therefore builds the shared parts once. Every game, and every doc and tutorial, moves to the new actions, so they stay consistent.

This clears four entries in `docs/outstanding-issues.md`:

- No `spawn` or `despawn` actions
- A still mouse pointer misses later obstacles
- Rules can't follow an effect ending
- A delayed effect finds its player by number

### Decisions taken

| Decision         | Choice                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Trigger naming   | Today's `…End` family is kept, so no existing data changes. New triggers: `{ "actionStart": "<name>" }` and `{ "actionEnd": "<name>" }` (the latter with an optional `target` filter on the element the action ended with, like `effectEnd`'s; built: `actionStart` has no `target`, as it starts before any element is known), and `{ "raised": "<name>" }`. Any action can have `name`. New action: `{ "raise": "<name>" }`. There is no `spawned` trigger: a named spawn's `actionEnd` carries the copy.                                                                                                                                                                                |
| Who hears        | Every shown scene hears `actionStart`, `actionEnd` and `raised`. Their `event` is the one the action ran with (id, player, playerId), except that a spawn's end carries the copy's id. Events carry no data of their own.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `"event"` target | A target keyword meaning "the element that fired this rule". It is resolved when the action is queued, to `[id="<event.id>"]`, and works for `effect`, `stop` and `despawn`. An empty `event.id` logs an error naming the action, and the action ends at once. Using it on a trigger with no element (`start`, `every`, `after`, `when`) is a load error. (Built: `raised`, `actionStart` and `actionEnd` carry the raiser's or starter's `event`, which may have an element, so they are allowed.)                                                                                                                                                                                        |
| Groups           | `{ "series": [ … ] }` and `{ "parallel": [ … ] }` are actions too, so they nest and can have `name` and `delayMs`. A plain `do` list is parallel, as now. A `delayMs` waits from when its action would start, and in a series the next action starts when this one has ended.                                                                                                                                                                                                                                                                                                                                                                                                              |
| Ends             | Each action ends as follows: `set`, `answer`, `completeChallenge`, `resetChallenge`, `enterStage`, `resetState`, `finishReset` and `raise` at once; a sound on `ended` (or on error); a reward on `onDone` (at once under reduced motion); an effect when all its elements have ended (reduced motion jumps to the end and still reports it); an indefinite effect when it is stopped; a spawn when its copy is in the DOM; a despawn at once.                                                                                                                                                                                                                                             |
| Broken action    | It is logged and counts as ending at once, so a series carries on.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Ending early     | A group whose scene closes or resets is dropped without firing ends, as delayed actions are now.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Engine purity    | The running groups live in `session.runningActions`. Queued sounds, effects, spawns and delayed actions carry an `actionId`, and hooks report an end with `setGameState(s => endAction(env, s, id))`. Only groups and named actions are tracked: a plain unnamed action at the top of `do` needs no record. Named start and end, and `raise`, fire listeners in the same pure update, with a depth guard `MAX_EVENT_CHAIN = 10` that logs and stops, like `MAX_WHEN_CHAIN`.                                                                                                                                                                                                                |
| Player identity  | `RuleEvent` gains `playerId` (the registry's stable id), set by `onPlayerInteraction`. A `"triggering"` player effect finds the player by `playerId` when it is present, and by number otherwise.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Copies           | Each copy gets an automatic `id` (`<template id or "spawn">-<n>`) unless its markup sets one, plus `data-spawned`. `keepPlacement()` gains a `beforeNodeRemoved` that keeps `[data-spawned]`, so copies survive re-renders. Idiomorph 0.8 never soft-matches an IDed node against a different id, and it morphs `<template>` content, so Handlebars in a template (`{{#if state.high}}`) follows a `set` earlier in the same rule. Copies live in `.templateBody`, which is keyed by `scope#run`, so a reset or close drops them for free, and they are never saved. `MAX_SPAWNED = 100` per scene: past that, one `console.error` per run and the spawn is skipped (it counts as ending). |
| Still pointer    | `GameSceneTemplateComponent` hit-tests `lastPointer()` on each animation frame while the scene has `mouse-enter`/`mouse-exit` rules and the pointer is over the page. One `hoveredRef` per body is the single source of truth for browser `mouseover`/`mouseout` and for frame ticks, so neither double-fires, and React state is never set. `useMouseFeet` runs `feet.restand()` each frame on the same conditions. This replaces the one-off hit-test on a new body and the `SCENE_RENDERED_EVENT` listener.                                                                                                                                                                             |
| Validation       | A load-time warning for an `actionStart`/`actionEnd` naming no action in the game, or a `raised` naming nothing that raises it. `checkStartRule`'s self-reset loop error also looks inside groups. A runtime warning for a `spawn` matching no `<template>`, or an `into` matching nothing (`warnUnmatchedSelectors`). `despawn` isn't checked, as copies don't exist at start.                                                                                                                                                                                                                                                                                                            |

### Constraints and reuse

- Rules stay pure state transitions. DOM work stays in the hooks: `useGameEffects` (`effects/GameEffectsHook.ts`), `useRuleEffects` (`Game.tsx:139`) and `useDelayedActions` (`RuleWaitsHook.ts`).
- Reuse:
  - `useQueueDrain` (`QueueDrainHook.ts`) and `queueVisualEffect`, `delayAction` and `applyRule` (`logic/GameRuleUtils.ts`);
  - `startOnElements`, `endPick` and `resolveTargets` (`effects/`), `sceneRoots` and `matchTarget` (`logic/TemplateUtils.ts`);
  - `checkSelector` (`logic/GameEffectCompile.ts:43`), `triggerInteractions`, and `lastPointer` (`util/PointerPosition.ts`).
- `random` takes two arguments: `random(0, 1) < 0.5`.
- The schema is generated from `src/entities/data/scenes/GameSceneData.ts` by `generate-schemas.sh`, which `npm run validate` runs.
- AGENTS.md: no `any`, comments state intent, zero lint and type warnings, aislop findings fixed the same turn.

### Stage 1: A still pointer meets moving things (Opus)

**Brief:**

- `scene/GameSceneTemplateComponent.tsx`:
  - Add a `watchPointer?: boolean` prop.
  - Replace `useAnnounceNewBody`'s one-off `mouseOver` with `useRestingPointer(bodyRef, bodyKey, watchPointer, onSceneEvent)`. Its `hoveredRef` resets on a new `bodyKey`. On each frame it finds `hit` = the element under `lastPointer()` inside the body, or `null`. If `hit !== hoveredRef`, it emits `mouseOut(old, related: hit)` and then `mouseOver(hit, related: old)`.
  - The `onMouseOver`/`onMouseOut` handlers go through the same ref. An over whose target is already `hoveredRef` is dropped. An out is emitted only if its target is `hoveredRef`.
- `scene/GameSceneComponent.tsx`: `watchPointer` = whether any rule's `interact` includes `mouse-enter` or `mouse-exit`. Dialogs and scrolls are left alone (`ponytail:` note: add when one needs moving targets).
- `layout/MouseFeetHook.ts`: a rAF loop calling `feet.restand()` while enabled, not paused and `lastPointer()` is defined. Drop the `SCENE_RENDERED_EVENT` listener, then delete the event if nothing else uses it.

**Tests:**

  - `RunningAction { id, parent?, scope, run, event, name?, kind, pending, open }` in `session.runningActions`;

### Stage 4: `spawn` and `despawn` (Opus)

**Brief:**

- Types: `GameSpawnAction { spawn: string; into: string }` and `GameDespawnAction { despawn: string }`. Both are queued on `session.visualEffects` (widen `QueuedVisualEffect.effect`), so they play in order with effects and reuse `startOnElements`' wait for the run to reach the screen.
- New `effects/Spawns.ts`:
  - `spawn(scope, action, where)`: finds the template and `into` in `sceneRoots`, enforces `MAX_SPAWNED`, clones the content's first element child (warning if there are more), adds an id if it has none and `data-spawned`, appends it, and returns the copy;
  - `despawn(scope, selector)` removes only `[data-spawned]` matches.
- `GameEffectsHook`: after a spawn, `endAction` with the copy's id as the end's `event.id`. Effects on a disconnected element don't report `effectEnd`. Check `ItemEffects` for this, as despawning mid-move cancels its animation.
- `keepPlacement()` (`layout/FloorPlacement.ts:132`): `beforeNodeRemoved`.
- `warnUnmatchedSelectors` (`GameRulesHook.ts:46`): `spawn` and `into`.
- Compile: `checkSelector` on `spawn`, `into` and `despawn`.

**Tests:**

- New `tests/Spawns.test.ts`: the copy's id and marker; its own id is kept; a missing template or `into` warns; the cap errors once; despawn removes only copies.
- `tests/GameRulesHook.test.tsx`, a rendered scene:
  - a named spawn's `actionEnd` with a `target` filter starts an `item-move` on `"event"`;
  - an `interact` rule finds copies by class;
  - `despawn: "event"` on `effectEnd` removes the right copy;
  - a re-render keeps copies;
  - the template's Handlebars follows a `set` from the same rule;
  - a reset removes every copy.

**Gate:** `dev-qual/scripts/check.sh --fast` + `npx vitest run` + `npm run validate`.
