## Context

Games played with the camera need two things that rules can't give yet:

- a way to get the player ready before a display starts, such as "return to the start" before the lava floor appears;
- feedback when the player does something, such as a sound or an animation.

The prompt settles most of the design. This plan adds the decisions taken while planning, and stages the work.

### Findings from exploration

- **The rule engine** is `GameRuleUtils.ts`. It is pure:
  - `fireRules` and `runWhens` return a new `GameState`;
  - `applyShowResets` runs on every state change, inside `GameStateProvider`'s `setGameState`;
  - `compileGameRules` validates every display at load time (`allDisplays`, `actionSources`, `triggerSources`).
- **Which displays are live** comes from `getShownDisplays` (`RenderDataUtils.ts`). `GameRulesHook.ts` (start, timers, `when`, camera rules) and `fireRules` are both driven by it. Render data is built separately by `getOverviewRenderData`, `getStageDisplayRenderData` and `getChallengesRenderData`. `getDisplayKey` decides when the scene fades.
- **Saving progress** (`GameStateStorage.ts`) writes only `stages`, `current` and `displayStates`. On load, `parseDisplayStates` keeps only the scopes in `allDisplayScopes`. A new `GameState` field is therefore session-only unless it is added to the stored format.
- **Feedback** is `useGameFeedback` in `Game.tsx`. It uses partycles `useReward("reward-element", animation, config)`, whose animation is fixed when the hook is created, so one hook can't play different animations. It calls `reward()` even with reduced motion. **There is no volume setting:** `playAudio` (`AudioUtils.ts`) plays at full volume, and the music provider only fades.
- **Camera interactions:** the `PlayerMonitor` targets are keyed by rule and element. `reportCovered` counts each interaction's streak against `stableFrames`. `updateMonitors` (in `PlayerInteractionHook.ts`) drops the monitor of a player who has gone.
- **The bare camera interaction names** (`hand`, `foot`, `head`, `body`, `any`) appear in:
  - `GameDisplayData.ts`;
  - `PlayerMonitor.ts` (`PART_GROUPS`);
  - `public/game-repository.json`;
  - about 8 test files;
  - `docs/game-data.md` and `docs/camera-mode.md`.
- **The rules demo** has no sound resources. magic-trifle has `win-sound.mp3` and `bells.mp3`.
- **Held players** have no feet on the debug overlay: `feetPositionsOf` in `CharacterCanvas.tsx` leaves them out.

### Decisions taken

The prompt's table still applies. These were added while planning:

| Decision                     | Choice                                                                                                                                                                                                                                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Interaction ending           | `-exit` names for every camera coverage interaction: `hand-exit`, `foot-exit`, `head-exit`, `body-exit` and `any-exit`. Entry and exit names can then be mixed freely (eg. `["hand-exit", "mouse-exit"]`).                                                                                                                      |
| Entry names, for consistency | The bare names become `hand-enter`, `foot-enter`, `head-enter`, `body-enter` and `any-enter`, matching `mouse-enter` and `mouse-exit`, which stay as they are. `click`, `jump`, `jump-from` and `jump-onto` are events, not states, so they keep their names. An old bare name is a load-time error that names its replacement. |
| Volume                       | Rule sounds play at full volume, like the existing sound effects. "No volume setting" goes in `docs/outstanding-issues.md`.                                                                                                                                                                                                     |
| Revealing the parent         | Fades, like any display change: the display key includes the shown scope. Camera interactions pause during the fade, so a foot already on the start doesn't fire on the revealed display.                                                                                                                                       |
| Reduced motion               | Rule reward animations are skipped with `prefers-reduced-motion`, and so is the existing stage-complete reward (a fix). Sounds still play.                                                                                                                                                                                      |
| Sounds for the demo          | Generated (`chime`, `tick`, `pop`, `fanfare` `.wav`), not reused: `bells.mp3` has no recorded licence.                                                                                                                                                                                                                          |

### Design

- **Session state.** `GameState` gains `session: { finishedResets: DisplayScope[]; effects: QueuedEffect[]; nextEffectId: number }`. `createBlankGameState` and `loadGameState` start it empty, and it is never saved. A reload therefore shows reset displays again and drops queued effects.
- **Reset displays.**
  - A reset display's scope is `<parent scope>/reset`, and a nested one's is `<parent scope>/reset/reset`.
  - A new `resolveResets(display, scope, state)` in `RenderDataUtils.ts` walks down while there is a reset display whose scope isn't in `finishedResets`. It returns the display to show, its scope, and the camera settings (the parent's, with the reset display's own overrides).
  - `getShownDisplays` and the three render-data getters use it, so the parent's rules, timers and `start` stay off until it is revealed.
  - `ShownDisplay` gains `resetScope?`, so `finishReset` knows what to mark finished.
- **Showing a reset display.**
  - `applyShowResets` works on display slots (the parent scopes being shown).
  - A newly shown slot whose reset display is `every-show` has its reset scopes removed from `finishedResets`.
  - A newly shown reset scope always has its display state cleared.
  - Reset scopes aren't in `allDisplayScopes`, so their state is dropped on load anyway.
- **`resetChallenge`** (`GameStateUtils.ts`) also removes the challenge's reset scopes from `finishedResets`.
- **Effects.**
  - `sound` and `reward` actions add `{ id: nextEffectId, …, delayMs }` to `session.effects`.
  - In `Game.tsx`, `useRuleEffects` plays each new id after its `delayMs`, then drains it with `setGameState(prev => …)`.
  - Because the engine is pure, a React updater that runs twice produces the same ids, and the hook remembers the highest id it has played, so nothing plays twice.
  - Effects queued together start together.
  - A reward mounts a `<RewardBurst key={id} animation config />` that fires partycles once on mount and unmounts when it is done.
- **`holdMs` on interact.**
  - For camera interactions, `PlayerMonitor` records when each streak started, and fires once the streak has lasted `stableFrames` frames and `holdMs`.
  - For `mouse-enter`, `useGameRules` starts a timer per rule and element on mouse-over, and cancels it on mouse-out.
  - `holdMs` with `click`, an `-exit` interaction or a jump is a load-time error.
- **`forMs` on when.**
  - `whenRound` records the values of `forMs` rules but doesn't fire them.
  - `useGameRules` compares the edges. It starts a timer per rule on a rising edge, and cancels it on a falling edge or when the display is hidden.
  - When the timer fires, the rule fires through `fire`.
  - Like `when`, it needs a rising edge, so a condition already true when the display is shown is recorded, not counted.
- **`-exit` on the camera.**
  - An exit fires when an interaction that had fired stops holding for `stableFrames` frames.
  - It also fires for a player who is dropped as gone. It doesn't fire when the monitors are cleared because interactions are paused for a transition.

- Rename the names in `public/game-repository.json`, the tests (`grep -E '"(hand|foot|head|body|any)"'`), `docs/game-data.md` and `docs/camera-mode.md`. Then regenerate the schemas and TSDoc.

### Stage 2: Session state and reset displays (Opus)

- Add `session` to `GameState` and initialise it in `createBlankGameState` and `loadGameState`. Add `GameResetDisplay` and `resetDisplay?` to `GameDisplayBase`, as in the prompt.
- Add `resolveResets`, change `getShownDisplays`, the render-data getters and `getDisplayKey` to use it, and include the scope in the key.
- Extend `applyShowResets` (slots, `every-show`, and clearing reset state on show), and `resetChallenge`.
- Add the `finishReset` action. `allDisplays` recurses into reset displays (flagged `isReset`, and inheriting `isChallenge`), and `finishReset` elsewhere is a load-time error. `applyAction` adds the shown display's `resetScope` to `finishedResets`.
- Camera settings: the render data's `camera` merges the parent's settings with the reset display's overrides, and `resolveCameraMode` then uses it unchanged.
- **Tests:**
  - `RenderDataUtils.test.ts`: the reset display is shown in place, then the parent after finishing, and a nested reset display.
  - `GameRuleUtils.test.ts`: `finishReset` reveals the parent; `finishReset` outside a reset display is rejected; `every-show` shows again on the next showing, and `first-show` doesn't; `resetChallenge` shows it again; reset state is cleared on each showing.
  - `GameStateStorage.test.ts`: `session` is not saved, and a loaded game shows the reset display.
  - `GameRulesHook.test.tsx`: the parent's `start` and timers wait until it is revealed.
  - `Game.test.tsx`: revealing changes the display key.
- **Gate:** `check.sh --fast`, the unit tests, the schemas regenerated, and the rules browser suite.

### Stage 3: `-exit` camera interactions (Opus)

- Add the `<part>-exit` names. `PlayerMonitor` keeps the interactions that fired and are holding. One that stops holding for `stableFrames` frames fires its `-exit`, if the target accepts it.
- `updateMonitors` gives a monitor whose player has gone a `release()` call, which fires its exits. Clearing the monitors when interactions are paused doesn't fire exits.
- **Tests:** `PlayerMonitor.test.ts`:
  - an exit after an entry;
  - no exit without an entry (including one already held when the monitor was armed);
  - a one-frame dropout doesn't exit when `stableFrames` is 2;
  - `release()` exits.

  `GameLayersLayout.test.tsx`: a player who has gone exits, and a transition doesn't.

- **Gate:** `check.sh --fast` and the unit tests.

### Stage 4: `holdMs` on interact (Opus)

- `holdMs` is on `GameInteractTrigger`, as `CameraRuleTarget.holdMs` and then `MonitorTarget.holdMs`. In `PlayerMonitor`, entry interactions keep `since`, and fire once both the stable frames and the hold are met.
- Mouse: in `onDisplayEvent`, a `mouse-enter` match on a rule with `holdMs` starts a timer keyed by rule and element, a `mouseOut` from that element cancels it, and hiding the display cancels them all. The timer fires the rule through `fire`.
- Load-time error: `holdMs` with only click, exit or jump interactions, or a negative `holdMs`.
- **Tests:** `PlayerMonitor.test.ts`: fires after the hold and not before, and a streak broken before the hold restarts it. `GameRulesHook.test.tsx` (fake timers): fires after a mouse hold, cancelled when the mouse leaves early. `GameRuleUtils.test.ts`: the load-time errors.
- **Gate:** `check.sh --fast`, the unit tests, and the rules browser suite.

### Stage 5: `forMs` on when (Opus)

- `whenRound` records the values of `forMs` rules but doesn't fire them. `runWhens` returns the edges as it does now. `useWhenRules` compares the previous and new edges for `forMs` rules: it starts a `setTimeout(forMs)` on a rising edge, and clears it on a falling edge or when the display is hidden. When the timer fires, it calls `fire(scope, pick that rule)`.
- Load-time error: a negative `forMs`.
- **Tests:** `GameRulesHook.test.tsx` (fake timers):
  - fires after `forMs` while still true;
  - doesn't fire if it turns false first;
  - restarts after a false-to-true change;
  - cancelled when the display is hidden;
  - a condition already true when the display is shown doesn't count.
- **Gate:** `check.sh --fast` and the unit tests.

### Stage 6: Effects queue: `sound` and `reward` (Opus)

- Add the `GameSoundAction` (`sound`, `delayMs?`) and `GameRewardAction` (`reward: { animation, particleCount? }`, `delayMs?`) actions, and the `QueuedEffect` type. `applyAction` appends the effect.
- Load-time error: a `sound` naming a resource the game doesn't have, or a negative `delayMs`.
- In `Game.tsx`, `useRuleEffects` plays new ids:
  - a sound through `playAudio(resources[name])`;
  - a reward through `RewardBurst` (`src/components/core/sfx/RewardBurst.tsx`), skipped with `prefers-reduced-motion`.

  It then drains the played ids. `useGameFeedback`'s stage reward also skips the animation with reduced motion.

- **Tests:**

  - `Game.test.tsx` (mock `playAudio` and partycles):

    - two effects from one rule both start;
    - `delayMs` is honoured;
    - reduced motion skips the animation but plays the sound;
    - played effects are drained;
    - the stage reward respects reduced motion.
- **Gate:** `check.sh --fast` and the unit tests.

### Stage 8: Rules demo: reset displays, effects and the bulb (Opus decides, Sonnet builds)

- **Balloons:** a "Get ready… 3, 2, 1" reset display (`after` 3000, with `every` counting down), and a sound when a balloon pops.
