## Context

Today only overview displays can react to input, and only by entering a stage (`clickIdToStageId`). Templates have no state, and every re-render replaces their DOM, which kills CSS transitions. This work makes rules (`on` / `if` / `do`) and state a capability of every display. Behaviour is described as data and evaluated by a sandboxed expression engine, and templates stay logic-less and sanitised. The 003 custom-elements work will reuse the state and the game actions built here.

### Findings from exploration

- `Game.tsx` builds the layers. Clicks go through `GameLayerWrapper` → `useLayerClickHandler` (which reads `event.target.id`) → `getNewGameStateForClick`. Only foreground layers have the handler. A click on the title screen moves on only when it lands on an element that has an `id`.
- `GameChallengeGrid`'s cells use `.childClicksOnly`, so each display's template container (100% × 100%) accepts pointer events and blocks every layer beneath it.
- `usePlayerInteractions` (`PlayerInteractionHook.ts`) looks up `clickIdToStageId` ids with `document.getElementById` on every frame. `PlayerMonitor` keys its memory `${elementId}:${interaction}` and is pure (no DOM).
- `HeadsUpDisplay` calls `setGameState` directly (return to title, close challenge), so "display shown" handling can't sit only in `Game`.
- No challenge reset exists today. The only reset is `clearGameState` from the landing page.
- `GameStateStorage` validates a versioned record field by field. An optional new field can be added without a version bump, so saved progress survives the upgrade.
- jsdom has no layout, no `elementFromPoint` and no CSS animations. Hit-testing and animation behaviour need Playwright, or mocks in unit tests.

### Decisions taken

| Decision                           | Choice                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Expression library                 | **filtrex 3.1.0** (MIT, no dependencies). It parses to an AST and emits JS through `new Function`. Handlebars already does the same, so it adds no new CSP requirement. Its default property lookup is own-property only. Runtime errors are _returned_ rather than thrown. `a.b` means `data['a.b']`, so we supply a `customProp` that walks dotted paths through own properties only. `true` and `false` are supplied as `constants`. Syntax: `if x then y else z`, `and` / `or` / `not`, `==`, `"double-quoted strings"`. |
| Where display state lives          | In `GameState.displayStates`, keyed by display scope. Saved in the existing progress record as an optional field. Actions stay pure functions on `GameState`.                                                                                                                                                                                                                                                                                                                                                                |
| `when` already true when shown     | Recorded, not fired (matching the camera's "already held" rule). Use `start` with `if` for "on show, if X".                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `resetStateOnShow`                 | Applied inside `GameStateProvider`'s `setGameState`, in the same update that shows the display, so no stale frame renders. This covers every caller, including the HUD.                                                                                                                                                                                                                                                                                                                                                      |
| Event routing                      | Each display's template container handles its own `click`, key activation, `animationend` and `transitionend`, bound to its scope. The layer wrappers' click delegation is removed. Because the browser delivers each event to the topmost element, a background display receives clicks wherever nothing covers it. This achieves the prompt's "every layer has the handler" with less code.                                                                                                                                |
| Camera covering                    | One `elementFromPoint` per (player, body part, element) that already passes the coverage threshold, sampled at the centre of the part's region clipped to the element. The cost is a handful of calls per frame. `includeCovered` skips the test.                                                                                                                                                                                                                                                                            |
| `answer` action                    | Same path as a typed answer: `validateAnswer`, then `completeChallenge`. Feedback (reward, stage-complete sound) follows automatically from `useGameFeedback`. A wrong answer does nothing; templates can show state instead.                                                                                                                                                                                                                                                                                                |
| `resetChallenge`                   | New pure `resetChallenge` in `GameStateUtils`: `succeeded = false`, stage completion recomputed, availability unchanged, and every `displayStates` entry for that challenge removed.                                                                                                                                                                                                                                                                                                                                         |
| Rule actions that need a challenge | `completeChallenge`, `answer` and `resetChallenge` are rejected at load outside challenge displays.                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Selectors matching nothing         | `console.warn` once per rule each time the display is shown, after its first render. Invalid selector syntax is a load error (checked when `document` exists).                                                                                                                                                                                                                                                                                                                                                               |

### Stage 4: Rule engine (pure) (Opus)

**Brief:** in `GameRuleUtils.ts`:

- `applyRule(state, display, rule, event?) → GameState` checks `if` and then applies `do` in order:
  - `set` evaluates every value against the state before the action;
  - `resetState`;
  - `completeChallenge` (a no-op if already succeeded);
  - `answer` (`String(value)` → `validateAnswer` → `completeChallenge`);
  - `resetChallenge`;
  - `enterStage` (export `enterStage` from `GameClickUtils.ts`; locked or completed means unchanged).
- `fireTrigger(state, rules, match: (trigger) => event | undefined) → GameState` runs every matching rule of the shown displays, in display then rule order.
- `evaluateWhens(state, rules, edges: ReadonlyMap<string, boolean>) → { state, edges, fired }`: the key is `${scope}#${ruleIndex}`. A missing key is recorded and not fired. A rising edge fires. Keys for displays that are no longer shown are dropped. All `when`s are evaluated against the same state, then the fired rules are applied in order.
- Export `MAX_WHEN_CHAIN = 10`.

**Tests:** each action, including `set` reading pre-action state (swap two keys) and `if` false skipping; each trigger kind through `fireTrigger`; `when` baseline-not-fire, rising edge fires, stays-true doesn't refire, false-then-true refires; a dropped display re-baselines; `enterStage` on a locked stage is unchanged.
