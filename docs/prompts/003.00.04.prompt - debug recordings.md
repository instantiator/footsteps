Prepare a plan to implement recording to support testing and debugging.

In debug mode, add a start/stop recording button in the HUD that allows the user to capture short videos that can then be downloaded for examination and used for testing. After a recording, the last video is held in memory and a download button allows the user to download the video. Starting a new recording or downloading a video discards the current video.

Capture it all as video, so frames can be extracted later when testing against it. Capture metadata, too, and download that alongside the video, ie.

- download is a zip of video + metadata, including:
  - the id/timestamp of frames that were used and processed by the game
  - the data for those frames (ie. the segmentation and mask for those frames)
  - player states for those frames (ie. the player positions (hands, feet, head))

The plan should branch from the `003.00.03-behaviour-and-scale` branch, so the PRs can be stacked.

# Provenance

The record option was first proposed in [993.00.00](<993.00.00.prompt - jump detection review.md>), the jump detection review, and was moved here so it can be built ahead of that review. Until now, the vision fixtures have been still photos only: they can't show flicker, segmentation lag or quick movement.

# What recordings are for

- **Debugging:** a tester captures a moment that went wrong (eg. a player turning into a spectator) and the developer examines what the game saw and decided, frame by frame.
- **Replay tests:** the replay bench in 993 extends [`vision-bench.spec.ts`](../../tests/browser/vision-bench.spec.ts) to replay recordings through candidate models and settings, and measures jump precision and recall, latency and achieved fps.
- **Tuning with real footage:** 993's further BodyPix tuning repeats the D5 sweep from [003.00.03](<003.00.03.plan - behaviour and scale fixes.partial.md>) against recordings, measuring flicker, lost limbs and frame rate.
- **Labelled recordings:** 993's calibration game will label each moment ("stand", "walk", "jump", "duck"), so recordings should leave room for labels in their metadata, even though the game is out of scope here.

# Questions to answer in planning

- **Format and size:** the video codec and container the browser can record, and how large the video and metadata become for a short recording. Masks may need compressing.
- **Matching frames to video:** how each processed frame's id or timestamp maps to a frame of the video, so tests can extract the exact frame the game used.
- **Consent:** how to ask testers before recording them, and where recordings are kept. Recordings stay in memory until downloaded, and are never uploaded.
- **Recording from one or more testers:** whether recordings from several people or sessions need anything in common (eg. the camera configuration and calibration in the metadata).
