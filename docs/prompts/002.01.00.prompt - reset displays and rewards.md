# Reset displays and rewards

> **Draft.** This follows on from display rules and state (`002.00.00.prompt - templated elements and state.md`).
> Refine it before planning.

Please create a plan to add reset displays, and rewards that rules can give.

## Context

Displays can now keep state and run rules (`on` / `if` / `do`), triggered by clicks, the mouse, the camera,
animations, timers and changes in the game. See `docs/game-data.md#rules-and-state` and ADR 0006.

Two things are missing for games played with the camera:

- **A way to get ready.** A challenge starts as soon as it is shown. Players may be in the wrong place, or not
  expecting it. The lava stage, for example, should start with everyone standing on the start.
- **Feedback from rules.** The game rewards a completed stage (the `reward` animation and `sounds`), but a rule
  can't play a sound or an animation when a player does something, or needs to do something.

## Goal

### Reset displays

- Any display can have an optional **reset display**: another display, shown in its place first, that helps
  players reset for it. For example, a "Get ready!" message, or "Everyone stand on the start".
- A reset display completes, revealing its parent display, through **ordinary rules**. Examples:
  - when the players are in position;
  - when a certain time has passed;
  - when the players have been in position for a certain time.
- Reset displays shouldn't need special rules. Anything added to support them (eg. "held for a time") must be a
  generic trigger or action that any display can use.
- A reset display can have a reset display of its own. There may be no reason to, but nothing should prevent it.
- When a challenge is reset (the `resetChallenge` action), a challenge display that has a reset display shows it
  again, so the players reset alongside the challenge.

### Rewards

- A rule can reward the players, or prompt them: play a sound, or show an animation such as the fireworks shower.
- This should reuse what the game already has: named `resources` for sounds, `playAudio`
  (`src/components/core/sfx/AudioUtils.ts`), and the partycles `useReward` used by `useGameFeedback` in
  `src/components/core/Game.tsx`, with the same `RewardAnimation` names as the game-level `reward`.

## Possible approach

These are starting points, not decisions. The plan should weigh options with the user.

### Data model

```ts
/** Fields common to every display. */
export interface GameDisplayBase {
  purpose: GameDisplayPurpose;
  component: GameDisplayComponentData;
  camera?: GameDisplayCameraData;
  /** Shown in this display's place first, until one of its rules completes it. */
  resetDisplay?: GameResetDisplay;
}

/** A display that helps players get ready for its parent display. */
export interface GameResetDisplay {
  component: GameDisplayComponentData;
  camera?: GameDisplayCameraData;
  resetDisplay?: GameResetDisplay;
}
```

### New triggers and actions

All of these are generic, usable by any display:

- **Held interactions:** an `interact` trigger that fires once the interaction has been held for some time, eg.
  `{ "interact": "foot", "target": "#start", "holdMs": 2000 }`. `PlayerMonitor` already counts stable frames, so it
  could time how long an interaction holds.
- **Interactions ending:** the camera equivalent of `mouse-exit` (eg. a foot leaving an element), so rules can track
  "in position" in state, and `when` rules can combine them (eg. every player in position).
- **Finishing a display:** an action that ends the display that runs it. For a reset display, this reveals the
  parent. Decide what it means elsewhere: nothing, or perhaps ending a challenge's title display early.
- **Rewards:** eg. `{ "reward": { "animation": "fireworks", "particleCount": 100 } }` and
  `{ "sound": "<resource name>" }`.

For example, the lava stage's challenge display could have this reset display:

```json
"resetDisplay": {
  "component": {
    "type": "template",
    "data": {},
    "rules": [
      { "on": { "interact": ["foot", "mouse-enter"], "target": "#start", "holdMs": 1500 },
        "do": [{ "sound": "ready" }, { "finishDisplay": true }] }
    ],
    "foregroundTemplate": { "sourceType": "embedded", "content": "<div id=\"start\" class=\"lava-start\">Stand here</div>" }
  }
}
```

### Things the engine must handle

- **Side effects.** The rule engine is pure: `fireRules` and `runWhens` return a new `GameState`. Sounds and
  animations are side effects, so the engine needs a way to report them (eg. returning effects alongside the
  state, or a queue in state that the game drains). They must play once, even when React runs an updater twice.
- **Which display is showing.** The game needs to know whether a display's reset display is still showing. This
  is probably state on the parent's scope (eg. `displayStates`, or a new field). `getShownDisplays` should return
  the reset display in its parent's place, so the parent's rules, timers and `start` don't run until it is revealed.
- **State scope.** A reset display needs its own state scope (eg. `<parent scope>/reset`), reset each time it shows.
- **Camera settings.** A reset display might inherit its parent's camera settings, or set its own.

## Examples

Extend `rules-demo`:

- **Balloons:** a "Get ready… 3, 2, 1" reset display that finishes after 3 seconds (`after`), with a sound.
- **Lava:** a reset display asking everyone to stand on the start, which finishes once a foot (or the mouse) has
  been there for 1.5 seconds. Stepping on lava resets the challenge (`resetChallenge`), so the reset display shows
  again.
- **Rewards:** a sound when a balloon pops, and the fireworks when the door is reached.

## Out of scope

- Conditions over all players (eg. "every player is on the start"), which are still recorded in
  `docs/outstanding-issues.md`. Note if this work makes them easier, and leave a design in the outstanding issue.
- Shared state between displays.

## Open questions for the plan

- Does a reset display show every time its parent is shown, or only the first time and after a challenge reset?
  Should that be a setting (eg. `resetDisplayOn: "show" | "challengeReset"`)?
- Is "which reset display is showing" saved with progress, so a reload shows it again?
- What does the finishing action do on a display that isn't a reset display?
- Do rewards and sounds respect `prefers-reduced-motion`, and the music volume, as the existing feedback does?
- How do held interactions interact with `visionStableFrames`, and with players moving in and out of view?

## Constraints and conventions

- Follow `AGENTS.md`, as in the 002.00 plan: no type escapes, zero warnings, comments that state intent.
- Keep the engine pure. Keep DOMPurify and `knownHelpersOnly` as they are.
- Regenerate schemas and TSDoc after changing `src/entities/`.
- Update `docs/game-data.md`, `docs/camera-mode.md`, `docs/testing/manual-testing.md` and the `rules-demo` game.
- Tests cover each new trigger and action, reset displays (shown first, revealed by a rule, nested, shown again on
  challenge reset), effects playing once, and the examples, with browser tests by mouse.

## Done when

- A display with a reset display shows it first, and reveals the display when one of its rules finishes it.
- Resetting a challenge shows its reset display again.
- Rules can play sounds and reward animations, once each time they fire.
- The balloons and lava examples get players ready, and reward them, by mouse and by camera.
- `dev-qual/scripts/check.sh --comprehensive` passes.
