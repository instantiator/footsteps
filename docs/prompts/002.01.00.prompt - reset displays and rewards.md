# Reset displays and rewards

> This follows on from display rules and state (`002.00.00.prompt - templated elements and state.md`) and the camera
> feedback (`002.00.02.feedback - camera feedback.md`). Its decisions were refined with the user on 2026-10-27.

Please create a plan to add reset displays, and rewards and other effects that rules can trigger.

## Context

Displays can now keep state and run rules (`on` / `if` / `do`). The triggers are clicks, the mouse, the camera,
animations, timers and changes in the game. See `docs/game-data.md#rules-and-state` and ADR 0006.

Two things are missing for games played with the camera:

- **A way to get ready.** A challenge starts as soon as it is shown, when players may be in the wrong place or not
  expecting it. The lava stage, for example, should start with the player standing on the start.
- **Feedback from rules.** The game rewards a completed stage (the `reward` animation and `sounds`), but a rule
  can't play a sound or an animation when a player does something, or needs to do something.

Steadier tracking was in an earlier draft of this prompt. The camera feedback work did it: a player the model loses
for a moment is held and faded ([ADR 0007](../ADRs/0007-camera-flicker.md)), and their monitor and any jump in
progress wait for them. It is out of scope here, apart from the debug marker below.

## Decisions taken

| Question                                        | Decision                                                                                                                                                                                                                                                                            |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| When does a reset display show?                 | `showOn: "first-show"` (the default) shows it before its parent is shown for the first time. `"every-show"` shows it before every showing. It always shows again when the parent's challenge is reset (`resetChallenge`).                                                           |
| Is "reset display showing" saved with progress? | No. "First time" counts from when the game is loaded, so a resumed game shows the reset display again, and the player starts the display from the beginning.                                                                                                                        |
| Which displays can have one?                    | Any display, including a reset display (nesting is allowed, though rarely needed).                                                                                                                                                                                                  |
| What does the finishing action mean elsewhere?  | `finishReset` only applies to reset displays, and is a load-time error elsewhere. A challenge display is finished by `completeChallenge`. Overview and stage displays move on with `enterStage` and the like.                                                                       |
| Camera settings and state                       | A reset display inherits its parent's camera settings, and may override them. Its state is session-only, in its own scope (`<parent scope>/reset`), and is cleared each time it shows.                                                                                              |
| How do rules trigger sounds and animations?     | Through an **effects queue** in session state (not saved with progress). Each effect has an id, and the game plays each id exactly once, even when React runs a state update twice. The rule engine stays pure.                                                                     |
| Can effects run at the same time?               | Yes. Effects are **non-blocking**: all of a rule's effects start together (sounds overlap, animations play together), and no rule waits for an effect to finish. An optional `delayMs` on an effect staggers it. To act after an effect ends, a rule uses an `after` timer for now. |
| Action names                                    | `finishReset: true`, `sound: "<resource name>"`, and `reward: { "animation": …, … }` with the same `RewardAnimation` names as the game-level `reward`.                                                                                                                              |
| New triggers                                    | `forMs` on `when` (true for a while), `holdMs` on `interact` (held for a while), and **interaction ending**, for every camera interaction (eg. a hand leaving the water). All are generic: any display can use them.                                                                |
| Do held times survive interruptions?            | No. `forMs` and `holdMs` restart after a reload, a display change, or a player being lost for longer than they are held (`cameraHoldMs` + `cameraFadeMs`).                                                                                                                          |
| Do rewards respect reduced motion and volume?   | Yes. With `prefers-reduced-motion`, no particle animation is shown, but its sound still plays. Sounds follow the game's music volume, as the existing feedback does.                                                                                                                |
| Held players on the debug overlay               | A held player's feet are shown with a hollow, faded marker, so testers can tell them from players the model can see.                                                                                                                                                                |

## Goal

### Reset displays

- Any display can have an optional **reset display**: another display, shown in its place first, that helps the
  player get ready for it. For example, a "Get ready!" message, or "Return to the start".
- A reset display finishes, revealing its parent display, through **ordinary rules**. For example:
  - when the player is in position;
  - when a certain time has passed;
  - when the player has been in position for a certain time.
- Reset displays shouldn't need special rules. Anything added to support them (eg. "true for a time") must be a
  generic trigger that any display can use. The one exception is `finishReset`.
- While a reset display shows, its parent's rules, timers and `start` don't run. `getShownDisplays` returns the reset
  display in its parent's place.

### Effects

- A rule can reward the player, or prompt them: play a sound, or show an animation such as the fireworks shower.
- Reuse what the game already has:
  - the named `resources` for sounds;
  - `playAudio` (`src/components/core/sfx/AudioUtils.ts`);
  - the partycles `useReward` used by `useGameFeedback` in `src/components/core/Game.tsx`.
- Effects are non-blocking and can run in parallel, as decided above.

### Triggers

- `when` with `forMs`: fires once its expression has stayed true for that long, eg.
  `{ "when": "state.ready", "forMs": 3000 }`.
- `interact` with `holdMs`: fires once the interaction has held for that long, eg.
  `{ "interact": "foot", "target": "#start", "holdMs": 2000 }`. `PlayerMonitor` already counts stable frames, so it
  can time how long an interaction holds.
- **Interaction ending**: fires when a camera interaction stops holding, eg. a hand leaving the water. The plan should
  propose its shape. One option is an `ends: true` flag on `interact`. Another is `-exit` names to match
  `mouse-exit`, eg. `hand-exit`. Jumps have no ending.

### Debug overlay

- Show held players' feet with a hollow, faded marker. Today `feetPositionsOf` (`CharacterCanvas.tsx`) leaves held
  players out.

## Possible approach

These are starting points, not decisions. The plan should weigh options with the user.

### Data model

```ts
/** Fields common to every display. */
export interface GameDisplayBase {
  purpose: GameDisplayPurpose;
  component: GameDisplayComponentData;
  camera?: GameDisplayCameraData;
  /** Shown in this display's place first, until one of its rules finishes it. */
  resetDisplay?: GameResetDisplay;
}

/** A display that helps the player get ready for its parent display. */
export interface GameResetDisplay {
  component: GameDisplayComponentData;
  /** Overrides the parent's camera settings; inherited when omitted. */
  camera?: GameDisplayCameraData;
  /** When it runs: before the parent's first showing (the default), or before every showing. */
  showOn?: "first-show" | "every-show";
  resetDisplay?: GameResetDisplay;
}
```

### Effects

```json
{ "sound": "ready", "delayMs": 0 }
{ "reward": { "animation": "fireworks", "particleCount": 100 }, "delayMs": 500 }
```

The engine adds each effect, with a fresh id, to a queue in session state. The game plays new ids and drops them
from the queue. Effects queued by one rule start together, after their `delayMs`.

## Examples

Extend `rules-demo`.

### Lava: return to the start

The lava stage's challenge display gets a reset display that brings the player back to the start:

1. It shows a dark background with the starting point clearly marked out in a bright colour, and the label
   **"Return to the start"**.
2. When the player reaches the start (a foot, or `mouse-enter` with the mouse), they are rewarded with a sound and a
   short animation, and the label changes to **"Get ready!"**.
3. Three seconds later, the reset display finishes, and the lava floor is revealed.

Stepping on lava resets the challenge (`resetChallenge`), so the reset display shows again, and the player
returns to the start. A sketch of its rules:

```json
"resetDisplay": {
  "component": {
    "type": "template",
    "data": {},
    "initialState": { "ready": false },
    "rules": [
      {
        "on": { "interact": ["foot", "mouse-enter"], "target": "#reset-start" },
        "if": "not state.ready",
        "do": [{ "set": { "ready": "true" } }, { "sound": "ready" }, { "reward": { "animation": "sparkles" } }]
      },
      { "on": { "when": "state.ready", "forMs": 3000 }, "do": [{ "finishReset": true }] }
    ],
    "foregroundTemplate": { "sourceType": "relative", "templateSource": "games/rules-demo/lava-reset.hbs" }
  }
}
```

```handlebars
<div class="demo-screen demo-reset">
  <div id="reset-start" class="lava-start lava-start-bright">Start</div>
  <p class="demo-score">{{#if state.ready}}Get ready!{{else}}Return to the start{{/if}}</p>
</div>
```

The start must sit where the lava stage's own start is, so the player is in place when the floor appears.

### Balloons: get ready

A "Get ready… 3, 2, 1" reset display that finishes after 3 seconds (`after`), with a sound.

### Effects

- A sound when a balloon pops.
- The fireworks, with a sound at the same time, when the lava door is reached.

### Interaction ending

A small demo where a rule fires when a hand leaves an element, eg. the switch display lights a bulb while a hand is
over it and turns it off when the hand leaves (by mouse, `mouse-enter` / `mouse-exit`).

## Out of scope

- Steadier tracking beyond the camera feedback work (projecting a lost player's motion was considered and dropped,
  as a guessed position could fire interactions the player never made).
- Conditions over all players (eg. "every player is on the start"), which are still recorded in
  `docs/outstanding-issues.md`. Note if this work makes them easier, and leave a design in the outstanding issue.
- Shared state between displays.
- A trigger for an effect finishing. Record it in `docs/outstanding-issues.md`, to act on when a game needs to
  sequence rules on an effect's end.

## Constraints and conventions

- Follow `AGENTS.md`, as in the 002.00 plan: no type escapes, zero warnings, comments that state intent.
- Keep the engine pure. Keep DOMPurify and `knownHelpersOnly` as they are.
- Regenerate schemas and TSDoc after changing `src/entities/`.
- Update `docs/game-data.md`, `docs/camera-mode.md`, `docs/testing/manual-testing.md` and the `rules-demo` game.
- Tests cover:
  - each new trigger and action;
  - reset displays: shown first, revealed by a rule, nested, shown again on challenge reset and after a reload, and
    `every-show`;
  - effects: played once, in parallel, after `delayMs`, and respecting reduced motion and volume;
  - the held-player debug marker;
  - the examples, with browser tests by mouse.

## Done when

- A display with a reset display shows it first (by default, before its first showing since the game loaded), and
  reveals the display when one of its rules finishes it.
- Resetting a challenge shows its reset display again, and so does resuming a saved game.
- Rules can play sounds and reward animations, in parallel and once each time they fire, respecting reduced motion
  and volume.
- Rules can fire on an interaction holding for a time, an expression staying true for a time, and an interaction
  ending.
- The debug overlay marks held players.
- The lava stage asks the player to return to the start, rewards them, says "Get ready!", and reveals the floor 3
  seconds later, by mouse and by camera. The balloons count down first.
- `dev-qual/scripts/check.sh --comprehensive` passes.
