# Reset displays and rewards

> **Draft.** This follows on from display rules and state (`002.00.00.prompt - templated elements and state.md`).
> Refine it before planning.

Please create a plan to add reset displays, rewards that rules can give, and steadier player tracking.

## Context

Displays can now keep state and run rules (`on` / `if` / `do`), triggered by clicks, the mouse, the camera,
animations, timers and changes in the game. See `docs/game-data.md#rules-and-state` and ADR 0006.

Three things are missing for games played with the camera:

- **A way to get ready.** A challenge starts as soon as it is shown. Players may be in the wrong place, or not
  expecting it. The lava stage, for example, should start with the player standing on the start.
- **Feedback from rules.** The game rewards a completed stage (the `reward` animation and `sounds`), but a rule
  can't play a sound or an animation when a player does something, or needs to do something.
- **Steady positions.** When a player flickers out of view for a frame or two, their monitor is dropped, so an
  interaction in progress is lost and fires again when they reappear.

## Decisions taken

| Question                                            | Decision                                                                                                                                                                                           |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| When does a reset display show?                     | Configurable. By default, before its parent is shown for the first time. Always again when the parent's challenge is reset.                                                                        |
| Is "reset display showing" saved with progress?     | No. "First time" counts from when the game is loaded, so a resumed game shows the reset display again, and the player starts the display from the beginning.                                       |
| What does the finishing action mean elsewhere?      | It only applies to reset displays, and is a load-time error elsewhere. A challenge display is finished by `completeChallenge`; overview and stage displays move on with `enterStage` and the like. |
| Do rewards respect reduced motion and music volume? | Yes, all of them: animations follow `prefers-reduced-motion`, and sounds follow the game's music volume, as the existing feedback does.                                                            |
| What happens when a player flickers out of view?    | Their position is held for several seconds, and their motion projected for about a second, for every purpose, not only held-position triggers.                                                     |

## Goal

### Reset displays

- Any display can have an optional **reset display**: another display, shown in its place first, that helps the
  player reset for it. For example, a "Get ready!" message, or "Return to the start".
- By default it runs before its parent is shown for the first time (since the game was loaded). A setting can make
  it run every time the parent is shown instead.
- A reset display completes, revealing its parent display, through **ordinary rules**. Examples:
  - when the player is in position;
  - when a certain time has passed;
  - when the player has been in position for a certain time.
- Reset displays shouldn't need special rules. Anything added to support them (eg. "true for a time") must be a
  generic trigger that any display can use. The one exception is the action that finishes a reset display.
- A reset display can have a reset display of its own. There may be no reason to, but nothing should prevent it.
- When a challenge is reset (the `resetChallenge` action), a challenge display that has a reset display shows it
  again, so the player resets alongside the challenge.

### Rewards

- A rule can reward the player, or prompt them: play a sound, or show an animation such as the fireworks shower.
- This should reuse what the game already has: named `resources` for sounds, `playAudio`
  (`src/components/core/sfx/AudioUtils.ts`), and the partycles `useReward` used by `useGameFeedback` in
  `src/components/core/Game.tsx`, with the same `RewardAnimation` names as the game-level `reward`.
- Every reward respects `prefers-reduced-motion` (no particle animation, or a still alternative) and the game's
  music volume.

### Steadier tracking

- When a player is lost for a few frames, keep them: hold their last known position for several seconds, and
  project their motion forward for about a second, before treating them as gone.
- This applies to everything the camera drives: interactions (and their edge triggering), jumps, held positions,
  the feet positions, and the debug overlay. A player who flickers shouldn't fire an interaction again, or lose a
  held position.
- The hold and projection times should be app settings (`AppConfig`, with URL overrides, like `visionStableFrames`).
  `src/vision/Tracking.ts` already keeps stable player ids and smooths key points; `usePlayerInteractions` drops a
  player's `PlayerMonitor` the moment they are missing from a frame.

## Possible approach

These are starting points, not decisions. The plan should weigh options with the user.

### Data model

```ts
/** Fields common to every display. */
export interface GameDisplayBase {
  purpose: GameDisplayPurpose;
  component: GameDisplayComponentData;
  camera?: GameDisplayCameraData;
  /** Shown in this display's place first, until one of its rules finishes it. */
  resetDisplay?: GameResetDisplay;
}

/** A display that helps the player get ready for its parent display. */
export interface GameResetDisplay {
  component: GameDisplayComponentData;
  camera?: GameDisplayCameraData;
  /** When it runs: before the parent's first showing (the default), or before every showing. */
  showOn?: "first-show" | "every-show";
  resetDisplay?: GameResetDisplay;
}
```

### New triggers and actions

- **Held conditions (generic):** `when` with a duration fires once its expression has stayed true for that long,
  eg. `{ "when": "state.ready", "forMs": 3000 }`. It covers "in position for a while" too, when rules track
  position in state.
- **Held interactions (generic):** an `interact` trigger that fires once the interaction has held for some time,
  eg. `{ "interact": "foot", "target": "#start", "holdMs": 2000 }`. `PlayerMonitor` already counts stable frames,
  so it could time how long an interaction holds.
- **Interactions ending (generic):** the camera equivalent of `mouse-exit` (eg. a foot leaving an element), so
  rules can track "in position" in state.
- **Finishing a reset display:** eg. `{ "finishReset": true }`, which reveals the parent. Only valid on reset
  displays.
- **Rewards (generic):** eg. `{ "reward": { "animation": "fireworks", "particleCount": 100 } }` and
  `{ "sound": "<resource name>" }`.

### Things the engine must handle

- **Side effects.** The rule engine is pure: `fireRules` and `runWhens` return a new `GameState`. Sounds and
  animations are side effects, so the engine needs a way to report them (eg. returning effects alongside the
  state, or a queue in state that the game drains). They must play once, even when React runs an updater twice.
- **Which display is showing.** The game needs to know whether a display's reset display is still showing. This
  is session state, not saved progress (see the decisions above). `getShownDisplays` should return the reset
  display in its parent's place, so the parent's rules, timers and `start` don't run until it is revealed.
- **State scope.** A reset display needs its own state scope (eg. `<parent scope>/reset`), reset each time it shows.
- **Camera settings.** A reset display might inherit its parent's camera settings, or set its own.

## Examples

Extend `rules-demo`.

### Lava: return to the start

The lava stage's challenge display gets a reset display that brings the player back to the start:

1. It shows a dark background with the starting point clearly marked out in a bright colour, and the label
   **"Return to the start"**.
2. When the player reaches the start (a foot, or `mouse-enter` with the mouse), they are rewarded (a sound, and a
   short animation), and the label changes to **"Get ready!"**.
3. Three seconds later, the reset display finishes, and the lava floor is revealed.

Stepping on lava resets the challenge (`resetChallenge`), so the reset display shows again, and the player
returns to the start. A sketch of its rules:

```json
"resetDisplay": {
  "component": {
    "type": "template",
    "data": {},
    "initialState": { "ready": false },
    "rules": [
      {
        "on": { "interact": ["foot", "mouse-enter"], "target": "#reset-start" },
        "if": "not state.ready",
        "do": [{ "set": { "ready": "true" } }, { "sound": "ready" }, { "reward": { "animation": "sparkles" } }]
      },
      { "on": { "when": "state.ready", "forMs": 3000 }, "do": [{ "finishReset": true }] }
    ],
    "foregroundTemplate": { "sourceType": "relative", "templateSource": "games/rules-demo/lava-reset.hbs" }
  }
}
```

```handlebars
<div class="demo-screen demo-reset">
  <div id="reset-start" class="lava-start lava-start-bright">Start</div>
  <p class="demo-score">{{#if state.ready}}Get ready!{{else}}Return to the start{{/if}}</p>
</div>
```

The start must sit where the lava stage's own start is, so the player is in place when the floor appears.

### Balloons: get ready

A "Get ready… 3, 2, 1" reset display that finishes after 3 seconds (`after`), with a sound.

### Rewards

A sound when a balloon pops, and the fireworks when the lava door is reached.

## Out of scope

- Conditions over all players (eg. "every player is on the start"), which are still recorded in
  `docs/outstanding-issues.md`. Note if this work makes them easier, and leave a design in the outstanding issue.
- Shared state between displays.

## Open questions for the plan

- How does `forMs` behave across a reload or a display change: does the time restart?
- How should held and projected players appear in the debug overlay, so testers can tell them from seen ones?
- What are good defaults for the hold and projection times? Bench them on the photo set, and with a real camera.

## Constraints and conventions

- Follow `AGENTS.md`, as in the 002.00 plan: no type escapes, zero warnings, comments that state intent.
- Keep the engine pure. Keep DOMPurify and `knownHelpersOnly` as they are.
- Regenerate schemas and TSDoc after changing `src/entities/`.
- Update `docs/game-data.md`, `docs/camera-mode.md`, `docs/testing/manual-testing.md` and the `rules-demo` game.
- Tests cover each new trigger and action, reset displays (shown first, revealed by a rule, nested, shown again on
  challenge reset and after a reload, `every-show`), effects playing once and respecting reduced motion and
  volume, tracking through flicker, and the examples, with browser tests by mouse.

## Done when

- A display with a reset display shows it first, by default before its first showing since the game loaded, and
  reveals the display when one of its rules finishes it.
- Resetting a challenge shows its reset display again, and so does resuming a saved game.
- Rules can play sounds and reward animations, once each time they fire, respecting reduced motion and volume.
- A player who flickers out of view keeps their interactions and held positions.
- The lava stage asks the player to return to the start, rewards them, says "Get ready!", and reveals the floor 3
  seconds later, by mouse and by camera. The balloons count down first.
- `dev-qual/scripts/check.sh --comprehensive` passes.
