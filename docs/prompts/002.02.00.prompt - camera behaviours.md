## Feedback for `cameraFillGaps`

When set `true`, the `cameraFillGaps` setting seems to cause the outline of the player to be occasionally shown at unexpected locations on screen - either above and to the left of the player, or below and to the right of the player. This is unexpected, and causes an extra copy of the player's shape to be displayed (but as it is the wrong part of the image, it just shows background from the camera image in the shape of the player).

## Camera selection

We intend to operate the game with a camera behind the player, and the screen in front, offering a 3rd person perspective. (Camera will be positioned behind and a little above the player, looking down - so as to be able to capture their head and feet as they move around the playing space.)

To achieve this, we'll need to be able to select the camera based on those available to the browser.

At the landing page for the game, the user should be able to select and preview their choice of camera. Either make that choice available once they have granted camera access permission, or before (depending on how permissions are granted - ie. are they granted when a camera is selected, or do they need to be granted in order to see all cameras?)

A dropdown should list all cameras available to the system, with a mark indicating the currently selected choice.

Default to the system default device.

If the system default device changes, the selected camera should update, on the game landing page, but not during gameplay. To change the camera, the user should return to the landing page (for now).

### Requirement

Modify `GameDisplayCameraData`:

- rename `enabled` to `requirement` and change the type from `boolean` to `("enabled" | "required" | false)`

If any display in a game enables or requires the camera, the camera permission should be checked and shown (and the user should be able to grant it) on the game's landing page.

If any display in a game requires the camera, it should not be possible to start the game (either continue, or a new game) from the game landing page.

Similarly, if the camera is not used at all by any display in the game, it needn't appear on the game landing page.

If the camera is _required_ by any display in a game, and the camera permission is not granted, the user should be bounced from the game's `play` page back to its landing page to get that permission.

## Player depth tracking

Currently, the players are assumed to exist between the background and foreground layers.

Items in the foreground layer ought to have depths attributed to them (perhaps as a Z-index?)

_Provided player foot detection is reasonably stable,_ the height of a player's feet can be considered a good proxy for their distance, and so the user's 'cut out' should be rendered at a z-index that effectively shows them as behind or in front of the foreground items.

Is foot detection stable enough for this? If not, perhaps it can be implemented in tandem alternative body tracking that may help to improve this. (See below...)
