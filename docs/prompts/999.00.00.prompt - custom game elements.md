Please create a plan for custom game elements: pieces of a game's interface that carry their own logic and interactions, written in TypeScript and React, and delivered either with the game's data or alongside it.

This prompt records the exploration that led to the decisions below. The plan should implement those decisions and resolve the open questions at the end. It is not written yet.

## Where we are

A game is data. It is described by `GameData` (`src/entities/data/GameData.ts`), authored as JSON in a game repository (`public/game-repository.json`), and checked against a JSON schema that is generated from the TypeScript types.

A game's screens are built from **displays** (`src/entities/data/displays/GameDisplayData.ts`). Each display says when it shows (`purpose`) and how it renders (`component`). There are three kinds of component today:

| `type`     | What it renders                                                               |
| ---------- | ----------------------------------------------------------------------------- |
| `template` | Handlebars templates, one for the background layer and one for the foreground |
| `dialog`   | Paged text on an image the game supplies                                      |
| `scroll`   | A dialog on the app's own paper image                                         |

Templates are compiled with Handlebars, rendered to HTML, and sanitised with DOMPurify. Sanitising matters because a repository can be remote and its templates are not trusted. Templates can repeat and branch, but they cannot hold logic. A game cannot say "this keypad remembers the digits already typed" or "this puzzle shows a different message after the player has solved stage 2".

Resources (images, audio, stylesheets and template files) are named in the game data and resolved to URLs when the game loads. CSS is loaded through `stylesheets`, which already accepts `https:` or same-site URLs.

Every page is prerendered to static HTML at build time, because the site is served from GitHub Pages with no server (`react-router.config.ts`). Games in the local repository are rendered during the build. A game that fetches code at runtime cannot be part of that render.

## Terms used below

- **Bundle**: the JavaScript files a build tool produces from source code. The browser downloads and runs them.
- **ES module**: the browser's standard format for JavaScript files that import and export values. Browsers can load one at runtime.
- **Dynamic import**: `await import(url)`, which loads an ES module after the page has started, rather than at build time.
- **Import map**: a small JSON block in an HTML page that tells the browser which URL a bare module name means. For example, it can say that `react` means `/assets/react.js`, so code can write `import { useState } from "react"` without knowing the final URL.
- **Module Federation**: a build tool feature that lets one application load code built by another, and agree on a single copy of shared libraries such as React.
- **Web Component**: a browser feature for defining a custom HTML element (such as `<my-puzzle>`) with its own behaviour and, optionally, its own isolated styles.
- **Sandboxed iframe**: an HTML frame that runs code in a separate browsing context, so the code cannot touch the parent page directly.
- **React context**: a way for a React tree to share a value without passing it down through every component.
- **Hook**: a React function whose name starts with `use`, such as `useState`. Hooks only work inside a component rendered by the same copy of React that provides them.

## What we explored

| Approach                             | How it works                                                                                                                                    | Strengths                                                                             | Drawbacks                                                                                                                                   |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Registry bundled with the app**    | Game code lives in this repository, is registered in one place, and Vite splits each game into its own file that is loaded when that game opens | Simple; full type checking, hot reload and tests; one React; no new security boundary | The game ships only when the whole site is rebuilt and redeployed                                                                           |
| **Runtime ES module from a URL**     | A game is built on its own to one JavaScript file, hosted anywhere that serves files, and loaded with `await import(url)`                       | Games can ship independently of the site                                              | The host must share React with the game; the code runs with full access to the page; a build-time import map or Module Federation is needed |
| **Module Federation**                | The same idea as the URL approach, with a build plugin that negotiates shared libraries at runtime                                              | Handles shared React and version negotiation properly                                 | More configuration for both the host and the game author                                                                                    |
| **Web Components**                   | A game registers a custom HTML element with its own DOM and styles                                                                              | Framework-independent; style isolation                                                | The React boundary becomes awkward: the element manages its own tree, so the host cannot render its components directly                     |
| **Remote DOM or a sandboxed iframe** | The game's code runs in a worker or frame and sends a description of what to draw, or messages, to the host                                     | A real security boundary; the host keeps control of rendering                         | More machinery: a message protocol, sizing, focus and accessibility work                                                                    |
| **Declarative element types only**   | No shipped code: add richer built-in component types to `GameData` and implement them in the engine                                             | Cheapest; stays inside schema validation and prerendering                             | Limited to logic the engine already knows; cannot express a new puzzle                                                                      |

There is no single standard for React plugins. The web platform's answer is ES modules and import maps. The micro-frontend answer is Module Federation. Content-driven applications usually start with a static registry and add runtime loading only when independent publishing is needed.

## What we decided

1. **Scope: display components.** A custom element renders as a display's component, in either the background or foreground layer. Replacing the whole layout, adding HUD widgets or adding camera interactions are out of scope for this work.
2. **Authors: trusted external developers.** They may host their own game code, but their code is expected to be reviewed or known. We are not defending against deliberately hostile code yet.
3. **What an element can do: React UI and game actions.** It renders interactive React components, reads the game's progress, and can complete challenges or enter stages.
4. **The contract is props-only.** The host passes everything an element needs as props: its data, the game snapshot, resources, and callback functions. Elements import React, but nothing else from the host: no host contexts and no host components. This keeps the contract stable and lets an element run under either loader.
5. **One module per game.** A game has at most one custom module, and that module can expose several named elements. The game data names the element it wants in a display.
6. **Two loaders, one contract.** A **registry** loader for code in this repository, and a **URL** loader for code hosted elsewhere. The registry loader comes first; the URL loader is a later addition.
7. **React must be shared between the host and the module.** If the host renders a module's component, the component's hooks must belong to the same React instance. Two copies cause the "Invalid hook call" error. The registry gets this for free. The URL loader must arrange it with an import map or Module Federation; the plan for that phase must choose. Do not bundle React into a module that the host renders.
8. **Element state survives unmounting.** Displays open and close during a game, so a React component's own state would be lost. The host provides a small store per element that lives above the display layers for the life of the game.
9. **Elements can read the whole game's progress** through a stable, read-only interface, because their rendering may depend on what happened earlier. They receive a snapshot, not the internal state object.
10. **No raw state setter.** Elements do not receive `setGameState`. They get named actions, so they cannot put the game into a state the layers cannot render.
11. **CSS through the existing `stylesheets` mechanism.** A module's CSS file is declared as a resource and listed in `stylesheets`. No new loading mechanism.
12. **A version handshake.** A module declares the version of the contract it was built against. The host refuses a version it does not support, with a clear message.
13. **In-memory state only.** Element state, like game progress today, is not saved between page reloads. Persistence is out of scope.

## The module contract

The contract lives in a new `game-api` area: types, plus one small React helper. It can later be published as a package that external authors install, without pulling the rest of this application into their build.

```ts
/** What a game module provides. */
export interface GameModule {
  /** The version of this contract the module was built against. */
  apiVersion: 1;
  /** The elements the module provides, by the name a display uses. */
  elements: Record<string, GameElementComponent>;
}

/** A React component that draws one game element. */
export type GameElementComponent = ComponentType<GameElementProps>;

/** Everything the host passes to an element. */
export interface GameElementProps {
  /** The display's `data` for this element, exactly as authored. */
  data: Record<string, unknown>;
  /** The layer this instance draws into. */
  layerHint: "background" | "foreground";
  /** A stable identifier for this element instance, used to scope its state. */
  elementScope: string;
  /** A read-only view of the game and its progress. */
  game: GameSnapshot;
  /** Resolved resource URLs, by resource name. */
  resources: Record<string, string>;
  /** The challenge this display belongs to, when it is a challenge display. */
  challenge?: GameChallengeSummary;
  /** The element's own state, kept for the life of the game. */
  state: GameElementState;
  /** The actions the element may take. */
  actions: GameElementActions;
}
```

### Reading game state

`GameSnapshot` is a read-only projection of the game's progress. It deliberately does not expose the internal `GameState` type, so the internal shape can change without breaking game code.

```ts
export interface GameSnapshot {
  /** The game's id in the repository. */
  id: string;
  /** The game's title. */
  title: string;
  /** The settings that change how the game behaves. */
  config: {
    sequential: boolean;
    autoAdvanceStages: boolean;
  };
  /** Each stage in order, with its progress. */
  stages: GameStageSummary[];
  /** What the player is looking at now. */
  current: {
    stageId: string | null;
    overviewDisplay: string | null;
  };
}

export interface GameStageSummary {
  id: string;
  availability: "locked" | "unlocked";
  completion: "ready" | "partial" | "completed";
  challenges: GameChallengeSummary[];
}

export interface GameChallengeSummary {
  id: string;
  succeeded: boolean;
}
```

The host builds a new snapshot whenever the game state changes. React re-renders the element with the new props. An element can therefore tell whether a stage is complete, whether a particular challenge has been solved, and which stage is open.

The authored game data itself (displays, templates, styles) is not part of the snapshot. An element already receives the `data` written for it and the resolved `resources`. If a future element needs the whole authored `GameData`, that is an open question below.

### Element state

React throws away a component's state when the component leaves the page. Displays change as the player moves from a title screen to a challenge, and a challenge's display changes when it is solved, so an element's state would be lost at exactly the moments a game usually needs to remember something.

The host keeps a store above the display layers, for the life of the game. Each element receives a `GameElementState` object:

```ts
export interface GameElementState {
  /** The stored value, or undefined if nothing has been stored yet. */
  read<T>(): T | undefined;
  /** Replaces the stored value. */
  write(value: unknown): void;
  /** Calls the listener when the value changes. Returns a function that stops listening. */
  subscribe(listener: () => void): () => void;
}
```

The `game-api` package also provides a React hook that wraps it:

```ts
const [value, setValue] = useElementState<MyState>(props.state, initialState);
```

The hook uses `useSyncExternalStore`, React's built-in way to read a value that lives outside React and re-render when it changes. The helper is bundled with the module, so it uses whichever React the module uses; because React is shared (see decision 7), it is the same instance as the host's.

**Scope.** The host derives an `elementScope` for each rendered element from the module id, the element name and an optional `stateKey` in the display's data. State therefore follows the element as the player moves between displays and stages. An author who needs two otherwise identical elements to keep separate state gives them different `stateKey` values.

**Lifetime.** The store is created when an element first renders, and removed when the game changes or the page is reloaded. It is not written to local storage. This matches the lifetime of game progress today.

**Why not module-level variables?** A variable at the top level of a module looks like an easy place to keep state, but it is fragile: hot reload can replace the module and lose it, tests leak values between cases, and there is no clean way to reset it when a new game starts. A store owned by the host avoids all three.

Two copies of the same element mounted at once, with the same scope, share one store and stay in step.

### Actions

```ts
export interface GameElementActions {
  /** Marks a challenge as solved, exactly as a correct answer does. Does nothing if it is already solved. */
  completeChallenge(stageId: string, challengeId: string): void;
  /** Opens a stage, exactly as clicking its entry on the stages overview does. */
  enterStage(stageId: string): void;
}
```

The host implements these with the existing pure functions: `completeChallenge` in `src/components/core/logic/GameStateUtils.ts`, and the click handling in `src/components/core/logic/GameClickUtils.ts`. The element never receives `setGameState`.

## Delivery

### Registry loader (first)

Game code lives in `src/games/<gameId>/`. The entry file exports a `GameModule`. One registry maps a module id to a function that imports it:

```ts
export const GAME_MODULES: Record<string, () => Promise<GameModule>> = {
  "magic-trifle": () => import("./magic-trifle"),
};
```

Vite turns each entry into a separate file, loaded only when that game opens. Development gets hot reload, type checking and the existing test setup. The game data refers to the module by id:

```json
"modules": {
  "custom": {
    "enabled": true,
    "source": { "type": "registry", "target": "magic-trifle" }
  }
}
```

An explicit map is preferred over a wildcard import such as `import.meta.glob`, because every id is visible, and a missing or misspelled id is a normal TypeScript error rather than a runtime surprise. The plan may revisit this.

### URL loader (later)

The game's own build produces an ES module and a CSS file. Both are hosted anywhere that serves files with CORS (the response header that lets another site load them). The game data names the module:

```json
"source": { "type": "relative", "target": "modules/magic-trifle.js" }
```

or

```json
"source": { "type": "url", "target": "https://example.com/games/magic-trifle.js" }
```

`relative` resolves against the repository's location, using the same rule as relative templates and resources (`resolveRelativeURL` in `src/util/ObjectUtils.ts`). `url` is used as it is.

The loader:

1. Resolves the URL.
2. Accepts it only if it is `https:` or same-origin, mirroring the rule for stylesheets in `src/components/core/Game.tsx`.
3. Calls `await import(/* @vite-ignore */ url)`. The comment stops Vite trying to resolve the URL at build time.
4. Checks `apiVersion` and that the module exports an `elements` map.
5. Caches the loaded module per URL, so opening a game twice does not fetch it twice.

The load happens in an effect, after the page has mounted, never during render. Prerendering runs in Node with no browser, and a render-time import would try to fetch the module during the build. While the module loads, the game shows its existing loading view. A failure moves the game into a new `module-error` loading state with a clear message.

**Sharing React.** The host and the module must use one React instance, because the host renders the module's components. There are two established ways to arrange this:

- **A build-time import map.** The host's build writes a `<script type="importmap">` into each page, mapping `react`, `react/jsx-runtime` and the game API to the host's files. The game's build marks those names as external. This needs a stable URL for the host's React, which means either a fixed output filename or generating the map from Vite's build manifest in `finish-static-build.sh`.
- **Module Federation.** The host and the game both use the federation plugin and declare React as a shared singleton. The plugin resolves the shared copy at runtime.

The URL phase must choose one and record the decision. Module Federation is the more robust option if several games share more than React. An import map is a smaller change if React is the only shared dependency.

## Data model changes

`GameData` gains a custom module:

```ts
export interface CustomModuleData extends GameModuleData {
  /** Where the module's code comes from. */
  source: GameModuleSourceData;
}

export type GameModuleSourceData =
  { type: "registry"; target: string } | { type: "relative"; target: string } | { type: "url"; target: string };
```

`GameData.modules` becomes:

```ts
modules?: {
  camera?: CameraModuleData;
  custom?: CustomModuleData;
};
```

`enabled` follows the camera module's convention: when it is false, the game's custom elements are not loaded or rendered.

A display gains a component type:

```ts
export interface GameDisplayCustomComponentData extends GameDisplayComponentBase {
  type: "custom";
  /** The name of an element the game's module provides. */
  element: string;
  /** Separates otherwise identical element instances that should not share state. */
  stateKey?: string;
  /** CSS for the background layer's container. */
  backgroundStyle?: CSSProperties;
  /** CSS for the foreground layer's container. */
  foregroundStyle?: CSSProperties;
}
```

`GameDisplayComponentType` and `GameDisplayComponentData` gain `"custom"`. The schemas in `public/schemas/` are regenerated from these types by `pre-build.sh`.

## Rendering

The custom element is rendered by `GameDisplayComponent` (`src/components/core/display/GameDisplayComponent.tsx`), which already chooses the component for a display.

That function currently computes a `common` object from `component.backgroundTemplate` before it switches on `component.type`. Only the template, dialog and scroll types have templates. The custom case must be handled before `common` is computed, or the types must be reorganised so that the shared fields are explicit.

The element is rendered twice per display, once for each layer, as the other component types are. It receives `layerHint` and can draw differently for each half. The layer wrappers in `src/components/core/layout/GameLayersLayout.tsx` already provide positioning, click handling and stacking.

The module itself is loaded by a provider inside `GameDataProvider`, alongside `GameContentCacheProvider`. Both are keyed by game id, so changing game resets the module and its state. The provider exposes the loaded `GameModule` and a loading state. The element store provider sits at the same level, above the layers.

## Security

Custom code runs in the page, with access to the DOM, `localStorage` and the network. With trusted authors, that is accepted for now. The cheap safeguards go in immediately:

- accept a module URL only if it is `https:` or same-origin;
- check `apiVersion` and refuse an unsupported one;
- never give an element `setGameState`;
- log a clear error, and show the game's loading view, when a module or element is missing.

If the site later loads games from untrusted authors, the answer is a sandboxed iframe or Remote DOM, not a stricter version of `import()`. The existing entry in `docs/outstanding-issues.md` about a `script-src` Content-Security-Policy stays relevant: a policy that blocks scripts would also need to allow the module's origin.

## Validation and tests

The data validators (`validate-game.sh`, `validate-repository.sh`, `scripts/validate-resources.ts`, `scripts/resource-checks.ts`) should check the module source as they check resources and templates:

| `source.type` | What to check                                                                                                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `registry`    | The id exists in the registry. This needs a list the validator can read without executing React components; the plan should choose how. |
| `relative`    | The file exists beside the repository                                                                                                   |
| `url`         | A request succeeds, unless `--skip-urls` is given                                                                                       |

The checker cannot see inside a JavaScript file, so it cannot confirm exports or `apiVersion`. Those are checked when the module loads, and the error message must name the game, the module source and what was expected.

Tests should cover:

- the registry loader returns the module, and fails clearly for an unknown id;
- the URL loader resolves `relative` and `url` sources, rejects an `http:` source, checks `apiVersion`, and reports a failed import;
- an element receives its `data`, `layerHint`, `resources` and `challenge`;
- element state survives unmounting and remounting within one game, and is separate for different `stateKey` values;
- an element sees an updated `game` snapshot after a challenge is completed;
- `actions.completeChallenge` completes a challenge and `actions.enterStage` opens a stage;
- an element renders in both the background and foreground layers;
- the generated schema accepts a `"custom"` component and rejects a missing `element`.

Use the existing test setup (`tests/`, msw serving `public/`, `tests/data/SmallGame.ts`) and a small fake module fixture. The URL loader test can serve a stub module from msw.

## Open questions for the plan

- **Registry shape**: an explicit map or `import.meta.glob`? The explicit map is the current preference.
- **Publishing the contract**: npm package, a git dependency, or a copied `d.ts`. External authors need the types before the URL loader exists. The registry phase does not need a published package, so this can wait for the URL phase.
- **Typing the state store**: `GameElementState.read<T>()` returns `T | undefined` from an untyped store, which is a deliberate unchecked read. Keep any such escape in one documented helper in the API package, never in game code, and avoid `any`.
- **One element per display or several**: today a display has one component. Several independent custom elements on one layer would need a different data shape. An element can compose its own internal components, so this may not be needed.
- **The whole authored `GameData`**: the snapshot covers progress. If an element needs the authored displays or templates, add them to the contract deliberately.
- **Other hooks**: camera interactions, HUD widgets and stage transitions are out of scope. Decide later whether they join the same contract.
- **URL phase**: import map or Module Federation, and whether the URL loader ships at the same time as the registry loader or in a later release.
- **Error experience**: what a player sees when a custom element fails to load. The game's existing loading view is the starting point.
- **Version policy**: how long an old `apiVersion` stays supported once a second version exists.

## Constraints and conventions

- Follow `AGENTS.md`: no `any` or equivalent type escapes, zero warnings, comments that state intent, and change only what the work requires.
- Reuse the existing helpers rather than adding parallel ones:
  - `completeChallenge` and `validateAnswer` in `src/components/core/logic/GameStateUtils.ts`;
  - the click and stage-entry logic in `src/components/core/logic/GameClickUtils.ts`;
  - `resolveRelativeURL` in `src/util/ObjectUtils.ts`;
  - `GameContentCacheProvider` and its fetch-once cache;
  - `GameDisplayRenderData` in `src/components/core/logic/RenderDataUtils.ts`;
  - the `GameDataLoadingState` pattern in `src/providers/GameDataContext.tsx`.
- Run `dev-qual/scripts/check.sh` after every stage, and `--comprehensive` in the final stage.
- Regenerate the schemas and the TSDoc after changing `src/entities/` or exported types, as the pre-commit hook does.
- Per `docs/prompts/README.md`, implementation goes on a new branch from the head of `main`, named for this prompt (for example `001.00.00-custom-game-elements`), and the plan is stored beside this file as `001.00.01.plan - custom game elements.md`.

## Done when

- A game in the local repository uses a custom element from the registry and plays correctly through the dev server and a static build.
- The element renders from its `data`, reads the game snapshot, and completes a challenge through `actions.completeChallenge`.
- Its state survives switching between the displays of one game, and resets when a different game is opened.
- The URL loader is either implemented and tested or recorded as planned follow-on work, with the React-sharing choice noted.
- The schema, the validators, the tests and the documentation all reflect the new component type and module source.
- `dev-qual/scripts/check.sh --comprehensive` passes.
