## Context

The game will run with the camera behind and above the player, and the screen in front. That needs a way to choose the camera, an unmirrored picture, and sturdier tracking from behind. A player should also pass in front of or behind scene items. `cameraFillGaps` currently draws stray copies of the player, and needs fixing.

### Decisions taken

| Decision                                            | Choice                                                                                                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mirroring (not in the prompt, found while planning) | "Mirror picture" checkbox on the landing page, off by default, saved with the camera choice. A rear camera moves the wrong way on screen if mirrored.          |
| Players and depth                                   | Each player is sorted separately, with one canvas per player.                                                                                                  |
| Depth source                                        | Bottom of the silhouette, not the foot points. Build now, tune on the real camera afterwards.                                                                  |
| Depth scope                                         | `data-depth` items in challenge foregrounds only. Overview and stage foregrounds stay behind the player, because they must stay beneath challenge backgrounds. |
| Coloured markers                                    | Not now. Recorded in the ADR, with what would change the decision.                                                                                             |
| Kinect                                              | Not now. Needs a native bridge, so it gets its own prompt (stage 7).                                                                                           |

### Defaults to check when reviewing

- **"Should not be possible to start"** in the prompt is read as: not possible _until the permission is granted_.
- **A game that only enables the camera can start without permission.** The browser asks when the first camera display appears. If refused, the existing fallback plays on by clicks.
- **A `required` camera that fails in play for another reason** (eg. another app is using it) keeps the existing fallback. Only a missing permission bounces the player to the landing page.
- **`modules.camera` is renamed to `requirement` too**, so one resolver handles both.
- **`resetDisplay` camera settings now count** when scanning a game for camera use. The current scan misses them.
- **The "No permissions needed" panel goes away**, because the camera is the only permission.
- **The webcam preview now always sits above foreground items.** Today they can cover it.

### Findings

- **`cameraFillGaps` (likely cause, not yet reproduced on real footage).** `movement` (`src/vision/Tracking.ts:109`) takes the _mean_ move of the key points. BodyPix builds four of its eight key points from the extent of the face pixels (`src/vision/models/BodyPixModel.ts:92`). One stray face pixel moves those four together, diagonally, which fits the reported above-left and below-right copies. Nothing limits the shift, so the whole silhouette is copied that far away. `fillFromPrevious` itself looks correct.
- **Permissions and labels.** Browsers hide camera names until permission is granted, and may list only one camera. So the order is: grant, then list, then preview.
- **System default.** There is no reliable "default" id for cameras. "System default" therefore means asking with no device id, and reading the real device from `track.getSettings().deviceId`.
- **From behind.** The bench's one rear-view photo placed 0 of 4 feet with every model, while silhouettes reached 92–94% of the frame height (ADR 0005). BodyPix's head points come from face pixels, so they may be missing from behind too, which would affect `head-enter`. This is one photo and needs a real-camera check (stage 8).
- **Kinect.** Depth via libfreenect is reported working on an M1, but flaky. No Mac skeleton tracking was found, because NITE is no longer available. A browser can't use it directly.

### Constraints and reuse

- Reuse: `getCameraStream` (`CameraSupport.ts`), `checkGamePermission` and `requestGamePermission` (`GamePermissionUtils.ts`), `useGamePermissions`, `OneEuroFilter` (`Tracking.ts`), the try/catch storage pattern in `GamePermissionUtils.ts`, `tests/helpers/permissions.ts`, and `tests/browser/fixtures/fakeCamera.ts`.
- No new dependencies. The dropdown is a native `<select>`.
- Security: the preview and device ids stay in the browser, and ids go only in `localStorage`. `data-depth` comes from game content, so it is parsed as a number and clamped to 0–100 before use.

### Stage 1: Fix `cameraFillGaps`

**Brief:** in `src/vision/Tracking.ts`:

- `movement` uses the median move per axis, not the mean.
- Add a `MAX_FILL_SHIFT` const (5% of frame width, about 48 px at 960 wide, roughly a brisk walk per frame at 10 fps). `fill` skips the fill for any frame that moved further. Filling is only cosmetic, so a skipped frame costs little.

The cap is the real guarantee: whatever the cause, no copy can appear further away than this.

**Tests:** `tests/Tracking.test.ts`:

### Stage 5: One canvas per player

**Brief:** no depth yet, and players should look the same as before.

- `startTrackingLoop` keeps a pool of canvases by position, not by player id: the existing `canvasRef` canvas draws the first player, and the others are added and removed as the number of players changes. A canvas is redrawn every frame, so nothing about a player needs to stay with it. One player costs exactly what they did before. (Changed from a `Map<id, canvas>` during stage 5: the pool is simpler, and keeps the reference canvas drawing.)
- It calls `drawPeople` once per player, with `{ ...frame, people: [person] }`, and clears the first canvas when nobody is found.
- Canvases are created directly in the DOM, not through React, so frames don't cause re-renders. A grid on the container overlays them.
- `tintPixels` picks its tint by `person.id`, not list index, or everyone would get the same colour.

### Stage 6: Player depth

**Brief:**

- **Stack.** In `GameLayersLayout`, a new `.depthStack` (`z-index: 6`, `isolation: isolate`) holds the player canvases and the challenge foreground layer. That layer loses its own z-index, so it no longer forms a stacking context, and items can sit between players. The preview and debug layers stay above it.
- **Order.** Items and canvases get `z-index = depth - 1000`, always negative. Items with no `data-depth` stay at `auto`, so they stay in front of players as they are today.
- **Ground point.** `groundOf(mask, width)` gives the row with 99% of the person's pixels above it, so stray pixels are ignored. Its result is a % of frame height.
- **Smoothing.** A `DepthFollower` per player takes the highest ground value (lowest on screen) over a rolling window, so a jump doesn't read as moving away. It then ignores changes inside a deadband, so a player near an item's line doesn't flicker across it. A held player keeps their last depth.
- **Knobs,** in `AppConfig.ts` and `docs/configuration.md`, for real-camera tuning: `cameraDepthWindowMs` (default 700) and `cameraDepthDeadband` (default 2, in %).
- **Items.** Each frame, set `z-index` on the stack's `[data-depth]` elements. Per-frame, because a template re-render (Idiomorph) can strip inline styles. `:where([data-depth]) { position: relative }` makes `z-index` apply, without overriding an author's own `position`.
- **Debug.** `?debug=true` draws each player's depth line.
- **Sample.** Add a "Walk around" stage to the rules demo in `public/game-repository.json`, with far and near posts, for manual testing. (Changed from `public/test-repository.json` during stage 6: the app never loads that file, it only feeds the validator.)

**Limitation to document:** a template ancestor with `transform`, `opacity` or similar forms its own stacking context, which stops sorting for the items inside it.

**Tests:**

- `tests/Depth.test.ts`: `ground ignores stray pixels`, `a jump keeps the depth`, `stepping forward updates at once`, `stepping back updates after the window`, `the deadband stops flicker`, `a bad data-depth is ignored`, `values clamp to 0–100`.
- Browser, new `tests/browser/depth.spec.ts`: `a player is ordered between a far and a near item`, `an item with no depth stays in front`, `the canvases overlay correctly under the foreground`.

**Gate:** `dev-qual/scripts/check.sh --fast` + `npx vitest run tests/Depth.test.ts` + `scripts/run-browser-tests.sh depth`.

## Verification

- **Automated:** `check.sh --comprehensive` passes, including the browser suite with the fake camera.
- **By hand, on the landing page:** a camera game shows the dropdown after granting, the preview switches with the choice, and unplugging a chosen camera falls back to the default. A `required` game can't start until granted. Opening `/play` directly bounces only when required. A game with no camera shows no panel.
- **By hand, in play:** with the camera behind you, stepping right moves you right on screen. Walking past a depth item puts you behind it, then in front. A jump doesn't change the order. With `?cameraFillGaps=true`, no stray copies appear.
- **Not provable by me:** real-camera behaviour from behind. This remains owed to the user, using the stage 8 script, and the depth defaults are estimates until then.
