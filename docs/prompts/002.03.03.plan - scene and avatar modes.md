## Context

The 002.03 series needs two settings that later prompts build on. **Scene mode** (`2D` for now, `2.5D` in 002.03.04) sets how a scene is laid out. **Avatar mode** (`mouse`, `camera`, `mouse-feet`) sets what stands in for the player. They replace `camera: { requirement, preview }`. `mouse-feet` lets a pointer play foot and jump rules without a camera, so every scene plays without one.

### Decisions taken

| Decision                                | Choice                                                                                                                                                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `avatar.fallback` inheritance           | Travels with `mode`. The setting that supplies the winning mode also supplies the fallback, and `{ mode: "camera" }` on its own means the camera is required. `preview` inherits separately, as now.   |
| Interactions mouse-feet fires           | `foot-enter/exit`, `any-enter/exit`, `jump`, `jump-from` and `jump-onto`, all as player 1. Pointer interactions (`click`, `mouse-*`) fire as usual. Hand, head, body and near interactions never fire. |
| Rules demo                              | A new "stepping stones" stage on `mouse-feet` that reuses `lava.hbs`. The lava stage stays on `camera` with a `mouse` fallback.                                                                        |
| Key names                               | `scene` and `avatar`, the same at `modules` and on any scene (and reset scene), as `camera` is now.                                                                                                    |
| Active challenges that disagree on mode | `camera` > `mouse-feet` > `mouse`. This extends today's "a challenge turning the camera on wins".                                                                                                      |
| Scene-mode resolver                     | Not added yet. With one value, nothing reads it, and knip would flag an unused export. Stage 1 adds the type and schema, and 002.03.04 adds the resolver when `2.5D` arrives.                          |

### Mapping from the old key

| Old `camera`              | New `avatar`                        |
| ------------------------- | ----------------------------------- |
| `requirement: "required"` | `mode: "camera"`, no fallback       |
| `requirement: "enabled"`  | `mode: "camera", fallback: "mouse"` |
| `requirement: false`      | `mode: "mouse"`                     |
| `preview`                 | `preview`, unchanged                |

### Reuse

- `src/components/core/logic/RenamedKeys.ts`, which `compileGameRules` and `scripts/validate-schema.ts` already call. Add `camera` to it, with a message that gives the mapping.
- `src/components/core/logic/CameraModeUtils.ts`: the inheritance order (`resolveCameraField`, `firstDeclared`) becomes the avatar resolver.
- `ResolvedCameraMode { enabled, preview }` stays the layout's and `useSceneTransition`'s camera input, derived from the effective avatar mode, so the reshape and preview code doesn't change.
- `useCameraFallback` in `GameLayersLayout.tsx:257` already switches modes when the camera fails. It now switches to the resolved fallback, not always to mouse.
- `PlayerInteractionHook.ts`: `CameraRuleTarget`, `CameraRuleEvent`, `sceneRoots` and the `elementFromPoint` topmost check (`frameTargets`, line 101) are the model for the mouse-feet target lookup.
- `useMouseHolds` in `GameRulesHook.ts`: the timer pattern for `holdMs`.

### Stage 3: Mouse-feet input (Opus)

**Brief:** add `src/components/core/layout/MouseFeetHook.ts`. `useMouseFeet(viewportRef, cameraRules, onPlayerInteraction, enabled)` listens for pointer events on the viewport while the effective mode is `mouse-feet` and the scene isn't transitioning.

- **Targets.** Find them as `frameTargets` does: rules with `foot-*`, `any-*` or `jump*`, their elements via `sceneRoots(scope)`, and a hit at the point. The element must be topmost there (`elementFromPoint`) unless the rule sets `includeCovered`. Thresholds don't apply, since a point is inside or not. `ponytail:` note the ceiling: a point, not a foot-sized area.
- **Hover.** On `pointermove` with no button down, work out what the feet are over. Fire `foot-enter` and `any-enter` on new targets, and the matching exits on targets left. Honour `holdMs` with a timer per target, as `useMouseHolds` does. The first position after the hook is enabled only records what holds, as `PlayerMonitor` does on its first frame.
- **Drag = jump.** On `pointerdown`, record the take-off point and the targets under it. Once the pointer moves more than `DRAG_PX` (8), the player is airborne: fire exits for everything entered.
  - On `pointerup`, take the targets under the release point.
  - Fire `jump-from` for each take-off target, `jump-onto` for each landing target, and `jump` for each target in both. Then fire entries for the landing targets.
  - An `anywhere` jump rule (`selector === undefined`) fires `jump`, as in `PlayerMonitor.followJump`.
  - Swallow the `click` the browser fires after a drag (capture-phase listener, once). Block native image drag with `dragstart` `preventDefault`.
- **Click.** A press and release that never moves more than `DRAG_PX` is untouched, and fires a normal `click`.
- **Leaving.** `pointerleave` fires the exits of everything entered. Fire every event through `onPlayerInteraction` as `player: 1`.
- **Rearm.** On a scene reset, rearm as `useRearmOnReset` does: drop what is entered without firing exits.
- Mount it in `GameLayersLayout` with `enabled = mode === "mouse-feet" && !scene.transitioning`.

**Tests:** `tests/MouseFeetHook.test.tsx`, using jsdom pointer events with a stubbed `elementFromPoint` and `getBoundingClientRect`:

- moving over and off fires `foot-enter` and `foot-exit` once each, and `any-*` when a rule asks;
- a covered element doesn't fire, unless `includeCovered`;
- `holdMs` delays the entry;
- a drag from A to B fires exits on take-off, then `jump-from` A, `jump-onto` B and enter B, and no `click`;
- a drag within one element fires `jump` for it;
- an `anywhere` rule fires `jump`;
- a press with a 3px wobble is a `click` and no jump;
- disabled fires nothing;
- `pointerleave` fires exits.

**Gate:** `dev-qual/scripts/check.sh --fast` and `npx vitest run tests/MouseFeetHook.test.tsx` pass.
