Prepare a plan to implement floor area management.

# Context

Each display that uses the camera will have a _conceptual_ floor layout.

For a given game, the camera is not expected to move, so the floor layout for all displays is the same.

It's important that a player be able to walk around every part of the floor area - ie. their feet should be planted on the floor.

To achieve this, we'll need to rescale all displays that have camera enabled to ensure that they fit around the floor area.

## Calibration view

Footsteps should have a built in calibration view, accessible from each game's landing page (ie. a calibrate button on the camera preview). This will make use of the camera, and also mouse interactions, to help the user set the playable area.

The camera preview on the landing page should have the playable area superimposed onto it so it's visible during game setup.

The calibration view must be used at least once before a game can be started or resumed.

The view should show the floor layout as 4 points of a symmetrical quadrilateral, joined by lines, initially laid out as:

- bottom left: near the bottom left corner of the camera view
- bottom right: near the bottom right corner of the camera view
- top left: 1/5 from left, 1/3 from top of the camera view
- top right: 4/5 from left, 1/3 from top of the camera view

(Challenge these positions if they don't make best sense for a typical "camera is above head height looking down on the playing area" situation. The goal here is that the user can walk around the view and their feet are always tracked.)

Each corner should have a draggable anchor point (show it as a circle with a draggable cursor icon when the mouse is over it).

It should be possible to drag the bottom bar up and down, and adjust its width by moving the bottom left / bottom right points left and right.

Same goes for the top bar, and the top left / top right points.

This should be sufficient to allow a user to set the playable area.

Buttons on this view:

- reset
- save

## Display rescaling

If the playable area in the calibration display is modified to indicate that the initial assumption about the player's available area of motion is smaller than the default, displays should be rescaled so that players can still stand at all points at the front of the display.

> [!NOTE]
> If their area of motion is restricted, players may not be able to stand at every point at the back of the display. We need a solution for this.

## Recommendations

Fit the view to the floor by cropping the camera image, and let games place key items in floor coordinates to solve the back-of-floor problem. These come from reading the code and working through the geometry. Nothing has been built or tried on a real camera.

### Display rescaling

- **Crop the camera, not the displays.** Position the camera canvases so the front bar spans the viewport's width and sits on its bottom edge.
- **Reshape the viewport.** A single scale can't always fit both width and height: a short, narrow front bar could push the back of the floor off the top. Instead, set the viewport's shape to the crop, which is the front bar's width by the height from the image top down to the bar. The viewport already reshapes to fit the camera. Extreme calibrations would get side bars.
- **Interactions.** `maskRectForElement` already maps through the canvas's on-screen rectangle, so most camera interactions should keep working. Player depth needs checking, as do camera displays in dialogs.
- **No special case.** Use the same calculation for the default and any smaller area.

### Back of the floor

The floor narrows towards the back, so the display's back corners can't be reached.

| Option                                                                                                                   | Good                                                       | Bad                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Floor-placed items (recommended):** for example `data-floor="x y"`, with the engine working out the position and depth | Silhouettes stay true, and items are reachable in any room | Existing items need converting                                                                             |
| Slide each player sideways by depth                                                                                      | Works with existing games                                  | People drift sideways when walking forwards, jitter is amplified, and interactions need per-player mapping |
| Warp the camera image to a rectangle                                                                                     | The whole display is reachable                             | Distorts bodies and adds a cost to every frame                                                             |

Authors can't hand-place items safely, because every room's calibration differs. Debug mode should also shade the unreachable area, and warn when an interactive item sits inside it.

### Default corner positions

Change the defaults, because the back bar in the prompt looks too far away and too wide:

| Corners | Left | Right | From top |
| ------- | ---- | ----- | -------- |
| Front   | 8%   | 92%   | 90%      |
| Back    | 25%  | 75%   | 55%      |

These are calculated, not measured, for a 4:3 webcam with a 42° vertical field of view, 2 m high and tilted down 22°. In that setup, a back bar at 1/3 height is about 7.5 m away, and the floor would only be about a third of the image wide there, not 60%. The recommended back bar is about 4.5 m away, with the whole body in frame at both front and back. The front inset keeps feet and bodies away from the image edge, where tracking is weakest.

### Other recommendations

- **Calibration storage.** Save it per camera rather than per game, because it describes the room. Using image coordinates means mirroring won't invalidate it.
- **Dragging.** Moving one corner mirrors the other, which keeps the shape symmetrical. An off-centre camera won't fit perfectly, so wait to see if that matters. Use pointer events and add arrow-key control.
- **The calibration requirement.** Enforce it on the `/play` route too, because direct links skip the landing page. Exempt games without a camera and people playing by clicks. Browser tests will need a saved calibration.
- **People outside the area.** Keep tracking them as normal, as ignoring spectators is a separate feature.

### Questions

1. How should "This means" end in "Playable area preview", and what are "the playable area, and the selected playable area"? The recommendations assume they mean the default and the calibrated area, both shown as debug outlines.
2. Are floor-placed items acceptable for the back of the floor? This is the biggest choice, because it adds a new way for authors to position items.
3. Should existing games be converted in this work? The recommendation is to convert only the rules demo, and leave `magic-trifle` until it needs it.
