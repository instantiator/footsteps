Prepare a plan to add `spawn` and `despawn` actions, to let things that move under a still mouse pointer interact with it, and to rework how rules, triggers, actions and events fit together: named actions and events, actions that report when they finish, and actions grouped to run together or one after another.

This prompt folds in what was 002.03.20 (actions, events and sequences), as both rework the same parts of the rules engine.

# Context

[002.03.10](<002.03.10.prompt - new games and badges.md>) added Jump and duck (2D), a runner. It sends a fixed pool of four obstacles across the scene with `item-move`, each restarted on its `effectEnd` with a random `delayMs`, and a speed worked out from the score. That was enough for a simple runner, so `spawn` and `despawn` were left out. Playing it by mouse also showed that an obstacle moving under a pointer that isn't moving only counts the first time each obstacle passes.

A rule today has a trigger (`on`), an optional condition (`if`), and a list of actions (`do`), applied in order but all at once. Only `delayMs` spaces them out ([002.02.02](<002.02.02.prompt - effects.md>)). Some things a rule starts report their end, by class rather than by name:

- `effectEnd`, for an effect by its name (eg. `item-move`), optionally on a target.
- `animationEnd` and `transitionEnd`, for CSS animations and transitions on an element.

Sounds and rewards don't hold anything up, and nothing fires when they finish. So a game can only line things up with them by matching times by hand: a `delayMs` here, an `after` there. [002.03.10](<002.03.10.prompt - new games and badges.md>)'s games do this, eg. completing a challenge 1.5 s after a fall or a fanfare.

# Spawn and despawn

| Addition                                                   | Does                                                                                                                         |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `{ "spawn": "<template selector>", "into": "<selector>" }` | Adds a copy of a `<template>` element's content to the element `into` names, so any number of items can be on screen at once |
| `{ "despawn": "<selector>" }`                              | Removes spawned copies, eg. on an obstacle's `animationEnd` or `effectEnd` once it has left the scene                        |

- Copies go when their scene closes or resets, as effects do. A reset rebuilds the template, so this may come for free; check.
- Rules, effects, and camera and mouse interactions find copies by selector, as they find any other element. Copies have no `id` unless the author gives them a way to have one, so think about how a rule tells copies apart (eg. `event.id`, or a counter in state the copy's markup can use).
- A copy should be able to start its own effect: eg. a spawned obstacle starts its `item-move` as it arrives. Consider a `start`-like trigger for a spawned copy, or an effect that targets "the copy just spawned".
- Copies are not saved, like effects.
- Validation: a `spawn` whose `<template>` or `into` matches nothing is a console warning, like other unmatched selectors. A spawn rate high enough to flood the scene (eg. an `every` of 50 ms with no `despawn`) deserves a guard, like the loop guards elsewhere.
- Templates are re-rendered by Idiomorph, which keeps elements by `id`. Spawned copies must survive a re-render of the template around them.

Rework Jump and duck to use `spawn` if it makes the game simpler, and let it pick each obstacle's kind (high or low) at random with `random()`.

# Things moving under a still mouse pointer

In mouse mode, `mouse-enter` and `mouse-exit` come from the browser's own `mouseover` and `mouseout`. Chrome reports an element moving under a still pointer, but only on that element's first pass. A still pointer in Jump and duck's lanes loses a life or two, then goes untouched. Moving the pointer, as a player does, counts every pass. `mouse-feet` is the same: it only hit-tests on pointer events.

- Hit-test the last pointer position (`lastPointer` in `src/util/PointerPosition.ts`, added in 002.03.10) on each animation frame, while a shown scene has `mouse-enter`, `mouse-exit` or `mouse-feet` rules. Fire enters and exits from it, as a real move would.
- Don't double-fire with the browser's own events, and don't re-render the game each frame when nothing has changed.
- Only run it when it can matter: there's a pointer over the game, and the scene has moving elements or rules that need it.

# Named actions and events

- **Named actions:** any action can be given a name. A rule can then trigger on that action's **start** or **end** (eg. `{ "on": { "actionEnd": "fanfare" } }`), as well as on the classes of event there are today.
- **Raising an event:** an action can raise a named event (eg. `{ "raise": "door-opened" }`), and a rule can trigger on it (eg. `{ "on": { "event": "door-opened" } }`). Decide which scenes hear an event: the scene that raised it only, or others (eg. a stage's shared scene, or every shown scene), and whether events carry data.
- **Naming:** settle how events are named and spelled across the rules: today's `effectEnd`, `animationEnd` and `transitionEnd`, the new action start and end, and raised events. Aim for one consistent scheme, and keep today's triggers working or name what replaces them, as the renamed-keys checks do for older names.

# Actions report their end, and groups

- **Every action reports its end.** An effect ends when it finishes. A sound ends when it has played, and a reward when it has shown. An action that applies at once, such as `set`, `completeChallenge` or `enterStage`, ends at once. An indefinite effect ends when it is stopped or its scene ends.
- **Groups:** a rule's actions can be grouped as **parallel** (start together; the group ends when the last one ends) or **series** (each starts when the one before it ends; the group ends with the last). Groups nest. A `do` list with no grouping is parallel, as now.
- **Delays** still apply within a group: a `delayMs` waits from when that action would start.
- **Ending early:** decide what happens to a group, and to its remaining actions, when its scene closes or resets (today delayed actions are dropped), and what a series does when one of its actions can't run (eg. an expression time that doesn't work out).
- **Reduced motion:** effects jump to their end and still report it, so series still run in order.

Rework the demos and Nanny's Magic Trifle to use series where they now match times by hand. Eg. the pits: fall, then reset, rather than a 1.5 s `delayMs` that matches the fall's length.

# Things to consider

- Keep the rule engine pure: rules change the game through pure functions of the latest state, so the record of what is running and what ends next belongs in the session, as delayed actions do now.
- **Players:** a delayed or series action that acts on the triggering player should keep reaching the same person if their number is reused before it runs. See the related outstanding issue below.
- Validation: a trigger naming an action or event that nothing in the game names or raises is a warning, like an unmatched selector. A series inside a `start` rule that resets its own scene is the same loop error as today.
