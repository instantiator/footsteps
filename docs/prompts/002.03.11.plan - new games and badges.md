## Context

Scene modes, avatar modes and 2.5D scenes are in place. The repository now needs one game for each style: a 2D mouse demo, a 2D camera runner, and the 2.5D demo with some changes. The landing page should show what each game needs and how far the player has got. Two bugs are fixed along the way: a pointer or player already in place at scene start isn't noticed, and a scroll's paper sits behind the player while its text sits in front.

### Decisions taken

| Decision                  | Choice                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Starting state (bugfix 1) | **Fire on what already holds.** When a scene starts, resets, or is revealed after its fade, every `-enter` interaction fires for whatever is already under the mouse pointer, the mouse-feet, or a camera player. A `when` that is already true fires too. The engine's "must move away and back" rule goes. The existing guard of 10 resets a second stops a scene that resets itself on an enter and has no reset scene. |
| Dialog depth (bugfix 2)   | **Dialogs and scrolls sit above the players**, in every layer (overview, stage and challenge). Paper, text and controls are drawn together in one layer, above `.depthStack` and below the camera preview, debug overlay and HUD.                                                                                                                                                                                          |
| Lava effect               | **Reuse `player-static`**, with chunky pixels easing to `proportion: 1`, then reset after a delay. No new effect.                                                                                                                                                                                                                                                                                                          |
| Spawning                  | **Left out.** A fixed pool of obstacles, each restarted on `effectEnd` with a random `delayMs` and a score-based `durationMs`, is enough for the runner. `spawn` and `despawn` go to `docs/outstanding-issues.md`.                                                                                                                                                                                                         |
| `random(min, max)`        | A filtrex `extraFunctions` entry. It returns a uniform real in `[min, max)`; use `floor` for integers. It isn't predicted anywhere, because validation only parses expressions. It is allowed everywhere, including in `when`.                                                                                                                                                                                             |
| Effect timings            | `durationMs`, `cycleMs` and `delayMs` take a number or an expression, and `durationMs` also takes the reserved `"indefinite"`. They are worked out when the rule fires (`delayMs`) or when the effect is queued (`durationMs`, `cycleMs`), from the state at that moment. A result that isn't a finite number ≥ 0 is logged naming the rule, and that action is skipped, as `ruleDelay` does today.                        |
| Jump and duck             | **Camera optional**: `camera` with `fallback: "mouse"`, where the pointer is the runner. Its badge reads "Camera optional", and browser tests play it by mouse.                                                                                                                                                                                                                                                            |
| Demo camera use           | **Camera is optional everywhere.** Nothing in the demo requires the camera today. Stone hop is the exception the prompt asked about: it is `mouse-feet` only and can never use the camera, so it becomes `camera` with a `mouse-feet` fallback. Pits, floor-is-lava and walk-around fall back to `mouse-feet` ("your mouse is your feet"). Balloons, effects and the overview keep falling back to `mouse`.                |
| Play without camera       | A **"Play without the camera"** checkbox on the landing page, shown only for "Camera optional" games. When it is ticked, the game opens at `/game/:id/play?camera=off`. Calibration and camera permission are then not needed, and `useCameraFallback` starts in its failed state, so every scene uses its fallback.                                                                                                       |
| Demo renames              | Stage `lava` → `pits` ("Avoid the pits"), and `stone-hop` → `floor-is-lava` ("The floor is lava"), ids included. Saved demo progress for those two stages is dropped, which is acceptable for a demo.                                                                                                                                                                                                                      |

### - [ ] Stage 2: Dialogs and scrolls in front of players (bugfix 2), and the virtual pointer prompt

A scene whose component is a dialog or scroll renders whole there, paper and text together, in place of its background and foreground parts. Keep the class names and ids that effect targets rely on ("Dialogs and scrolls give their whole frame", `special-effects.md` Targets), and keep the dialog's drop shadow. Don't add a stacking context inside `.depthStack` (see the warning at `GameLayersLayout.css:60`).

It describes a future avatar mode that tracks a player's hand relative to their head, turns it into a virtual pointer drawn with a default graphic that a game can replace, and lets camera players use dialogs and scrolls. It should explain why: dialogs are mouse-only today, which is why this stage puts them above the players.

**Tests:** `tests/GameLayersLayout.test.tsx`: for a challenge scroll and an overview dialog, the paper and text are both in the dialog layer, which comes after `.depthStack`. `tests/browser/viewport.spec.ts` (or `camera.spec.ts`, with the fake camera): `elementsFromPoint` at the scroll's centre finds the paper before any player canvas.

### - [ ] Stage 7: Jump and duck (2D) game

**Brief:** a new game `jump-and-duck`, "Jump and duck (2D)", with `modules: { scene: "2D", avatar: { mode: "camera", fallback: "mouse" } }`. Its theme and art are its own: rolling snowballs low down and flapping pudding-bats up high, drawn in CSS or SVG, in `public/games/jump-and-duck/`. Two stages share one template, differing by `data`: "Warm-up" (target 15, slower) and "Long run" (target 40, faster).

- **Reset scene** (`every-show`): a 3-2-1 countdown, as in balloons.
- **Obstacle pool:** `#low-1`, `#low-2`, `#high-1`, `#high-2`. A `start` rule launches each with an `item-move` from the right edge to the left, with `delayMs: "random(500, 2500)"` and `durationMs: "max(data.minMs, data.baseMs - state.score * data.speedUp)"`. One `effectEnd: item-move` rule per obstacle restarts it the same way.
- **Hits:** `body-enter` on `.low` and `head-enter` on `.high` (camera), plus `mouse-enter` on both (fallback), with `if not state.over` → `lives - 1` and a `quake` on the obstacle.
- **Score:** `every: 1000` → `score + 1` while not over.
- **End:** `when: "state.score >= data.target"` → `completeChallenge`, sound and reward. `when: "state.lives <= 0"` → `set over`, then `resetChallenge` with `delayMs: 1500`.
- The HUD shows score and lives. Thresholds are first guesses; tuning them on a real camera is owed (see wrap-up).

**Tests:** `tests/browser/jump-and-duck.spec.ts`, with `?camera=off`:

- With the pointer parked clear, the score rises and obstacles cross the scene.
- Moving the pointer onto an obstacle costs a life.
- Losing three lives shows the countdown again.
- With a small target patched in through `page.route`, a run completes.

Use `page.clock` to keep timings deterministic. A vitest case checks the template's obstacle rules fire `item-move` with resolved number timings.

**Gate:** `check.sh --fast`, `scripts/run-browser-tests.sh jump-and-duck`, `./validate-repository.sh public/game-repository.json`.
