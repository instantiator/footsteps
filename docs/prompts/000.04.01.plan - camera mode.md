# Plan: camera mode — per-display settings and player interactions

**Status:** done

**Reviewer summary (whole plan):** Seven gated stages. First the game-data format becomes interaction-aware (clicks keep working), then camera mode and its preview become per-display, then a pure `PlayerMonitor` turns segmentation masks into hand/foot/head/body/jump events, then it is wired into the live loop, then a real-browser fake-camera suite proves the segmentation loop fix, and finally the camera documentation is rewritten for junior developers. Every stage ends at a quality gate; nothing is deferred silently.

## 1. Context

**Reviewer summary:** Camera mode works visually but is all-or-nothing for the game, has no way to interact with what it sees, and its one bug fix has never run against a real camera.

Camera mode cuts the player out of the webcam and layers them into the game (`docs/camera-mode.md`). Today:

- `GameData.modules.camera.enabled` switches it on for a whole game; no display can override it.
- The webcam preview is always shown when camera mode is on.
- Elements in templates are clickable only; `GameOverviewDisplay.clickIdToStageId` maps element id → stage id string.
- `CharacterCanvas` already finds feet, but nothing consumes them except the debug overlay.
- The segmentation-loop cancellation fix from bug #16 has no test beyond jsdom, which has no camera, WebGL or TensorFlow.

The outcome wanted: per-display on/off for camera mode and its preview, an extensible element-interaction model, a monitor that reports what a detected player does, a jump detector, a real-browser test route for the camera code, and documentation a junior developer can follow.

## 2. Decisions taken

**Reviewer summary:** The data shape follows the prompt exactly; camera settings resolve by inheritance, with any active challenge able to turn the camera on; old game JSON breaks cleanly; the browser suite is local-only.

| Decision               | Choice                                                                                                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Game data shape        | `clickIdToStageId?: Record<string, GameInteractionTarget>` where `GameInteractionTarget = { stage, interactions?, threshold? }`                                                     |
| Interaction names      | `GameInteraction = "click" \| "hand" \| "foot" \| "body" \| "head" \| "jump" \| "any"`; camera-only subset is `Exclude<GameInteraction, "click">`                                   |
| Defaults               | `interactions` defaults to `["click"]`; `threshold` defaults to `1`; camera `preview` defaults to `true`                                                                            |
| Game default           | `modules.camera = { enabled: boolean; preview?: boolean }`; existing games keep their current behaviour                                                                             |
| Per-display settings   | `GameDisplayBase.camera?: { enabled?: boolean; preview?: boolean }`, so overview, stage and challenge displays all support it                                                       |
| Challenge layer        | Any active challenge that sets `enabled: true` turns the camera on; if none does, an explicit challenge `false` turns it off; if no challenge declares the field, the stage decides |
| Stage and overview     | Fallback chain: stage display → overview display → game setting                                                                                                                     |
| Preview                | Same any-true / else-any-false / else-inherit rule, then forced off when the camera is disabled                                                                                     |
| No camera in a display | The camera is stopped (tracks stopped, stream state cleared), not merely hidden                                                                                                     |
| Preview off            | The camera keeps running; the preview layer is hidden with `visibility: hidden`, so the `<video>` keeps decoding                                                                    |
| Interactions scope     | Only displays that already have `clickIdToStageId` (overview displays) can trigger interactions, as today; challenges gain it later                                                 |
| Click compatibility    | Clean break: the old `"id": "stage-id"` string form is rejected by the schema; all bundled JSON is migrated                                                                         |
| Property name          | Keep `clickIdToStageId` as the prompt specifies, even though it now holds more than clicks; the docs will explain it                                                                |
| Event shape            | `PlayerMonitorEvent = { elementId: string; interaction: CameraInteraction }`; edge-triggered (fires on entry, not every frame)                                                      |
| Jump tuning            | Constants in one module: velocity threshold `0.3` frame-heights/second, sequence window `1500 ms`; refined by manual test                                                           |
| Browser testing        | Playwright + Chromium, fake `getUserMedia` from a canvas `captureStream()`, so images can be switched mid-test; local/opt-in only, not CI                                           |
| Branch and commits     | `000.04.00-camera-mode`; prompt and plan early, then one commit per stage                                                                                                           |
| ADR                    | Add `docs/ADRs/0002-camera-interactions.md` in the documentation stage                                                                                                              |

## 3. Constraints and reuse

**Reviewer summary:** The plan reuses the existing helpers instead of inventing parallel ones, and each stage brief restates the exact standards that the gate will enforce.

### Code quality standards, applied per stage

- **Zero compiler and linter errors and warnings.** `dev-qual/scripts/check.sh --fast` after each change; `check.sh` before each stage commit; `check.sh --comprehensive` at the end.
- **No `any` or equivalent escapes.** Test mocks are typed (`Pick<ImageData, "data">`, `ComponentProps<typeof CharacterCanvas>`, plain `Rect` objects) — never `as any`.
- **TSDoc on every exported type, function, constant and interface member.** `npm run docs:api` fails on undocumented exports. Intent, not mechanics; a short opening sentence, a blank line, then paragraphs or numbered lists; `NB.` for caveats; `{@link Type}` links.
- **React standards.** Pure calculations outside components (`resolveCameraMode`, `maskRectForElement`, `PlayerMonitor`); components stay thin. Every `useEffect` and `useCallback` carries a comment saying why it exists. Dependency arrays must not restart the segmentation loop on ordinary re-renders — the frame callback reads mutable config from refs.
- **Less is more.** No new abstraction with one implementation. Reuse `isDefined`, `findFeet`, `BODY_PARTS`, `enterStage`, `getNewGameStateForClick`, the existing camera layer wrappers and the existing test helpers.
- **Security.** Game data is untrusted. `threshold` is clamped to 0–1, `interactions` are matched against the known union (unknown values are ignored), and element ids are only passed to `getElementById` — never interpolated into selectors or markup. No new network or storage behaviour.
- **Accessibility.** Click and keyboard paths stay exactly as they are. The docs will tell authors to keep `click` alongside camera interactions, so camera mode never becomes the only way to progress.
- **Data and schema.** New entity types flow into `public/schemas/*.json` through `./generate-schemas.sh`; `./validate-repository.sh public/game-repository.json` must pass. `@minimum 0` / `@maximum 1` on `threshold` are supported by `typescript-json-schema` and should appear in the generated schema.

## 4. Design

### 4.1 Game data model

**Reviewer summary:** One small set of types carries the whole feature; the schema is regenerated from them.

```ts
/** A way a player can interact with an element in a display. */
export type GameInteraction = "click" | "hand" | "foot" | "body" | "head" | "jump" | "any";

/** What interacting with an element does, and how the player can do it. */
export interface GameInteractionTarget {
  /** Stage entered by the interaction. */
  stage: GameStageId;
  /** Accepted interactions. Defaults to `["click"]`. */
  interactions?: GameInteraction[];
  /**
   * Fraction of the body part that must be inside the element (0–1).
   *
   * @minimum 0
   * @maximum 1
   */
  threshold?: number;
}

/** Camera mode settings for one display; unset fields fall back to broader displays. */
export interface GameDisplayCameraData {
  /** Whether camera mode is on while this display shows. */
  enabled?: boolean;
  /** Whether the webcam preview shows while this display shows. */
  preview?: boolean;
}
```

- `GameDisplayBase` gains `camera?: GameDisplayCameraData`.
- `GameOverviewDisplay.clickIdToStageId` becomes `Record<string, GameInteractionTarget>`.
- `CameraModuleData` gains `preview?: boolean`.
- `public/game-repository.json` migrates each magic-trifle entry to `{ "stage": "stage-N" }`; `interactions` and `threshold` are omitted, preserving today's behaviour.
- `tests/data/SmallGame.ts` and `tests/GameClickUtils.test.ts` migrate the same way.

### 4.2 Camera mode per display

**Reviewer summary:** A pure function resolves two booleans by inheritance. Any active challenge can switch the camera on; an explicit challenge can switch it off only when no challenge asks for it; otherwise settings flow stage → overview → game.

New `src/components/core/logic/CameraModeUtils.ts`:

```ts
/** Whether camera mode and its preview are on for the displays currently shown. */
export interface ResolvedCameraMode { enabled: boolean; preview: boolean }

/**
 * Resolves camera mode by inheritance, most specific first.
 *
 * Any active challenge that enables camera mode wins. If none does, an explicit
 * challenge setting disables it. If no challenge declares the field, the stage,
 * then the overview, then the game's camera module decide.
 */
export const resolveCameraMode = (
  gameData: GameData,
  renderData: LayeredGameDisplayRenderData,
): ResolvedCameraMode
```

Resolution of one field:

1. If any active challenge sets the field to `true`, the field is `true`.
2. Otherwise, if any active challenge sets the field to `false`, the field is `false`.
3. Otherwise, the stage display's value if set.
4. Otherwise, the overview display's value if set.
5. Otherwise, `gameData.modules?.camera` if set.
6. Otherwise, the default: `false` for `enabled`, `true` for `preview`.

`preview` is then forced to `false` when `enabled` is `false`.

Consequences to document:

- A challenge that sets nothing inherits its stage's setting.
- A challenge that sets `enabled: false` turns the camera off even when its stage sets `enabled: true`, because no other active challenge enabled it.
- Once any active challenge enables the camera, a second challenge cannot disable it while both are on screen. This matches "any challenge can enable it".

`Game.tsx` memoises `getLayeredRenderData`, derives the mode, and passes `camera` to `GameLayersLayout` instead of `cameraLayer`.

`GameLayersLayout` then:

- mounts `CharacterCamera` and `CharacterCanvas` only while `camera.enabled`;
- keeps `CharacterCamera` mounted when only the preview is off, hiding the preview layer (`visibility: hidden`) so the video keeps playing;
- clears `characterStream` and `video` when the camera is disabled, after the child's cleanup has stopped the tracks; `aspectRatio` is kept, so re-enabling does not blank the layers while the camera reacquires;
- keeps gating display layers on the aspect ratio exactly as now.

### 4.3 Interaction pipeline

**Reviewer summary:** The model already produces a per-pixel body-part mask; one scan totals it, one scan per element counts what is inside, and a monitor turns threshold crossings into events.

1. **Mask decode, once per person per frame** — `CharacterCanvas` calls `segmentation[i].mask.toImageData()` and reuses it for both `findFeet` and interactions. This removes the extra `toBinaryMask` call per person in `findAllFeet`.
2. **Report** — `CharacterCanvas` gains `onPlayersChange?: (players: PlayerFrame[], timestamp: number) => void`, where `PlayerFrame = { id, mask: ImageData, feet: FootPosition | null }`. The timestamp is `performance.now()`, passed in so tests are deterministic. The callback is stable, so the segmentation effect is not restarted by ordinary re-renders.
3. **Map to the frame** — `maskRectForElement(elementRect, canvasRect, maskWidth, maskHeight)` converts an element's viewport rect into mask pixel bounds, accounting for the mirrored canvas: `x` flips about the canvas centre, `y` does not. Bounds are clamped; no overlap yields an empty rect.
4. **Monitor per player** — `GameLayersLayout` keeps `Map<number, PlayerMonitor>`, creates one per detected id, drops monitors for players who leave, and calls `monitor.update(player, targets, timestamp)`. Targets are the current overview display's `clickIdToStageId`, by element id, each with its mask-space rect.
5. **Coverage** — one full-frame pass per player totals pixels per mask value; one pass per target rect counts inside pixels. Groups:

| Interaction | Pixels counted                                        |
| ----------- | ----------------------------------------------------- |
| `hand`      | `LEFT_HAND`, `RIGHT_HAND`                             |
| `foot`      | `LEFT_FOOT`, `RIGHT_FOOT`                             |
| `head`      | `LEFT_FACE`, `RIGHT_FACE`                             |
| `body`      | all body-part pixels (the person silhouette)          |
| `any`       | each individual body part, threshold applied per part |

`fraction = inside / total`; satisfied when `inside > 0` and `fraction >= threshold`. Threshold 0 therefore means "at least one pixel"; threshold 1 means "all of it". Out-of-range values are clamped. 6. **Events** — a `PlayerMonitor` fires `{ elementId, interaction }` only on a false→true transition, and re-arms when the condition stops holding. Holding a hand over an element fires once. `jump` fires when its sequence completes. 7. **Acting on events** — `GameClickUtils` gains `getNewGameStateForInteraction(state, targetId, interaction)`; `getNewGameStateForClick` delegates to it with `"click"`. A target responds only when its resolved interactions include the event's interaction. `leaveTitleScreen` stays click-only, so waving at the title screen does nothing. `Game` handles the event exactly as a click, and `enterStage` still ignores locked and completed stages.

### 4.4 Jump detection

**Reviewer summary:** A small per-element state machine over the feet's vertical velocity, with one timeout covering both "left the element briefly" and "held at the apex".

- Vertical motion comes from `feet.percent.y` between frames, divided by elapsed seconds. Positive is downward (screen y grows downward).
- `|velocity| <= 0.3` (frame-heights/second) counts as still; below `-0.3` is upward; above `+0.3` is downward.
- Per target element that lists `jump`:

| Phase     | Moves to              | When                                                                                 |
| --------- | --------------------- | ------------------------------------------------------------------------------------ |
| `ready`   | `rising`              | feet meet the threshold inside the element, and motion is upward                     |
| `rising`  | `falling`             | feet meet the threshold inside the element, and motion is downward                   |
| `falling` | `ready`, emits `jump` | feet meet the threshold inside the element, and motion is still                      |
| any       | `ready`               | `1500 ms` elapse without completing the sequence, including time outside the element |

- Leaving the element does not reset the sequence while the window is open; returning inside is required for the downward and still phases.
- The same threshold applies to the feet for "inside", so a `jump` target can require the whole foot to be over it.
- A missing foot position leaves the state untouched until the timeout; it cannot advance the sequence.

### 4.5 Testing the camera loop (outstanding issue: bug #16)

**Reviewer summary:** Three layers of proof — a mocked unit regression, a real-browser fake-camera test, and a short manual script for a physical camera. Playwright is feasible; the only real cost is the TensorFlow model download.

- **Unit regression** (`tests/CharacterCanvas.test.tsx`): mock `@tensorflow-models/body-segmentation` and `@tensorflow/tfjs`; mount with a stream and video; resolve the model; run a frame; unmount or change `maskType`; assert `segmentPeople` is not called again and `dispose` ran once. This proves the cancellation logic deterministically.
- **Browser test** (`tests/browser/`): Playwright + Chromium. An `addInitScript` replaces `navigator.mediaDevices.getUserMedia` with a `MediaStream` from `canvas.captureStream(10)`. Frames are drawn on that canvas, and `page.evaluate` can replace the image at any time — which answers the "switch the image" investigation without Y4M encoding. The test loads a game with camera mode on (the game JSON request is intercepted with `page.route` and patched, so no bundled game changes), waits for the silhouette canvas, toggles `?debug=true`, asserts the canvas keeps changing and the console shows no TensorFlow or "disposed model" errors. A fake-stream track's `readyState` on `window` proves the camera stops on a camera-off display.
- **Static/composite images:** the fake stream draws whatever image fixture the test loads, so a plain room, a person cut-out, or a composed "person in a room" image all work. Ship one CC0 person fixture only if its licence is verified; otherwise the harness accepts any image placed in `tests/browser/fixtures/`, and the manual script covers a real person.
- **Y4M alternative:** Chromium's `--use-file-for-fake-video-capture` (Y4M or MJPEG) is the "realistic" option, but it is fixed at launch, needs an encoder, and is Chromium-only. The canvas stream is simpler and switchable, so it is the primary route; document the flag as a fallback.
- **Feasibility estimate:** high. Risks: ResNet50 weights (~90 MB) are fetched from `storage.googleapis.com` at test time, so first run is slow and network-dependent; headless Chromium uses SwiftShader for WebGL and may fall back to CPU, so frames are slow. Mitigate with a 120 s timeout, assertions on state rather than exact frame counts, and local-only execution rather than the main gate.
- **Manual script** (`docs/testing/manual-testing.md`): camera smoke test, the bug #16 reproduction (toggle debug, resize, close and reopen a challenge, watch the console), per-display on/off and preview checks, and each interaction with expected results.

## 7. Risks and outstanding work (initial list)

**Reviewer summary:** The known weak points are model-download flakiness, small body parts at webcam resolution, and player identity across frames; each gets a measurable follow-up condition.

| Risk                                                                                    | Mitigation / outstanding condition                                                                                                                                                                     |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TensorFlow weights (~90 MB) make the browser suite slow and network-dependent           | Local-only suite; 120 s timeout; act when a run fails only on the model download or exceeds 3 minutes — then cache the model locally                                                                   |

| Players are keyed by segmentation index, which can change when someone enters or leaves | Act when two players are tested together and monitors swap; then track by nearest previous position                                                                                                    |
| Per-frame `getBoundingClientRect` and mask scans add work                               | Small compared with inference; measure with `?debug=true`; act when the loop drops below 5 fps with eight targets                                                                                      |
