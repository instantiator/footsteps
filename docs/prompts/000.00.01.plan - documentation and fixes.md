## Context

`docs/prompts/000.00.00.prompt - documentation and fixes.md` asks for:

- data-model docs for `GameData` and the repository
- TSDoc comments on every component, interface and function, plus generated API docs
- a wider test suite
- a list of potential bugs, to be fixed in a later piece of work

Tests that expose a bug are written and then skipped, so that follow-on work can re-enable them.

### Constraints and reuse

- AGENTS.md rules: no `any` or other type escapes (including in mocks), comments state intent, zero lint and type warnings, and only change code we were asked to change. **Don't fix bugs in this work.** Record them and skip their tests.
- TSDoc style (`dev-qual/guidance/languages/typescript/typescript.md`): multi-line `/** */` comments unless one line fits, and `{@link Type}` for types.
- Testing standards: `dev-qual/guidance/standards/testing.md`. Reuse `tests/data/SampleGameState.ts`, `tests/data/sample-repository.json`, and the msw server in `tests/mocks/` (which serves `public/`).
- The JSON schemas are generated from the types (`generate-schemas.sh`, run by `pre-build.sh`). New interface comments will become `description` fields in `public/schemas/*.json`. That's expected, so commit the regenerated schemas with each comment stage.
- Skipped-bug test convention: `it.skip("…", …)` preceded by `// BUG #N (docs/prompts/000.00.02.feedback - …md): <one-line intent vs actual>`.

### Stage 2: Data-model docs (Opus)

**Brief:**

- **`docs/game-data.md`** explains how `GameData` and its children fit together:
  - **Structure.** `GameData` → `GameOverviewDisplay[]` / `GameStageData[]` → `GameChallengeData[]` (→ `GameChallengeSolution`). Every level has displays with a purpose: `GameDisplayPurpose` and its three subsets. A display's `component` is `template` or `scroll`. The scroll `contents[]` hold `media` (`GameDisplayMediaData`). Also cover `modules.camera`, `config`, and `gameContainerStyle`.
  - **Display selection rules** (`calcOverviewDisplay`, `calcChallengeDisplay` in `src/components/core/logic/RenderDataUtils.ts`), and `challengeChunking`.
  - **Resources.** `GameResourceDefinitions` of `local`/`relative`/`url`, resolved to absolute URLs by `resolveResources` in `src/providers/GameDataProvider.tsx` (via `resolveRelativeURL` in `src/util/ObjectUtils.ts`). They're then used by the media `*Resource` keys and passed to templates as `resources`.
  - **Templating.** Template sources are `local`/`relative`/`url`/`embedded`, resolved by `resolveTemplateURL` and cached (`src/providers/GameContentCacheHook.tsx`). The Mustache view is `GameTemplateData`: `gameState` (a `DecoratedGameState` with `stages[].index/oneIndex/showCompleted/showUnlocked/showLocked`, plus `totalStages`), `componentData` (the display's `component.data`), `resources`, and `challenge`/`challengeState` (challenge displays only). Note that HTML escaping is off, and that `containerStyle` values are Mustache-rendered too. Cover `clickIdToStageId` and keyboard access by linking `dev-overview.md#clickable-elements-in-templates`.
  - Use a short example from `public/game-repository.json` (magic-trifle).
- **`docs/game-repository-data.md`** covers:
  - `GameRepository`: `games` keyed by `GameId`, plus the runtime-only `ready`/`loading`/`error` flags that `GameRepositoryProvider` sets.
  - The `GameSource` variants and where each loads from.
  - How relative URLs resolve per source.
  - The schema at `public/schemas/game-repository-schema.json`, and `validate-repository.sh`.
  - It links to `game-data.md` rather than repeating it.
- **`docs/index.md`**: add both docs.

**Gate:** `check.sh --fast`. Opus checks every claim against the code it names.
