## Context

The HUD shows the tracking fps, which the vision stats readout (`FrameStatsReadout` in `CharacterCanvas.tsx`: fps, ms, people, hands, feet) already shows. The readout and the other debug aids should be hidden by default and switched from the HUD. Testers and players also want to jump to any part of a game, and replay a completed challenge.

### Decisions taken

| Decision                          | Choice                                                                                                                                                                                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| What "Debug on / off" switches    | All debug aids: the stats readout, feet markers, colour key and coloured mask. It starts as `?debug` says (off by default).                                                                                                                                                    |
| `showFps`                         | Leaves the HUD. It stays as a URL/env setting that shows only the readout, as the vision benchmark's `VISION_BENCH_PLAIN` mode needs the readout without debug's coloured mask. It is off by default everywhere, dev included (`.env.development` drops `VITE_SHOW_FPS=true`). |
| Locked stages in Go to            | Shown but unselectable, like completed ones.                                                                                                                                                                                                                                   |
| Go to a challenge that isn't next | A new `session.focusedChallenge` shows the chosen challenge's chunk even if earlier ones are unsolved. It clears when that chunk is solved or the stage closes. It is session-only, so saved progress is unchanged (no storage version bump).                                  |
| Option labels                     | Stages and challenges have no authored names, so they read `Stage 2` and `Challenge 2.1`, prefixed `✓` when completed and `🔒` when locked.                                                                                                                                    |

### Reuse

- `resetChallenge` in `src/components/core/logic/GameStateUtils.ts`: Reset calls it as is (unsolved, stage completion recomputed, scene state and finished resets cleared).
- `enterStage` and `leaveTitleScreen` in `GameClickUtils.ts`, `getChunkedChallengeStates` and `getCurrentChallengeStates` in `GameStateUtils.ts`.
- The HUD's existing `buttonStyle`, and its pattern of setting `current`.
- `useNavigate` from react-router, as `GameLanding.tsx` uses it, for Catalogue (`/`) and Game (`/game/:id`).

### Stage 2: Focused challenge

**Brief:**

- Add `focusedChallenge: GameChallengeId | null` to `GameSession` (`src/entities/state/GameState.ts`), `null` in `newGameSession()`.
- `getActiveStageStateChallenges` returns the chunk containing the focused challenge, if it is in the open stage. Otherwise it returns the first unsolved chunk, as now.
- Clear it when the open stage changes or closes. Also clear it in `completeChallenge` once every challenge in its chunk is solved.
- Add `goToChallenge(state, stageId, challengeId)` to `GameClickUtils.ts`. It returns undefined if the stage is locked or the challenge is solved. Otherwise it opens the stage with the challenge focused.

**Tests:** `GameStateUtils.test.tsx` / `GameClickUtils.test.ts`:

- focusing a later chunk shows it;
- solving that chunk clears the focus, and the stage moves on to its first unsolved chunk;
- closing the stage clears it;
- a solved challenge or locked stage can't be focused.

**Gate:** as stage 1.

### Stage 3: HUD Go to

**Changed while implementing:** stages 3 and 4 share one picker component and one module (`src/components/core/logic/HudNavigation.ts`), so they landed in one commit. Labels follow the prompt's form, `Stage: 2` and `Challenge: 2.1`, which also keeps them distinct from games' own stage links.

**Brief:**

- In `HeadsUpDisplay.tsx`, a pure `goToOptions(gameState)` builds the option list (value, label, disabled), in this order:
  - Catalogue;
  - Game: `<title>`;
  - Title: `<title>`, if the game has a title scene;
  - Overview: `<title>`, if it has a stages overview;
  - then for each stage, Stage N, followed by its challenges indented with leading no-break spaces as Challenge N.M. Completed and locked entries are disabled.
- A native `<select aria-label="Go to">` and a "Go" button.
- Each option goes as follows:
  - Catalogue and Game navigate.
  - Title and Overview set `current` as "To title" does now.
  - A stage uses `enterStage`.
  - A challenge uses `goToChallenge`.
- The HUD wraps (`flexWrap: "wrap"`) so it fits narrow screens.

**Tests:**

- `goToOptions` on a game with:
  - a completed stage;
  - a locked stage;
  - a partly solved stage;
  - no title scene.
- Go for each kind of option, in `HeadsUpDisplay.test.tsx`, with a router mock for the navigations.

**Gate:** as stage 1.

### Stage 4: HUD Reset

**Brief:**

- `resetOptions(gameState)` lists each solved challenge as `✓ Challenge N.M`.
- A `<select aria-label="Reset">` and a "Reset" button, both disabled when nothing is solved.
- Reset calls `resetChallenge`, leaving what is showing alone.

**Tests:**

- Reset makes the challenge playable again, and Go to offers it again;
- the controls are disabled with nothing solved.

**Gate:** as stage 1.
