Prepare a plan to add scene modes and avatar modes to game data.

# Context

This follows [002.03.00](<002.03.00.prompt - refactor to scene.md>), which renames "display" to "scene" and lists the prompts in this series. Later prompts build on the two settings added here: 3D scenes are tracked in [997.00.00](<997.00.00.prompt - 3D scenes.md>), and drawn avatars in [996.00.00](<996.00.00.prompt - player avatars.md>).

Every scene mode works with every avatar mode, so scenes still render and play without a camera.

# Scene mode

How a scene is laid out.

- **2D:** a full-screen background, the players, and a foreground. For very simple scenes, like a bonus stage where the player walks around popping balloons above their head, or a runner where the player jumps and ducks as obstacles move towards them.
- **2.5D:** added by [002.03.04](<002.03.04.prompt - calibration.md>). Items are placed on a calibrated floor, and players move around it.
- **3D:** future work.

This prompt adds the setting with one value, `2D`. For now, a 2D scene behaves exactly as scenes do today, including `data-depth` sorting, so the existing games keep working. [002.03.06](<002.03.06.prompt - floor placement.md>) replaces depth sorting with floor positions in 2.5D scenes, leaving 2D scenes with no depth work.

# Avatar mode

What stands in for the player.

- **`mouse`:** clicks, as now when the camera is off.
- **`camera`:** the player's camera cut-out, as now.
- **`mouse-feet`:** as `mouse`, but the mouse's position is treated as player 1's feet:
  - Moving over and off elements fires `foot-enter` and `foot-exit`, so camera rules work unchanged.
  - A drag from A to B is a jump, taking off from whatever is under A and landing on whatever is under B. It fires `jump-from`, `jump-onto` and `jump` exactly as a camera jump with that take-off and landing would.
  - A press and release without moving more than a few pixels is still a `click`.
  - [002.03.06](<002.03.06.prompt - floor placement.md>) makes the position available to variables, so elements can draw something there.

# Game data

```json
"modules": {
  "scene": "2D",
  "avatar": { "mode": "camera", "fallback": "mouse", "preview": true }
}
```

- `avatar.fallback` is the mode to use when the camera isn't available. Leaving it out means the camera is required.
- These replace `camera`: `requirement: "required"` becomes `mode: "camera"` with no fallback; `"enabled"` becomes `mode: "camera", fallback: "mouse"`; and `false` becomes `mode: "mouse"`. `preview` moves across unchanged.
- Any scene can override either setting, most specific first, as camera settings do now.
- As in 002.03.00, update every game, and fail validation on the old `camera` key with a message naming the new ones.

# Done when

- Every game in the local repository loads, validates and plays as before, using the new keys.
- A stage in the rules demo uses `mouse-feet`, and tests cover its foot interactions, drags as jumps, and clicks.
- `game-data.md` and `camera-mode.md` describe both settings.
