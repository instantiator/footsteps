## Context

Games need richer feedback: items that shake, fall, move and pulse, and players who can fall, be knocked away, freeze, fade or turn to static. Some of these remove a player until the display resets, which needs player state that lasts longer than today's tracking was built for. Adding them also fills gaps in the engine: a delay on any action, a reset that really ends what a display was doing, rules that know which player fired them, and one coordinate system.

### Decisions taken

| Decision                                    | Choice                                                                                                                                                                                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What a reset does to timers                 | The display starts afresh: `every` and `after` restart, and `start` rules fire again. A `start` rule that resets (`resetState`, `resetChallenge`) is a load error, as it would loop. No current game has one. |
| No-target quake on a dialog or scroll       | Shakes the whole dialog frame. The background and foreground frames always share one motion, ignoring `consistentMotion: false`, so they stay lined up.                                                       |
| Gap at the edge of a shaking full-size item | While shaking, an item reaching the display's edges is scaled up just enough to cover `dx`/`dy`.                                                                                                              |
| Delivery                                    | One branch, one commit per stage.                                                                                                                                                                             |

### Defaults to check when reviewing

The prompt left these open. Each is the simplest reading, and each is cheap to change now.

1. **`border` is dropped from highlight steps.** It changes an element's size, which moves its layout and where the camera thinks it is. `outline` does the same job. (The prompt invited this.)
2. **Quake `easing` fades the strength out.** Strength is `1 - eased progress`, so every timed quake ends at rest rather than snapping back. No `easing` keeps full strength throughout, as the prompt says.
3. **A reset restores only the players that display affected; moving restores everyone.** Any display being replaced by another restores all players, as the prompt says, even with a stage's shared display still showing. A reset restores those whose state was set by that display's rules, so with challenges side by side, one resetting doesn't revive a player removed by the other. A display and its own reset display showing in turn count as a reset, not a move. `game.players.removed` counts across the whole scene.
4. **`keepRemovedPlayers` is read from the display being reset**, not from its reset display. It keeps only removed players. A player mid-fall on that reset goes straight to removed. Moving to another display still restores everyone.
5. **`"all"` for `player-restore` means everyone with a state, including the removed.** The prompt's table defines `"all"` as active players, but its own restore sample needs this.
6. **A leaving player doesn't restart.** "Firing again restarts" would make a repeated `player-fall` on a falling player start the fall over, so it is ignored.
7. **`stop` can't stop `player-fall` or `player-spin-away`.** They must finish, so naming them is a load error, and "all effects" skips them. `stop` also rejects the one-way effects (`player-invisible`, `player-visible`, `player-freeze`, `player-unfreeze`, `player-restore`) and `stop` itself. These have dedicated counterparts.
8. **Stopping an item effect returns the item to where its template puts it.** This includes a finished `item-fall` or `item-move`.
9. **A frozen player whose track is lost stays drawn and counted**, until unfrozen or inherited. Otherwise "everyone is frozen" could never be relied on.
10. **A reward with a `target` or `players` matching several gives one burst each.**
11. **`effectEnd` accepts every effect but `stop`.** `player-freeze` and `player-unfreeze` fire it at once.
12. **`event.player` is `0` when no player fired the rule**, as expressions need a number. A delayed `"triggering"` effect finds its player by number, so if that person left and the number was reused, it reaches the new holder. Recorded in the tracking doc.
13. **`player-*` effects without `visionSmoothing`** do nothing and log one warning.

### Findings

#### Answers to the prompt's checks

- **Web Animations survive template re-renders.** They aren't held in the `style` attribute that Idiomorph rewrites, so item effects don't need re-applying as depth's inline styles do. An id-less element that a re-render replaces loses its effect; the docs will recommend ids.
- **`filter` and stacking contexts.** Any transform or filter on a wrapper traps `data-depth` items nested inside it. `depth.hbs` has exactly this shape: `.templateBody > .demo-depth > [data-depth]`. Moving `.templateBody > *` there would stop items sorting among players for as long as the shake lasts. So when top-level items are chosen by default, a wrapper containing `[data-depth]` is replaced by its children, recursively. An explicit `target` that does this logs a warning.
- **Other positions and distances the prompt missed.** All are any-CSS-length, and the docs get guidance, not code: `backgroundStyle`, `foregroundStyle`, `backgroundTemplateStyle`, `foregroundTemplateStyle`, `gameContainerStyle`, and `initialState`/`set` values used as positions (the demo's `left`). To add to the "left as they are" table: `jumpStill`, `jumpMinDescent`, `cameraDepthDeadband`, `cameraFeatherPx`.
- **Existing games pass the camera-only check.** Every camera interaction in `public/game-repository.json` shares its rule with `click` or `mouse-*`, so nothing needs changing. Test fixtures may.

#### Problems the prompt doesn't mention

- **`cqw` isn't always the whole display.** A dialog's `OUTER_STYLE` sets `containerType: size` (`GameDisplayDialogComponent.tsx:62`), so inside one, `cqw` measures its column. Effects therefore multiply by a helper's display-to-container ratio. Authored CSS in a dialog template can't, so the docs state the limit. This qualifies the prompt's "in any column" claim.
- **The old display stays on screen during a fade.** `useSceneTransition` keeps showing the old layers after the state has moved on. Cancelling item animations on the state change would snap a fallen bridge back into view mid-fade. So on close, an item effect's end handler is detached and its animation runs on until the rebuild removes the DOM. Pending delays are dropped at once, and player effects are cancelled at once.
- **The new DOM isn't there yet when a rule fires.** After a show, the DOM arrives after the fade, and templates load asynchronously. After a reset, new layers commit after the state change, so `do: [resetState, effect]` would animate elements about to be discarded. `.templateBody` therefore carries `data-display-run`, and a targeted effect retries each animation frame until that run's body exists and its targets resolve (up to 5 s, then the unmatched warning).
- **Browsers remove replaced animations.** A finished forward-filling animation can be auto-removed once a later one covers the same property, and that applies even when both are additive. An item that moves then falls would snap. Every effect with a lasting end state calls `animation.persist()`.
- **A template's own `transform` must survive, and must not bend the effect.** Adding to `transform` would apply offsets after the template's own, so a scaled or rotated item moves wrongly. Effects animate the individual `translate`, `rotate` and `scale` properties, which apply before `transform`, with `composite: "add"` so concurrent effects combine.
- **`when` rules across a reset.** Edges and `forMs` waits are keyed by scope and rule only, so a wait that is still true survives into the new run, and a false-to-true flip caused by the reset fires immediately. `whenKey` gains the run, which cancels old waits and makes the rule record only on first sight.
- **Id-less targets re-fire after a reset.** Rebuilt elements get new keys, so armed monitors would fire `-enter` for a player standing there. Monitors are cleared without releasing whenever a shown run changes, as they are for a display change.
- **Tracker ids can't identify players.** They restart at 0 with each tracking loop, and a note's inheritor gets a new one. See `PlayerRegistry` below.
- **`.player-N` wrappers sit outside `displayRoots`**, and containers can hold the overview behind a stage. Target lookup covers both (stage 5).

### Key design

- **A display "run".** `session.displayRuns: Record<DisplayScope, number>` is the single reset signal. It is bumped when a scope is newly shown (in `applyShowResets`), and by `resetState` and `resetChallenge`. Everything a display started belongs to its run:
  - `.templateBody` is keyed on it, which rebuilds the template and ends and restarts its CSS animations. `getDisplayKey` must not include it, or a reset would fade.
  - `useDisplayLifecycles` keys timers on it.
  - Delayed actions and effects record it, and do nothing if it has changed.
- **Pure rules, effects at the edge.** `fireRules` stays pure. Effects and delayed actions are queued in `session`, and hooks drain them, exactly as `useRuleEffects` does with sounds. Ids only grow, so a queue worked out twice plays once.
- **A hidden reference canvas.** The `<canvas ref>` that exists today stops drawing and never moves, and it keeps the measuring, sizing and mirroring style. Each player gets a wrapper (`.player .player-N`, depth, effects, origin) holding their own canvas (mirror). This solves the measuring reference and `copyOfFirst` inheriting an effect in one move.
- **`PlayerRegistry`.** A plain class, one per game, surviving tracking-loop restarts. It sits between `PersonTracker` and everything else, and owns state, numbers and notes of lost players. It also maps tracker ids to **stable player ids**, and rewrites frames with them, so monitors, depths and wrappers all follow the player. A wrapper stays while its player is tracked or noted, including while removed, so inheriting a frozen note keeps its picture and a restore has something to fade in. Removing a frozen or leaving player from the list given to `onPlayersChange` makes `updateMonitors` call `release`. That gives the `-exit`s, and a fresh monitor on unfreezing gives "must leave and come back".

### Constraints and reuse

- No new dependencies. Web Animations API throughout.
- CSS easing in JS: a `new Animation(new KeyframeEffect(null, [], { duration, easing }))` and `getComputedTiming().progress`, for quake strength and static proportion.
- Reuse: `displayRoots` and `matchTarget` (`TemplateUtils.ts`), `queueEffect` and `applyAction` (`GameRuleUtils.ts`), `useRuleEffects` (`Game.tsx`), `checkSelector` and the path format (`GameRuleCompile.ts`), `resolveCameraField` (`CameraModeUtils.ts`), `centreOf` (`Tracking.ts`, to export), `maskRectForElement` (`CameraSupport.ts`), `stay`/`leave`/`hasHeld` (`PlayerMonitor.ts`), `useMediaQuery`, `tests/browser/fixtures/fakeCamera.ts`.
- `CSS.supports` and `element.animate` are missing in jsdom. Like `checkSelector`, the easing check skips where there is no `CSS`, and unit tests stub it. Runtime effects are covered by browser specs. Unit tests mock with typed fakes, never `any`.
- Browser specs aren't in the gate (`docs/dev-overview.md`), so stages that add them name the command, and it must pass.
- Security: `filter`, `shadow`, `outline`, `easing` and selectors come from game data and reach the browser only through `element.animate` and `querySelectorAll`, never as HTML. Nothing else crosses a trust boundary. Camera data stays in the browser.
- `AGENTS.md` rule 6: this prompt authorises the listed changes. Nothing else gets tidied on the way.

### Stage 10: Player registry, numbers, counts and `event.player`

### Stage 12: Player effects and restoring

**Brief:**

- New `src/components/core/effects/PlayerEffects.ts`: animates wrappers from registry state changes, called by `useGameEffects`. `players` resolves `"triggering"` by `event.player` (warning and doing nothing at 0), `"all"` from the registry.
- **`player-fall`/`player-spin-away`:**
  - state Leaving, snapshot taken;
  - on finish, Removed, then `effectEnd` (so counts have already changed);
  - a leaving player ignores another `player-fall`.
  - Fall distance comes from the silhouette's top.
  - Spin: `transform-origin` at the silhouette's centre (exported `centreOf`, x flipped when mirrored, worked out once); pure `offscreenDistance(centre, radius × zoom, angle, display)`, tested; `rotations` in a random direction, `angle` picked at random.
- **`player-invisible`/`player-visible`:** wrapper opacity, forwards, `persist()`.
- **`player-freeze`/`player-unfreeze`:** registry only, at once. `effectEnd` fires at once.
- **`player-restore`:** cancels everything on the wrapper, returns them to Active, fades in, and clears notes. The wrapper is still there for a removed player. A noted player with no track has their wrapper dropped.
- **Item effects on players:** quake and filter highlight run through the item runner on the wrapper, so they stay with that player. `stop` takes `players`.
- **Rewards on players:** centre of the body, through the registry and the wrapper's rect.
- **Display end:** per defaults 3 and 4. - **Bench:** a filter highlight on a player, with the figures recorded.
