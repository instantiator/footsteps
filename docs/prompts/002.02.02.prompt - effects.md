## Effect actions

Extend `GameAction`, adding `GameEffect` - one of which should be the quake effect.

> [!NOTE]
> `GameEffectAction` already exists, and means a sound or a reward (`GameDisplayData.ts`). Two near-identical names will confuse. **Proposed:** rename the existing one to `GameFeedbackAction`.

Each action is told apart by its keys, eg. `"sound" in action`. The new actions follow that, with `effect` naming which one it is:

```ts
/** An item effect, a player effect, or stopping one. */
export type GameEffect =
  | GameQuakeEffect
  | GameItemFallEffect
  | GameItemMoveEffect
  | GameHighlightEffect
  | GamePlayerFallEffect
  | GamePlayerSpinAwayEffect
  | GamePlayerOpacityEffect
  | GamePlayerStaticEffect
  | GamePlayerRestoreEffect
  | GameStopEffect;
```

### Common properties

These work the same way on every effect that accepts them.

| Property     | Type                     | Default         | Meaning                                                                    |
| ------------ | ------------------------ | --------------- | -------------------------------------------------------------------------- |
| `effect`     | string                   | required        | Which effect to run.                                                       |
| `target`     | CSS selector             | see each effect | The elements to apply it to. See [Targets](#targets).                      |
| `durationMs` | `number \| "indefinite"` | see each effect | How long it runs. See [Duration modifiers](#duration-modifiers).           |
| `cycleMs`    | number                   | see each effect | **Proposed.** The length of one loop, when `durationMs` is `"indefinite"`. |
| `easing`     | CSS easing function      | see each effect | How it speeds up and slows down.                                           |
| `delayMs`    | number                   | `0`             | How long to wait before starting. See [Delay](#delay).                     |

Names follow the existing `delayMs`, `holdMs` and `forMs`.

### Behaviour of all effects

- **Bad values:** a negative time, or an `easing` or `target` the browser can't parse, is an error when the game loads, naming the rule. This is what `GameRuleCompile.ts` does for other mistakes.
- **Firing again:** an effect fired on an element or player already running the same effect restarts it. Different effects run together.
- **Display hidden or reset:** running effects stop, and items return to where the template puts them. Delays still waiting are cancelled. See [Restore](#restore) for players.
- **Reduced motion:** for players who prefer reduced motion, nothing moves. `quake` doesn't play. `item-fall`, `item-move`, `player-fall` and `player-spin-away` jump straight to their end. `player-static` shows, but doesn't flicker. Game state changes exactly as it would otherwise, so these players can still finish the game.
- **Not saved:** effects and player states last for the session, like rewards. Reloading the page shows items where their templates put them.

## Quake effect

This is a fairly simple implementation.

Intended for use when the user completes a specific jump (ie. an effect attached to a jump completion) or any jump.

Example - effect is applied to a single element:

```json
{
  "on": { "interact": ["jump-from"], "target": "#some-element" },
  "do": [{ "effect": "quake", "target": "#some-element", "dx": 1, "dy": 0, "durationMs": 1000, "easing": "ease-out" }]
}
```

Example - any jump shakes the whole scene:

```json
{
  "on": { "interact": ["jump"] },
  "do": [{ "effect": "quake", "dx": 0.5, "dy": 1 }]
}
```

| Property     | Type                     | Default                              | Meaning                                                                                                                               |
| ------------ | ------------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `target`     | CSS selector             | all background and foreground layers | The elements to shake. Players don't shake unless targeted.                                                                           |
| `dx`         | number                   | `0`                                  | How far to shake horizontally, as a % of the display's width.                                                                         |
| `dy`         | number                   | `0`                                  | How far to shake vertically, as a % of the display's height.                                                                          |
| `durationMs` | `number \| "indefinite"` | `1000`                               | How long the shake lasts.                                                                                                             |
| `cycleMs`    | number                   | `100`                                | **Proposed.** The time for one shake there and back. The brief doesn't say how fast it shakes.                                        |
| `easing`     | CSS easing function      | none                                 | How the strength builds and fades. Without one, the full `dx` and `dy` apply throughout. Ignored when `durationMs` is `"indefinite"`. |

> [!NOTE]
> Two things to challenge during planning:
>
> - **"Any jump" isn't possible today.** `target` is required on `GameInteractTrigger`, and jumps only fire for an element the player's feet were on. **Proposed:** make `target` optional for `jump` only, firing on every landing, with `event.id` empty.
> - **Shaking the challenge foreground would break depth sorting.** Moving a container makes it a stacking context, so items inside it can't sit between players (see `.depthStack` in `GameLayersLayout.css`). Find another way to shake that layer, such as moving its items individually.
>
> Shaking a full-size layer also shows a gap at its edge, so check how that looks.

## Item fall effect

> [!NOTE]
> This could already be implemented with variables, as seen in the rules demo game, but this is more meaningful and easier to understand when composing games.

```json
{
  "on": { "interact": ["jump-from"], "target": "#some-element" },
  "do": [{ "effect": "item-fall", "target": "#some-element", "durationMs": 1000, "easing": "ease-in" }]
}
```

| Property     | Type                     | Default                                                                 | Meaning                                                                                                    |
| ------------ | ------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `target`     | CSS selector             | all background and foreground layers (not recommended for this effect!) | The elements that fall.                                                                                    |
| `durationMs` | `number \| "indefinite"` | `1000`                                                                  | Time until the element has left the display. If `"indefinite"`, it falls again from the start, repeatedly. |
| `cycleMs`    | number                   | `1000`                                                                  | **Proposed.** The length of one fall, when `durationMs` is `"indefinite"`.                                 |
| `easing`     | CSS easing function      | `linear`                                                                | How the fall speeds up.                                                                                    |

The element stays off-screen until its display resets. Off-screen, it can't be interacted with, as interactions already measure where elements appear.

## Item move effect

> [!NOTE]
> This could already be implemented with variables, as seen in the rules demo game, but this is more meaningful and easier to understand when composing games.

Move to a place in the display:

```json
{
  "on": { "interact": ["jump-from"], "target": "#some-element" },
  "do": [{ "effect": "item-move", "target": "#some-element", "durationMs": 1000, "end": { "left": 50, "top": 20 } }]
}
```

Move from one place to another:

```json
{ "effect": "item-move", "target": "#lift", "start": { "left": 50, "top": 100 }, "end": { "left": 50, "top": 50 } }
```

Move by an amount:

```json
{ "effect": "item-move", "target": "#lift", "end": { "by": { "left": 0, "top": -10 } } }
```

Move to a place relative to another element, here 10% above the centre of `#platform`:

```json
{ "effect": "item-move", "target": "#lift", "end": { "from": "#platform", "left": 0, "top": -10 } }
```

| Property     | Type                     | Default                                                                 | Meaning                                                                           |
| ------------ | ------------------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `target`     | CSS selector             | all background and foreground layers (not recommended for this effect!) | The elements to move.                                                             |
| `start`      | position                 | where the element is now                                                | Where the move begins.                                                            |
| `end`        | position                 | required                                                                | Where the move ends. The element stays there until its display resets.            |
| `durationMs` | `number \| "indefinite"` | `1000`                                                                  | How long the move takes. If `"indefinite"`, it jumps back to `start` and repeats. |
| `cycleMs`    | number                   | `1000`                                                                  | **Proposed.** The length of one move, when `durationMs` is `"indefinite"`.        |
| `easing`     | CSS easing function      | `linear`                                                                | How the move speeds up and slows down.                                            |

A position is one of:

| Form                                             | Meaning                                                     |
| ------------------------------------------------ | ----------------------------------------------------------- |
| `{ "left": 50, "top": 20 }`                      | A place in the display.                                     |
| `{ "by": { "left": 0, "top": -10 } }`            | An amount from where the element is when the effect starts. |
| `{ "from": "#selector", "left": 0, "top": -10 }` | An amount from the centre of another element.               |

> [!NOTE]
> Challenge this part of the prompt during planning and propose a working solution for a coordinate system.
>
> Do we have an established system for coordinates inside the display, bearing in mind that the view can be scaled? It'd be helpful to be able to move items relative to each other, too.

**What exists today.** There's no single system:

- Templates position items with `%` of their parent, eg. `left: 20%` in `lava.hbs`. With challenges side by side, that parent is one column of `GameChallengeGrid`, not the display.
- Templates size items with `cqw` and `cqh`, eg. `width: 8cqw` in `rules-demo.css`. `.gameViewport` is the size container, so these scale with the view, and always mean the whole display.
- Interactions turn on-screen positions into pixels of the camera's mask (`maskRectForElement`).
- Depth is a % of the scene's height (`groundOf`).

**Proposed system.** All positions are a % of the whole display: `left` of its width, `top` of its height, from the top left. A position places the centre of the element. This matches `cqw`, `cqh` and depth, and means the same thing at any scale, in any column, and whether or not the camera is mirrored, as mirroring only flips the player's canvases. `dx`, `dy` and `within` use it too.

**Limit to check.** Each column of `GameChallengeGrid` has `overflow: hidden`, so an item can't visibly move out of its own column.

## Near trigger

Fires when a player comes close to an element, and optionally when they move away again.

```json
{
  "on": { "interact": ["near"], "target": "#some-element", "within": 10 },
  "do": [{ "sound": "chime" }]
}
```

| Property   | Type                    | Default                         | Meaning                                                                                                                                              |
| ---------- | ----------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `interact` | `"near"`, `"near-exit"` | required                        | `near` fires as a player comes within range. `near-exit` (**Proposed**) fires as they leave it.                                                      |
| `target`   | CSS selector            | required                        | The elements to watch.                                                                                                                               |
| `within`   | number                  | required for these interactions | How close counts as near: the distance from the centre of the element to the closest part of the player's silhouette, as a % of the display's width. |
| `holdMs`   | number                  | `0`                             | As for `-enter` interactions: the player must stay near this long first. Applies to `near` only.                                                     |

- **The silhouette, not key points.** Measuring to a silhouette means it still works from behind, where the bench placed 0 of 4 feet ([ADR 0010](../ADRs/0010-player-tracking-from-behind.md)).
- **Width in both directions.** The range is a circle on screen, whatever the display's shape.
- **Flicker.** It follows `visionStableFrames`, as other camera interactions do, so a player on the boundary doesn't fire it repeatedly.
- **Already near.** A player already in range when a display appears must leave and come back, as with `-enter` interactions.
- **Other trigger settings.** `threshold` and `includeCovered` don't apply.
- **No camera.** There's no mouse equivalent, so a game that falls back to clicks needs another way forward.
- **Code to change.** `isEntering` looks for an `-enter` suffix, so it needs to accept `near` for `holdMs` to work. `COVERAGE_GROUPS` in `PlayerMonitor.ts` measures coverage, so `near` needs its own path.

## Highlight effect

This pair of rules pulses an element while a player is near it:

```json
[
  {
    "on": { "interact": ["near"], "target": "#some-element", "within": 10 },
    "do": [
      {
        "effect": "highlight",
        "target": "#some-element",
        "durationMs": "indefinite",
        "sequence": [
          { "filter": "brightness(1.5)", "shadow": "0 0 2cqw gold", "durationMs": 500, "easing": "ease-in" },
          { "filter": "brightness(1)", "shadow": "0 0 0 gold", "durationMs": 500, "easing": "ease-out" }
        ]
      }
    ]
  },
  {
    "on": { "interact": ["near-exit"], "target": "#some-element", "within": 10 },
    "do": [{ "effect": "stop", "target": "#some-element", "stop": "highlight" }]
  }
]
```

| Property     | Type                     | Default                              | Meaning                                                                                             |
| ------------ | ------------------------ | ------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `target`     | CSS selector             | all background and foreground layers | The elements to highlight.                                                                          |
| `durationMs` | `number \| "indefinite"` | once through `sequence`              | **Proposed.** `"indefinite"` repeats the sequence until stopped. A number repeats it for that long. |
| `sequence`   | list of steps            | required                             | A series of highlight effects, played in order.                                                     |

Each step of `sequence`:

| Property     | Type                | Default | Meaning                                                                           |
| ------------ | ------------------- | ------- | --------------------------------------------------------------------------------- |
| `filter`     | CSS `filter`        | none    | Applied to the element.                                                           |
| `shadow`     | CSS `box-shadow`    | none    | Applied to the element.                                                           |
| `outline`    | CSS `outline`       | none    | Applied to the element.                                                           |
| `border`     | CSS `border`        | none    | Applied to the element.                                                           |
| `durationMs` | number              | `1000`  | How long the step takes.                                                          |
| `easing`     | CSS easing function | none    | How the step's styles build. Without one, they apply at full strength throughout. |

When the sequence ends, the element returns to its own styles.

> [!NOTE]
> Things to check during planning:
>
> - **The sample in the brief had an `easing` beside `sequence` as well as in each step.** Only the per-step one is kept here, as two would conflict.
> - **`border` can change an element's size**, which moves its layout and where the camera thinks it is. Consider dropping `border` in favour of `outline`, or keeping its width unchanged.
> - **`filter` makes an element a stacking context**, which affects depth sorting if it is applied to a container of `data-depth` items.

| `stop`    | an effect's name                          | all effects                          | Which effect to stop.                                |

## Targets

We should be able to apply special targets to rewards/animations/etc. - ie. let's apply some additional css classes to these groups of elements:

| Class                         | Elements                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `.player`                     | **Proposed.** Every player's canvas.                                                                                                       |
| `.player-N` (eg. `.player-1`) | One player's canvas.                                                                                                                       |
| `.display-foreground`         | The display foreground containers: `#overview-foreground-container`, `#stage-foreground-container` and `#challenges-foreground-container`. |
| `.display-background`         | The display background containers, named the same way.                                                                                     |

```json
{ "reward": { "animation": "confetti" }, "target": ".player-1" }
```

```json
{ "effect": "quake", "target": ".display-background", "dx": 1, "dy": 1 }
```

- **Where a `target` looks (Proposed):** inside the display whose rule fired, plus the special classes above. Two challenges side by side may use the same ids, so one shouldn't affect the other. Today, trigger selectors look only inside a display's templates (`displayRoots`), and none of these classes are in there.
- **Rewards:** `GameRewardAction` gains an optional `target` (**Proposed**). The burst starts from the centre of the element, or the middle of the game as it does today. `RewardBurst` currently fixes that position.
- **Missing elements:** a `target` matching nothing logs a warning, as `warnUnmatchedSelectors` does for triggers.
- **`N`:** see [Player numbers](#player-numbers).

## Player state

Player state changes need to be tracked, so that these changes can be implemented.

Some of the effects described here result in players being removed from the display. This will require stable tracking of players over time. If this can't currently be achieved, challenge this part of the prompt during planning.

| State   | Meaning                                                                                         | Drawn       | Interacts | Counted as active |
| ------- | ----------------------------------------------------------------------------------------------- | ----------- | --------- | ----------------- |
| Active  | In play. Includes `player-invisible` and `player-static`, which only change how they are drawn. | Yes         | Yes       | Yes               |
| Leaving | A `player-fall` or `player-spin-away` is running.                                               | Yes, moving | No        | Yes               |
| Removed | The effect has finished, and they are off-screen.                                               | No          | No        | No                |

Leaving players count as active until they are off-screen, so a rule that resets the display when nobody is left lets the last fall finish.

### Stable tracking

> [!NOTE]
> Challenge for planning: **tracking isn't stable enough for this today.** It is good enough for drawing and interactions, where a mistake lasts a moment. A removed state would last until the display resets.

| What happens today                                                                                     | Where                             | What it means for removed players                                                 |
| ------------------------------------------------------------------------------------------------------ | --------------------------------- | --------------------------------------------------------------------------------- |
| A person who is unseen for over 500 ms, or the hold and fade time if longer, comes back with a new id. | `TRACK_TIMEOUT_MS`, `Tracking.ts` | A removed player the model loses for a moment comes back as a new, active player. |
| People are matched to the last frame by the nearest silhouette centre.                                 | `PersonTracker.match`             | Two players who cross can swap ids, moving the removal to the wrong person.       |
| With `visionSmoothing` off, an id is only the person's place in that frame's list.                     | `BodyPixModel.ts`                 | No tracking at all.                                                               |
| Each tracking loop has a new `PersonTracker`, and ids restart from 0.                                  | `startTrackingLoop`               | Turning the camera off for a display, or the loop restarting, forgets who is who. |
| Someone who walks out of shot and back is someone new.                                                 | `Tracking.ts`                     | They rejoin as active.                                                            |

**Proposed:**

- Player state is keyed by tracker id, and player effects need `visionSmoothing` on.
- When a removed player's track is lost, keep a note of where they were. A new person appearing near there inherits the removal, until the display resets.
- Accept that crossing players can swap, and that walking out of shot and back rejoins. Record both in `docs/camera-mode.md`. They are hard to fix without recognising people by appearance.
- Test this on the real camera with two people crossing, as the automated tests' fake camera won't show it.

### Other code that needs to change

- **Canvases follow position, not player.** `PlayerCanvases` redraws each frame by place in the list, so an effect on a canvas would jump to another person when the order changes. Canvases need to be kept per player id.
- **The first canvas is the measuring reference.** `frameTargets` measures every element against `canvasRef`, and that canvas also draws the first player. If it falls, everyone's interactions go wrong. Measure against something that doesn't move.
- **Mirroring uses `transform`.** Canvases can have an inline `scaleX(-1)`. Player effects mustn't replace it, so use the separate `translate`, `rotate` and `scale` CSS properties. `copyOfFirst` also copies the first canvas's inline style, so a new player mustn't inherit an effect.
- **Template re-renders drop inline styles.** The depth code re-applies them every frame for this reason. Check whether the Web Animations API (`element.animate`) avoids this for item effects.
- **Rules don't know which player fired them.** `CameraRuleEvent` and `RuleEvent` have no player, so they need one.

### Choosing players

Player effects use `players` rather than `target`, because a rule usually means "whoever did this".

| Value                    | Meaning                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `"triggering"` (default) | The player who fired the rule. On a rule no player fired (eg. `when` or `every`), the effect does nothing, and this logs a warning. |
| `"all"`                  | Every active player.                                                                                                                |

Rules also gain `event.player`, the triggering player's number, for use in expressions.

### Player numbers

**Proposed.** Tracker ids only ever grow, so `.player-1` wouldn't reliably mean anything to a game's author. Instead, each tracked person takes the lowest free number from 1, keeps it while tracked, and frees it when they go. `N` in `.player-N`, and `event.player`, are this number.

### Active players

The game should track active players as an additional variable that can be used as a trigger for rules to manage cases like "all the players fell" (ie. when active players reaches 0, the display should reset).

| Expression             | Meaning                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `game.players.active`  | **Proposed name.** Players in shot and not removed. A player the model has lost for a moment, and is still holding, counts. |
| `game.players.removed` | **Proposed name.** Players removed since the display last reset.                                                            |

```json
{
  "on": { "when": "game.players.active == 0 and game.players.removed > 0", "forMs": 500 },
  "do": [{ "resetChallenge": true }]
}
```

Check `removed` too, as `active` is also 0 before anyone has walked into shot, or when everyone has walked out.

These values belong in `GameState.session`, and `toGameSnapshot` exposes them. Update them only when they change, as a game state update every camera frame would re-render the game every frame.

### Restore

By default, when a display resets, any 'removed' players are also reset (ie. becomes visible again).

**Proposed.** "When a display resets" means any of:

- `resetState` or `resetChallenge` runs;
- a reset display shows;
- a display with `resetStateOnShow` shows again.

Moving to another display also restores everyone, so nobody misses the next challenge. Leaving, invisible and static players return to normal too.

To opt out, a display component sets `keepRemovedPlayers`:

| Property             | Type    | Default | Meaning                                                              |
| -------------------- | ------- | ------- | -------------------------------------------------------------------- |
| `keepRemovedPlayers` | boolean | `false` | **Proposed.** Whether players stay removed when this display resets. |

Players can also be restored by a rule, as described at the top of this prompt:

```json
{ "effect": "player-restore", "players": "all", "durationMs": 500 }
```

| Property     | Type                                      | Default        | Meaning                                                                       |
| ------------ | ----------------------------------------- | -------------- | ----------------------------------------------------------------------------- |
| `players`    | see [Choosing players](#choosing-players) | `"triggering"` | Who to restore. As removed players can't fire rules, this is usually `"all"`. |
| `durationMs` | number                                    | `500`          | How long they take to fade back in.                                           |

### Falling effect

It should be possible to apply a falling effect to a player - their particular canvas should be moved downards until off-screen. Similar properties as found on the `item-fall` effect.

```json
{
  "on": { "interact": ["foot-enter"], "target": ".pit", "threshold": 0.3 },
  "do": [{ "effect": "player-fall", "durationMs": 1000, "easing": "ease-in" }]
}
```

| Property     | Type                                      | Default        | Meaning                                                                                    |
| ------------ | ----------------------------------------- | -------------- | ------------------------------------------------------------------------------------------ |
| `players`    | see [Choosing players](#choosing-players) | `"triggering"` | Who falls.                                                                                 |
| `durationMs` | number                                    | `1000`         | Time until they are off-screen. `"indefinite"` isn't allowed, as they must end up removed. |
| `easing`     | CSS easing function                       | `linear`       | How the fall speeds up.                                                                    |

The player keeps their distance property. **Proposed:** their depth freezes as the fall starts, so they stay in the same place among foreground items as they fall, even if they step forward.

From the moment the player starts to fall, they should not be able to interact with any items in the display.

**Proposed:** at that moment they fire the `-exit` of whatever they were over, as they do on leaving the shot (`PlayerMonitor.release`). They appear as a moving silhouette while falling, and are no longer drawn once removed.

Once off screen, the player should be marked as removed from the display.

### Spin away effect

This follows a similar pattern, but the player leaves the screen in a random direction with an upward motion, their canvas rotates as if they have been knocked.

```json
{
  "on": { "interact": ["body-enter"], "target": ".boulder", "threshold": 0.2 },
  "do": [{ "effect": "player-spin-away", "durationMs": 1200, "rotations": 2 }]
}
```

| Property     | Type                                      | Default        | Meaning                                                                                                                 |
| ------------ | ----------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `players`    | see [Choosing players](#choosing-players) | `"triggering"` | Who spins away.                                                                                                         |
| `durationMs` | number                                    | `1000`         | Time until they are off-screen. `"indefinite"` isn't allowed, as they must end up removed.                              |
| `rotations`  | number                                    | `2`            | **Proposed.** How many times they turn on the way. The direction of spin is random, to match their direction of travel. |
| `easing`     | CSS easing function                       | `ease-out`     | How the movement slows.                                                                                                 |

Depth, interactions, `-exit`s and removal work as they do for `player-fall`.

### Static

This applies an effect that uses a static effect to make the player seem to be partially transparent. The mask for this should have configurable pixel size, with a sensible default, and a target proportion of the player's pixels made transparent. The effect should ease in and out by altering the proportion of transaprent pixels.

```json
{
  "effect": "player-static",
  "players": "triggering",
  "durationMs": "indefinite",
  "pixelSize": 0.5,
  "proportion": 0.6,
  "easeMs": 500
}
```

| Property     | Type                                      | Default        | Meaning                                                                                                    |
| ------------ | ----------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------- |
| `players`    | see [Choosing players](#choosing-players) | `"triggering"` | Who it applies to.                                                                                         |
| `durationMs` | `number \| "indefinite"`                  | `"indefinite"` | How long it lasts, including easing in and out. If `"indefinite"`, it holds until stopped, then eases out. |
| `pixelSize`  | number                                    | `0.5`          | The size of each block of static, as a % of the display's width, so it looks the same at any scale.        |
| `proportion` | number, 0–1                               | `0.5`          | The target proportion of the player's pixels made transparent.                                             |
| `easeMs`     | number                                    | `500`          | **Proposed.** How long it takes to reach `proportion`, and to fade away again.                             |
| `easing`     | CSS easing function                       | `linear`       | How the proportion changes while easing.                                                                   |

The player is still active, and can still interact. It only changes how they are drawn, so interactions keep using the full `mask`.

**Proposed:** the pattern changes on each camera frame, like a detuned TV, and holds still for players who prefer reduced motion.

This one is drawn pixel by pixel in `DrawPeople.ts`, so run the vision bench before and after. Each player's canvas is already drawn separately.

## Duration modifiers

Duration for most effects will be set to a number of ms, but for some it will be continuous. To achieve this: `durationMs` should be typed as `number | "indefinite"`

If `indefinite` any animation applied to the element should loop when it completes.

An indefinite effect has no length to loop over, so each needs its own:

| Effect                                                 | `"indefinite"` | One loop is                                  |
| ------------------------------------------------------ | -------------- | -------------------------------------------- |
| `quake`                                                | Allowed        | `cycleMs`                                    |
| `item-fall`                                            | Allowed        | `cycleMs`, then it starts again from the top |
| `item-move`                                            | Allowed        | `cycleMs`, then it starts again from `start` |
| `highlight`                                            | Allowed        | The length of its `sequence`                 |
| `player-static`                                        | Allowed        | Doesn't loop: it holds                       |
| `player-fall`, `player-spin-away`                      | Error on load  | They must finish, to remove the player       |
| `player-invisible`, `player-visible`, `player-restore` | Error on load  | They are one-way changes                     |

An indefinite effect ends with `stop`, or when its display is hidden or resets.

## Delay

All actions should gain an optional `delayMs` property that allows the effect or action being applied to be delayed by a number of ms. (Optional, default 0.)

```json
{
  "on": { "interact": ["jump-onto"], "target": "#bridge" },
  "do": [
    { "effect": "quake", "target": "#bridge", "dx": 0.5, "dy": 0.5, "durationMs": 400 },
    { "effect": "item-fall", "target": "#bridge", "delayMs": 400 },
    { "set": { "bridgeGone": "true" }, "delayMs": 1400 }
  ]
}
```

`delayMs` moves from `GameSoundAction` and `GameRewardAction` to a base all actions share, keeping its name and behaviour for those two.

> [!NOTE]
> Rules change the game through pure functions of the latest state (`fireRules`), applied in one step. Delays can't happen in there. Timers belong in `GameRulesHook.ts`, as they do for `every` and `after`. Sounds and rewards already wait in `useRuleEffects`, but those timers aren't cancelled when a display is hidden, so a sound can play on the next display. Decide whether to change that.

**Proposed behaviour:**

- A rule's `if` is checked when it fires. It isn't checked again after the delay.
- Later actions don't wait for a delayed one. Like sounds, each counts from when the rule fired.
- A delayed action's expressions are worked out when it runs, from the state at that time, using the `event` from when the rule fired.
- A delayed action is cancelled if its display is hidden or reset first. This stops a late `completeChallenge` or `set` from changing a display that has moved on.
- `delayMs` is a number, not an expression. Add expressions when a game needs them.

## Open questions

Beyond the items marked **Proposed**:

1. Should there be a trigger for an effect ending, eg. `{ "effectEnd": "item-fall", "target": "#x" }`? The existing `animationEnd` won't fire if effects use the Web Animations API. Without one, authors must match a `delayMs` or `after` to the duration by hand.
2. Should `.player-N` work as a target for item effects, eg. a `highlight` on a player? This brief describes it for rewards and animations, but `filter` and `shadow` on a canvas would interact with drawing and static.
3. Should a player be able to fall or spin away in a game with no camera? Nothing happens with no player to apply them to, so the rule's other actions decide whether the game can still be finished.
