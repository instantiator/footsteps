# Template interactions

Please create a plan to implement new template interactions.

## Context

At current time, templates have limited interactions with the app. Elements with an `id` in the template of a `GameOverviewDisplay` can be listed in `clickIdToStageId` - so clicks (and camera interactions) can be mapped to an action to move the player to a given stage.

- This is limited to game overview displays
- This is limited to "interaction switches stage"
- Templates have no state of their own, and cannot react to time, animations, or changes in values

Templates cannot run code: they are compiled by Handlebars with `knownHelpersOnly`, and their output is sanitised by DOMPurify, because a game repository can be remote and is not trusted. This work should keep that boundary. Behaviour is described as data, never as script.

## Goal

Make interactions a generic capability of every display: a display can hold its own state, change it in response to events, and act on the game. Simple behaviours (toggles, counters, timers, reacting to the player) should be configurable in game data, without writing a React component for each one.

Full custom elements written in code are a separate piece of work (`003.00.00.prompt - custom game elements.md`). The state store and the game actions built here should be the ones that work reuses.

## Approach

### Add rules to `GameDisplayComponentBase`

Add a list of rules for display components.

Each rule has a trigger (`on`), an optional condition (`if`) and a list of actions (`do`). This protects the template: it only renders the state, it's not involved in changing it.

Rules can refer to elements with CSS selectors (`#door`, `.lava`), so any number of rules can apply to one element, and one rule can apply to many elements. Rules that don't concern an element (eg. reacting to the score) have no `target`.

Add `initialState`, `resetStateOnShow`, and `rules` to `GameDisplayComponentBase`, so that these can be provided for every display type:

```ts
/** Fields common to every display component. */
export interface GameDisplayComponentBase {
  type: GameDisplayComponentType;
  data: Record<string, unknown>;
  /** The component's state when it is first shown (and after a reset). */
  initialState?: Record<string, unknown>;
  /** Whether state returns to `initialState` each time the display is shown. Defaults to false. */
  resetStateOnShow?: boolean;
  /** What happens in response to events, in order. */
  rules?: GameRule[];
}

/** One behaviour: when the trigger fires and the condition holds, apply the actions in order. */
export interface GameRule {
  on: GameTrigger;
  /** Expression; the rule is skipped when it is false. */
  if?: string;
  do: GameAction[];
}

export type GameTrigger =
  /** Any player (or a click) interacts with an element matching `target`. */
  | {
      interact: GameInteraction | GameInteraction[];
      target: string;
      threshold?: number;
      /** Camera interactions only: also fire when the element is covered by another element. Defaults to false. */
      includeCovered?: boolean;
    }
  /** A CSS animation with this name ends on an element matching `target`. */
  | { animationEnd: string; target: string }
  /** A CSS transition of this property ends on an element matching `target`. */
  | { transitionEnd: string; target: string }
  /** The expression turns from false to true. */
  | { when: string }
  /** Repeatedly, every so many milliseconds (a number, or an expression). */
  | { every: number | string }
  /** Once, this many milliseconds after the display is shown (a number, or an expression). */
  | { after: number | string }
  /** When the display is shown. */
  | { start: true };

export type GameAction =
  /** Sets state keys to the values of expressions, all evaluated against the state before the action. */
  | { set: Record<string, string> }
  /** Returns state to `initialState`. */
  | { resetState: true }
  /** Marks this display's challenge as succeeded. */
  | { completeChallenge: true }
  /** Submits an answer to this display's challenge, checked as a typed answer is. */
  | { answer: string }
  /** Clears this display's challenge, including its state. */
  | { resetChallenge: true }
  /** Opens a stage, as `clickIdToStageId` does today. */
  | { enterStage: string };
```

We'll refine these interfaces and types during planning - the capabilities are what's important here.

### Expressions

Conditions (`if`, `when`), `set` values and timer durations are short expressions, eg. `state.score + 1`, `state.score >= data.target`, `if state.position == 1 then 2 else 1`.

We should use an existing sandboxed expression library rather than writing a parser.

> Security note: `eval` or `new Function` on game input represent a risk. Expressions should not have access to prototypes, globals or functions.

`filtrex` is a candidate library for this. During planning, confirm this choice or identify an alternative if it cannot be used. (`expr-eval` is believed to be inappropriate as it is unmaintained, and recognised as at risk of code injection.)

Expressions should see:

- `state` - this display's state
- `data` - the component's `data`, as authored
- `game` - a read-only snapshot of the game's progress (the `GameSnapshot` described in the 003 prompt)
- `event` - for element triggers: the matched element's `id` (empty if it has none), and the `interaction`

Compile each expression once, when the game data loads, so a mistake is reported early and names the display and rule.

`state`, `data`, and `game` should also be made available to templates (if they aren't already).

### State

- Each display should have its own state, initialised from `initialState`
- State is kept in a store above the display layers for the life of the game, so it survives the display being hidden and shown again.
- Element states should be stored alongside the game state, using the same storage mechanism (as implemented in `docs/prompts/000.05.01.plan - appplication tweaks.md`)
- If `resetStateOnShow` is true, state returns to `initialState` each time the display is shown.
- Resetting a challenge (including the `resetChallenge` action) resets the state of that challenge's displays.
- Templates receive `state` alongside the existing template data, and so do the Handlebars-rendered style values.

### Triggers

**Interactions** should use the existing interaction types:

- click
- hand
- foot
- head
- body
- any
- jump

A trigger should fire when any player interacts with any element matching `target`. They fire when an interaction begins, not on every frame, as the player monitor does today.

**Camera targets should support selectors.** `usePlayerInteractions` already re-measures each target's rectangle on every frame, but finds targets by id from `clickIdToStageId`.

Instead, it should run each camera rule's selector with `querySelectorAll` inside the game viewport on every frame. This supports newly created and moving elements (eg. falling balloons).

Any CSS selector should work: classes, attributes, descendants, `:not(...)`.

**Matched elements don't _need_ to have an `id`.** The player monitor should key its memory for each element (ie. when an interaction began, jump phases, etc.) by a string.

It can use the element's `id` when it has one. Otherwise generate a key per element, and hold it in a `WeakMap<Element, string>`, so that it can be dropped when the element is removed.

idiomorph keeps elements alive between renders, so an element will keep its key. (An element without an `id` that is replaced rather than patched will get a new key, and its interaction counts as beginning again, so we should give an element an `id` when that matters.)

**Clicks should use selectors too.** The layer's click handler currently takes the clicked element's `id`. It should instead use selectors: for each click rule, use `event.target.closest(selector)` to find the clicked element, or its nearest ancestor in the DOM tree, that matches - stopping at the layer. If nothing matches, the rule doesn't fire. A click that matches no rule does nothing, as it does today.

**Covered elements.** The browser delivers a click to the topmost element at that point that accepts pointer events. Anything covered by it never sees the click. At current time:

- Only the foreground layers have a click handler (see `LowerDisplayLayers` and `UpperDisplayLayers` in `src/components/core/layout/GameLayersLayout.tsx`). Clicks on background layers are never handled.
- Each display's template container fills its grid cell, and accepts pointer events (via `.childClicksOnly` in `GameLayersLayout.css`), even when the display has no foreground template. So a foreground blocks clicks to everything beneath it, including empty space.

We should change this so that only elements drawn by a template can cover others:

- Every layer, background and foreground, should have the click handler.
- Template containers (and the layers and grids around them) should let pointer events through. Elements inside a template should accept them. eg. `pointer-events: none` on the container, and `pointer-events: auto` on its descendants.
- Template authors can still set `pointer-events: none` on decorative elements, so they don't block what's beneath them.

**Camera interactions should match clicks.** At current time, the camera compares each target's rectangle with the player's body, so a covered element can still be "touched". Instead, a camera interaction should only count where the element is the topmost element under the body part, as a click would - eg. hit-testing with `document.elementFromPoint` at the body part's position, and checking the result is the element or inside it. The plan should choose an approach that stays cheap enough to run on every frame.

If `includeCovered` is true on an interaction trigger, camera interactions ignore covering, and use the element's rectangle alone, as they do today. It has no effect on clicks.

**`animationEnd` / `transitionEnd`** are the browser's `animationend` / `transitionend` events. They bubble, so the existing delegating handler on the layer wrapper (`GameLayerWrapper`) can catch them, filtered by animation name or property and by `target`.

**`when`** is edge-triggered: it fires when the expression changes from false to true, after any state or game change, and not again until it has been false.

**`every` / `after` / `start`** run only while the display is shown. Timers stop when it is hidden.

### Actions

`set` replaces a previous proposal to use JSON Patch. Incrementing, toggling and computed values are all expressions.

Showing and hiding elements is will be managed by state. eg. `{{#if state.doorOpen}}` in the template.

For challenge and stage actions, we can reuse the existing pure functions:

- `completeChallenge`
- `validateAnswer`

See:

- `src/components/core/logic/GameStateUtils.ts`
- `src/components/core/logic/GameClickUtils.ts`

No rule receives `setGameState`.

`set` can make a `when` rule fire, which can `set` again. Cap the depth of such a chain, log the display and rule when the cap is hit, and stop.

### Replacing `clickIdToStageId`

Once rules work, migrate the existing games and remove `clickIdToStageId` from the data model, the code, the schemas and the docs. Each entry should become a rule:

```json
{ "on": { "interact": ["click", "hand"], "target": "#stage-1-door" }, "do": [{ "enterStage": "stage-1" }] }
```

### Responding to changes

`GameDisplayTemplateComponent` currently creates a `<div>`, and uses `dangerouslySetInnerHTML` to generate the component content. When the HTML changes, every element is replaced. This means CSS transitions can't run, and keyframe animations would restart.

#### idiomorph

We've assessed options, and we'll use `idiomorph` to retain elements between renders, matched by `id`, so they can be transitioned and animated from their previous state.

```bash
npm install idiomorph
```

Component body hooks:

```tsx
const bodyRef = useRef<HTMLDivElement>(null);

// Patches the template's DOM in place, matching elements by id, so CSS transitions run between renders
useLayoutEffect(() => {
  if (!isDefined(html) || !bodyRef.current) return;
  Idiomorph.morph(bodyRef.current, DOMPurify.sanitize(html, SANITIZE_OPTIONS), { morphStyle: "innerHTML" });
}, [html]);
```

In the jsx/tsx, we'll replace the div:

```tsx
{
  isDefined(html) && (
    <div style={templateStyleParsed} dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html, SANITIZE_OPTIONS) }} />
  );
}
```

with:

```tsx
{
  isDefined(html) && <div ref={bodyRef} style={templateStyleParsed} />;
}
```

Everything that animates or keeps state should have an `id`, so idiomorph matches it reliably between renders. Changing an element's `id` (eg. `balloon-{{state.balloon}}`) would make idiomorph create a new element (and so restart its animations). That's a simple way to "spawn" a replacement.

#### Alternatives

Alternatives included:

- The View Transitions API (provided by the browser). By providing a `view-transition-name`, the browser can animate between old and new snapshots, even if the element is fully replaced. It applies to the whole document, so it may interfere with the camera canvas.

- Parsing the HTML into React elements with `html-react-parser` (uses the virtual DOM to preserve elements). Seems more complex for similar gain.

## Examples

Build an example game in the local repository.

- It should have a basic title
- It should have a basic description
- It should have a simple overview with an entry for each stage

Stages:

1. Balloons
2. The floor is lava

These can be used as end-to-end tests, and a demonstration, of the feature.

### Toggle

An element that moves between two positions when clicked or touched.

```json
"component": {
  "type": "template",
  "data": {},
  "initialState": { "position": 1 },
  "rules": [
    { "on": { "interact": ["click", "hand"], "target": "#switch" },
      "do": [{ "set": { "position": "if state.position == 1 then 2 else 1" } }] }
  ]
}
```

```html
<div id="switch" class="switch position-{{state.position}}"></div>
```

```css
.switch {
  position: absolute;
  transition:
    left 0.4s ease,
    top 0.4s ease;
}
.switch.position-1 {
  left: 10%;
  top: 20%;
}
.switch.position-2 {
  left: 70%;
  top: 60%;
}
```

### Balloons

A challenge foreground:

- balloons drop from the top at a rate defined in the component's state, moving from side to side
- when the player's hand touches one, it pops, the score goes up, and a new balloon appears
- when a balloon reaches the bottom, it pops with no score, and a new balloon appears
- when the score reaches a number defined in the component's data, the challenge succeeds
- the score is shown on screen

The movement is pure CSS: a linear `fall` whose duration comes from state, plus an infinite side-to-side `sway`. Reaching the bottom is the end of the `fall` animation.

```json
"component": {
  "type": "template",
  "data": { "target": 10 },
  "initialState": { "score": 0, "balloon": 0, "popping": false, "dropMs": 4000 },
  "resetStateOnShow": true,
  "rules": [
    { "on": { "interact": ["hand", "click"], "target": ".balloon" }, "if": "not state.popping",
      "do": [{ "set": { "popping": "true", "score": "state.score + 1" } }] },
    { "on": { "animationEnd": "fall", "target": ".balloon" },
      "do": [{ "set": { "popping": "true" } }] },
    { "on": { "animationEnd": "pop", "target": ".balloon" },
      "do": [{ "set": { "popping": "false", "balloon": "state.balloon + 1" } }] },
    { "on": { "when": "state.score >= data.target" },
      "do": [{ "completeChallenge": true }] }
  ]
}
```

```html
<div
  id="balloon-{{state.balloon}}"
  class="balloon{{#if state.popping}} popping{{/if}}"
  style="--drop-ms: {{state.dropMs}}ms"
></div>
<p id="score">{{state.score}}</p>
```

```css
.balloon {
  position: absolute;
  top: -10%;
  left: 45%;
  animation:
    fall var(--drop-ms) linear forwards,
    sway 1.5s ease-in-out infinite alternate;
}
.balloon.popping {
  animation: pop 0.3s ease-out forwards;
}
@keyframes fall {
  to {
    top: 100%;
  }
}
@keyframes sway {
  from {
    margin-left: -10%;
  }
  to {
    margin-left: 10%;
  }
}
@keyframes pop {
  to {
    transform: scale(1.6);
    opacity: 0;
  }
}
```

Note: the `pop` animation must start from where the balloon is when it pops, not from the top. The plan should check this works (eg. by freezing `top` with `animation-fill-mode`, or a computed position held in state) and adjust the example.

### Lava

A challenge background:

- some elements represent lava
- when a player's foot touches lava, the exit door disappears
- when a player's foot touches the start point, the exit door reappears
- when a player's foot touches the base of the exit door, the challenge is complete

```json
"component": {
  "type": "template",
  "data": {},
  "initialState": { "doorOpen": true },
  "resetStateOnShow": true,
  "rules": [
    { "on": { "interact": "foot", "target": ".lava" },
      "do": [{ "set": { "doorOpen": "false" } }] },
    { "on": { "interact": "foot", "target": "#start" },
      "do": [{ "set": { "doorOpen": "true" } }] },
    { "on": { "interact": "foot", "target": "#door-base" }, "if": "state.doorOpen",
      "do": [{ "completeChallenge": true }] }
  ]
}
```

```html
<div id="lava-1" class="lava" style="left: 20%; top: 60%"></div>
<div id="lava-2" class="lava" style="left: 55%; top: 70%"></div>
<div id="start" class="start"></div>
{{#if state.doorOpen}}
<div id="door" class="door"><div id="door-base" class="door-base"></div></div>
{{/if}}
```

## Out of scope

- **Conditions over all players** (eg. "when every player's feet are on the start point"). Interaction triggers fire for any one player. Expressing "all players" needs a design for player counts, and possibly stable player identities across frames. Record it in `docs/outstanding-issues.md`.
- **Shared state between displays.** Each display has its own state. If a stage display and a challenge display need to share values, that is later work.
- **Running template code.** Templates stay logic-less and sanitised.

## Open questions for the plan

- The expression library, and its syntax for conditionals and booleans.
- How rules are validated: schema shape, expressions compiled at load, selectors that match nothing in the template (a warning).
- Where `answer` fits with the existing answer entry, and what feedback (sound, reward) it triggers.

## Constraints and conventions

- Follow `AGENTS.md`: no `any` or equivalent type escapes, zero warnings, comments that state intent, and change only what the work requires.
- Keep DOMPurify sanitisation and `knownHelpersOnly` as they are.
- Regenerate the schemas and the TSDoc after changing `src/entities/`, as the pre-commit hook does.
- Update `docs/game-data.md`, `docs/dev-overview.md` and any docs mentioning `clickIdToStageId`.
- Tests cover each trigger, each action, edge triggering of `when`, the loop cap, `resetStateOnShow`, state reset on challenge reset, clicks and camera interactions on covered elements (with and without `includeCovered`), clicks passing through empty foreground space, and the three examples.
- Run `dev-qual/scripts/check.sh` after every stage, and `--comprehensive` in the final stage.

## Done when

- `clickIdToStageId` is gone, and the existing games work through rules.
- The toggle, balloons and lava examples play correctly with a mouse and with the camera, through the dev server and a static build.
- Display state survives hiding and showing, resets when `resetStateOnShow` is set, and resets with its challenge.
- Elements in background layers can be clicked where nothing covers them, and covered elements respond to neither clicks nor the camera, unless `includeCovered` is set.
- `dev-qual/scripts/check.sh --comprehensive` passes.
