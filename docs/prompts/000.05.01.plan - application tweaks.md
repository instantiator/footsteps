# Plan: game landing page, permissions, keep-awake, and saved progress

- **Branch:** `000.05.00-application-tweaks`
- **Commits:** one commit per stage, after its gate passes
- **Orchestrator:** DeepSeek V4.1 Flash. One model for every stage: the stages share decisions and context.

## Context

The application currently drops straight into a game, asks for the camera lazily when a camera display
opens, has no saved progress, and lets the device sleep while a game is open. This work adds a landing
page for each game, checks required permissions up front, saves progress for New game/Continue, and
keeps the screen awake while a game is running.

The prompt is [`000.05.00.prompt - appplication tweaks.md`](000.05.00.prompt%20-%20appplication%20tweaks.md).

### Decisions taken

| Decision             | Choice                                                                                                                |
| -------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Landing route        | `/game/:id` is the landing page; `/game/:id/play` plays the game                                                      |
| Play access          | A direct visit to `/play` redirects to the landing page when a required permission is missing                         |
| Landing look         | Full-viewport tile graphic; title/description and permissions panels in the tile's translucent style; the game's font |
| Required permissions | Camera when `modules.camera.enabled` or any overview/stage/challenge display sets `camera.enabled`                    |
| Permission check     | `navigator.permissions.query({ name: "camera" })` on landing load                                                     |
| Permission fallback  | Unsupported query shows not granted with a Grant button; a successful `getUserMedia` counts as granted                |
| Grant                | `getUserMedia({ video: true })`, stop the tracks at once, re-check                                                    |
| Button gating        | New game and Continue are disabled until every required permission is granted and checks finish                       |
| Storage              | `localStorage`, one versioned progress projection per game; strict validation against the current game data           |
| Save timing          | Save every change after the initial render; do not save the initial blank state                                       |
| Keep-awake           | Screen Wake Lock API, reacquired when visible, released when the game completes or unmounts                           |
| New dependencies     | None                                                                                                                  |

### Constraints and reuse

- Reuse `isDefined`, `getCameraStream`, `resolveResources`, the existing provider stack, and the tile's panel styling.
- No `any` casts, no new dependencies, no secrets.
- TSDoc every exported symbol; comments state intent.
- Keep the browser suite's fake camera; update its URLs to `/game/:id/play`.
- The app is prerendered: add `/game/:id/play` to `react-router.config.ts`.
- Do not edit historical prompt or plan files. The deleted keep-awake prompt and the new application prompt are user work; leave them out of the stage commits unless a stage changes them.

### Stage 1: Landing route and visual shell

**Brief:** Split the routes: `/game/:id` renders a new `LocalGameLanding` page, `/game/:id/play` renders
`LocalGame`, and `/game/:id/json` stays as it is. Add `/game/:id/play` to the prerender list. Add
`src/pages/LocalGameLanding.tsx` with the feature-flag, repository, and game-data providers. Add
`src/components/landing/GameLanding.tsx` and `GameLanding.css`: a full-viewport background from the
game's resolved `tileGraphic` (fallback `#dce8f5`), the title and description in a translucent panel,
the game's `gameContainerStyle.fontFamily`, and a bottom-right New game button that navigates to
`/game/:id/play`. Extract `GameStylesheets` and `isAllowedStylesheet` from `Game.tsx` into a shared
component used by both pages. Share the tile panel's translucent styling rather than duplicating it.

**Tests:**

- `tests/GameLanding.test.tsx`: title, description, tile background, fallback background, game font, New game navigation, unknown game.
- `tests/LocalGame.test.tsx`: the play route is `/game/:id/play`.
- `tests/browser/camera.spec.ts` and `tests/browser/viewport.spec.ts`: use `/game/:id/play`.

**Gate:** `dev-qual/scripts/check.sh --fast` + the selected Vitest files + `npm run build`.
Expected: all pass, and the build prerenders both `/game/:id` and `/game/:id/play`.

### Stage 2: Up-front camera permission

**Brief:** Add `src/components/core/logic/GamePermissionUtils.ts` with a camera-only permission id, a
game-data scan that decides whether the camera is required, a browser check through
`navigator.permissions.query`, and a request through `getCameraStream` that stops the stream's tracks.
Add a permissions panel below the title panel in `GameLanding`: every required permission gets a check
mark when granted, otherwise a Grant button; no required permissions shows "No permissions needed."
Disable New game while checks run or any permission is ungranted. Re-check after a request; if the
Permissions API cannot confirm a successful request, keep it granted. Add the `/play` redirect: if a
required permission is not granted, `LocalGame` sends the player back to the landing page.

**Tests:**

- `tests/GamePermissionUtils.test.ts`: camera required from the module, overview, stage display, and challenge display; not required when no camera is enabled; query states; request success and failure; unsupported API.
- `tests/GameLanding.test.tsx`: no-permissions text, check mark, Grant request and re-check, disabled/enabled New game, unsupported API.
- `tests/LocalGame.test.tsx`: a direct play visit redirects to the landing page when the camera permission is missing.

**Gate:** `dev-qual/scripts/check.sh --fast` + the selected Vitest files.

### Stage 3: Saved progress and New/Continue

**Brief:** Add `src/entities/state/GameStateStorage.ts`: a `footsteps:game-state:<gameId>` key, a versioned
projection of stage progress, succeeded challenge IDs, and the current stage/overview; strict validation
against the current game data; availability and completion derived rather than trusted. `GameStateProvider`
resumes from storage and saves every change after the initial render. The landing page's New game clears
this game's stored state and navigates to play; Continue appears only when a valid state loads and
navigates to play. Clear localStorage before each test so tests cannot leak progress into one another.

**Tests:**

- `tests/GameStateStorage.test.ts`: round trip, blank state, partial and completed progress, corrupt JSON, wrong version, wrong game id, changed stage/challenge structure, derived availability/completion, clearing.
- `tests/GameStateProvider.test.tsx`: resumes stored progress, saves after a change, starts blank when nothing valid is stored.
- `tests/GameLanding.test.tsx`: New game always shown, Continue hidden without storage, Continue shown and resumes, New game clears and navigates.

**Gate:** `dev-qual/scripts/check.sh --fast` + the selected Vitest files.

### Stage 4: Keep-awake

**Brief:** Add `src/components/core/WakeLockHook.ts` with `useWakeLock(active)`. It requests a screen wake
lock when active and visible, releases it when inactive or unmounted, reacquires it on
`visibilitychange`, and warns rather than failing when the API is unavailable or rejects. Call it from
`Game` with active = the game is not complete (not every stage completed).

**Tests:**

- `tests/WakeLock.test.ts`: requests when active, no request when inactive, releases on deactivation and unmount, releases when hidden and reacquires when visible, handles unsupported and rejected requests.
- `tests/Game.test.tsx`: the game holds a wake lock while incomplete and releases it once every stage is complete, if it can be set up cleanly.

**Gate:** `dev-qual/scripts/check.sh --fast` + the selected Vitest files.

## Verification

On `magic-trifle` the landing shows the tile background and game font with "No permissions needed." and
New game enabled. With the camera module enabled, the landing lists the camera permission, Grant prompts
the browser, and both buttons enable after success. New game starts a fresh game; Continue only appears
after progress and resumes it; New game erases it. The device stays awake while the game is incomplete,
and the wake lock is released when it completes. The browser suite passes against `/game/:id/play`.
